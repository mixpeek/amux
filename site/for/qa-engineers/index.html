amux for QA Engineers

Test generation is inherently parallel. So is amux.

Quality assurance work is some of the most systematic, pattern-driven engineering in the stack. Writing unit tests, generating edge cases, finding uncovered branches, reviewing PRs for logic bugs — these are tasks an AI agent can execute reliably, and amux can run them in parallel across your entire codebase in a single overnight run.

The coverage gap problem

Most codebases have significant coverage gaps not because engineers do not know how to write tests, but because writing tests is slow relative to writing features. A module that would take a developer 4 hours to fully test can be covered by a Claude Code agent in 20–30 minutes. With 10 parallel agents running overnight, you can cover an entire service.

amux lets you turn the coverage gap into a board task queue: one task per module, one agent per task, all running simultaneously.

What QA engineers use amux for

  • Unit test generation at scale. Queue one task per module, each specifying the test framework, coverage requirements, and edge cases to include. Ten agents run in parallel overnight. Morning: a stack of test files ready to review.
  • Coverage gap analysis and fill. Feed an agent your coverage report and ask it to write tests specifically for uncovered lines and branches. Run multiple agents in parallel, each targeting a different coverage gap.
  • PR code review. Assign a dedicated review agent per open PR: check for missing error handling, race conditions, boundary conditions, and logic errors not caught by existing tests. Multiple dimensions reviewed in parallel.
  • Regression suite generation. For every bug fix, queue an agent to write a regression test that would have caught the bug. Build your regression suite automatically as tickets close.
  • API contract testing. Generate request/response tests for every endpoint in your API. One agent per endpoint or per service, all building simultaneously.
  • Integration test scaffolding. Generate the boilerplate for integration tests, database fixtures, and mock services — the setup work that slows down writing the tests themselves.

Quick start: test generation fleet

# Install amux
git clone https://github.com/mixpeek/amux && cd amux && ./install.sh

# Register your project
amux register myapp --dir ~/Dev/myapp --yolo

# Add test generation tasks to the kanban board
# (one per module — agents claim these atomically, no duplicates)
curl -X POST https://localhost:8824/api/board \
  -H 'Content-Type: application/json' \
  -d '{"title":"Generate unit tests for src/auth.py — cover happy path, invalid token, expired token"}'

curl -X POST https://localhost:8824/api/board \
  -H 'Content-Type: application/json' \
  -d '{"title":"Generate unit tests for src/billing.py — cover payment success, declined, refund"}'

# Start 10 parallel agents (each claims its own task from the board)
for i in $(seq 1 10); do
  amux start myapp
done

# Monitor from the dashboard or iOS app
amux serve  # → https://localhost:8824

Quality gates for generated tests

Generated tests need to pass before they are useful. Configure amux to enforce passing tests before closing each task by adding to your CLAUDE.md:

# CLAUDE.md
After writing tests, run: pytest src/tests/ -x --tb=short
All tests must pass before you mark the task complete.
If tests fail, debug and fix them — do not skip or stub expectations.

The agent will see pytest output, fix failing assertions, and iterate until tests pass. This loop typically converges in 2–3 runs per module.

Per-PR review agents

For code review, run a dedicated agent per PR with a structured review prompt:

amux send myapp-reviewer "Review PR #47:
1. Check for missing error handling on all external calls
2. Find race conditions in concurrent code paths
3. Identify boundary conditions not covered by existing tests
4. Flag any security issues in the auth flow changes
Report findings with file:line references."

Run multiple review agents in parallel — one checking security, one checking performance, one checking logic — and collect their findings in the amux board.

  • 6:00 PM — Queue 20 module-level test generation tasks to the amux board
  • 6:05 PM — Start 10 Claude Code agents; they begin claiming tasks immediately
  • 6:30 PM — Check the iOS app: 5 tasks in progress, 2 already complete
  • 8:00 AM — Morning: all 20 tasks complete, 18 with passing tests, 2 with partial coverage needing review
  • 9:00 AM — Open the PRs, review generated tests, merge the clean ones

Browser and UI automation with Robots

Beyond code-level testing, amux supports intent-based browser automation through Robots — reusable SOP files that describe browser tasks in plain language. Unlike brittle coordinate-recording scripts, a Robot re-resolves its intent on each run: it finds elements by meaning, not fixed position. QA workflows that work well as Robots:

  • Smoke test a deployed app. Navigate to production, log in with test credentials, exercise the critical path, report what succeeded and what failed. Schedule it nightly, report to the board.
  • Form validation sweep. Submit a form with boundary values — blank, max length, invalid types — and verify error handling. Run it against every form after a UI change.
  • Visual regression baseline. Screenshot key pages before and after a deployment. Hand the two sets to a coding agent that diffs them and files board cards for regressions it detects.
  • End-to-end flow verification. A Robot walks the user-facing signup or checkout flow end-to-end, verifying each step. No test harness setup required — it uses the real browser, the real app.

Robots compose with coding agents: a Robot can exercise a UI and capture output, then hand it to a Claude Code agent that processes the results and updates the board. QA pipelines that mix browser work and code analysis run as a coordinated sequence, not a custom script.

Workspace isolation for parallel test runs

Running 10 agents against the same codebase creates a shared-worktree problem: agent A's uncommitted test file can make agent B's test suite go red, even though B's code is clean. This produces false failures that look like flaky tests.

amux's workspace isolation mode gives each agent its own git worktree, scratch directory, and TMPDIR. Enable it with one environment variable:

AMUX_WORKSPACE_ISOLATION=1  # in worker, group, or global scope

With isolation on, each test-generation agent writes to its own branch. Test results reflect only that agent's changes. When each agent is done, it opens a PR with its additions — clean diffs, no cross-contamination.

Standing approvals for overnight test runs

Test generation agents hit permission prompts when they write new files, run the test suite, and commit changes. Without pre-authorization, these prompts block overnight runs. Standing approvals let you pre-authorize common action categories once from the dashboard:

  • Write files matching tests/**
  • Run pytest or npm test
  • Create git commits with message matching test: ...

Agents that hit an approved category proceed automatically. Everything outside the approved set still prompts. QA teams that run test-generation overnight routinely configure 3-5 standing approvals and wake up to 200+ new test files with zero intervention.
