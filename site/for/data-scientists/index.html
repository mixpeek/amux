amux for Data Scientists — Parallel AI Agents for EDA, Modeling & Pipeline Automation

Data science work is embarrassingly parallel: multiple datasets, multiple experiments, multiple model variants, multiple pipelines. amux runs one Claude Code agent per task in parallel, resumes them after usage limits, and lets you monitor everything from your phone. Updated September 2026.

  • Standing approvals (AMUX-5270): pre-approve filesystem reads, shell commands, and API calls so overnight EDA and training runs never pause for permission. Guide →
  • Auto-approve (AMUX-5301): per-ask policies route sign-in, key, and grant requests back to the worker queue instead of waking you up at 3 AM.
  • CUA computer-use sandboxes (AMUX-5300): rung 3 of the browser access ladder — agents can now automate native desktop apps (Jupyter, database GUIs, local data tools) that a headless browser cannot reach. Guide →

  • Goal keeper: declare a goal (e.g. "AUC above 0.85") and the harness re-prompts the agent at each turn until the goal is met or time runs out.

What data scientists use amux for

amux is an open-source control plane for running an AI engineering team from a single dashboard. For data scientists, it solves the core workflow problem: data work divides naturally into parallel streams, but running AI agents on all of them simultaneously used to require custom scripts and constant babysitting. amux handles that orchestration layer — launching agents, monitoring them, resuming them after usage limits, and reporting results to a shared kanban board — so you can run five experiments while you sleep and wake up to results, not crashed terminals.

The five highest-value use cases for data scientists:

  1. Parallel EDA — one agent per dataset or analysis question, running simultaneously
  2. Experiment fleet — one agent per model variant (different arch, hyperparameters, features)
  3. Notebook-to-production conversion — agent converts messy notebooks to tested Python scripts
  4. Pipeline automation — scheduled agents run ETL, transformation, and validation jobs
  5. Documentation generation — agent reads codebase, generates API docs, schema descriptions, data dictionaries

Instead of waiting for one analysis to finish before starting the next, you assign all of them at once:

Setting up a data science agent fleet

curl -fsSL https://amux.io/install.sh | bash

# Create a workspace pointing to your project
amux register ds-project --dir ~/Dev/my-ds-project

# Start the session manager
amux start ds-project

# Open the dashboard
amux serve  # → https://localhost:8824

# Launch your first parallel agents from the dashboard
amux send ds-project "Run EDA on data/sales_q3.csv — describe all columns, flag outliers (3σ), suggest 3 feature engineering candidates, write report to reports/eda_sales_q3.md"

With --yolo mode, agents run without confirmation prompts — safe for automated analysis and pipeline runs where you're not at the keyboard. Use a CLAUDE.md file to give agents domain context: column naming conventions, acceptable null rates, business definitions of key metrics.

Parallel EDA: one agent per dataset

The most common data science fleet pattern: assign one analysis agent per dataset or hypothesis, let them all run simultaneously, then review the reports together.

# CLAUDE.md — shared context for all agents in this workspace
# Column conventions: snake_case, date cols end in _at, ids end in _id
# Null rate > 20% = flag for imputation. Revenue is always in USD cents.
# Target variable: 'converted' (bool). Positive class is rare (~3%).

# Send parallel EDA tasks
amux send ds-project "EDA on data/train.csv — describe all features, compute correlation matrix with target, flag high-null columns, suggest top 5 features. Write to reports/eda_train.md"
amux send ds-project "EDA on data/test.csv — check distribution drift vs train.csv on all numeric features. Write drift report to reports/drift_analysis.md"
amux send ds-project "Profile data/external_signals.csv — check join key coverage vs train.csv (field: user_id), describe signal columns, recommend which signals to join. Write to reports/external_signals_profile.md"

All three run in parallel. amux's kanban board shows their progress. When each finishes, the card moves to done and the output file is in your project directory.

Experiment fleet: parallel model training

Run a grid search or ablation study as a fleet of agents. Each agent implements and evaluates one experiment variant:

# Experiment fleet — each variant runs as a separate agent card
curl -sk -X POST -H 'Content-Type: application/json' \
  -d '{"title":"XGBoost baseline — lr=0.1, depth=6","session":"ds-project","status":"todo"}' \
  $AMUX_URL/api/board

curl -sk -X POST -H 'Content-Type: application/json' \
  -d '{"title":"LightGBM + SMOTE — class_weight=balanced","session":"ds-project","status":"todo"}' \
  $AMUX_URL/api/board

curl -sk -X POST -H 'Content-Type: application/json' \
  -d '{"title":"CatBoost — categorical features native","session":"ds-project","status":"todo"}' \
  $AMUX_URL/api/board

amux's session loop auto-assigns queued cards to available agents. Each agent picks up its card, implements the experiment, writes results to a shared experiments/ directory, and marks the card done with the AUC score in the description. You review all three results from the board without opening a notebook.

Notebook-to-production conversion

Notebooks accumulate technical debt fast. An amux agent can convert them systematically:

amux send ds-project "Convert notebooks/churn_model_v3.ipynb to production code:
1. Extract preprocessing steps to src/preprocessing.py (functions, not globals)
2. Extract model training to src/train.py (CLI args: --data-path, --output-model-path)
3. Extract evaluation to src/evaluate.py (outputs metrics.json)
4. Write tests for preprocessing functions to tests/test_preprocessing.py
5. Keep the notebook working by importing from src/ instead of inline code
Report any data leakage or reproducibility issues you find."

The agent works through the notebook file-by-file, refactoring inline code into proper modules and tests. You get production-ready code without spending a day doing it manually.

Scheduled pipeline runs

Use amux's scheduler to run pipeline agents on a cadence:

# Schedule a daily data validation run
curl -sk -X POST -H 'Content-Type: application/json' \
  -d '{
    "title": "Daily data quality check",
    "session": "ds-project",
    "command": "Run data/quality_check.py against today'\''s data drop. If any check fails, post a board card titled ALERT: Quality Check Failed with the failing rules. If all pass, post Daily QC passed YYYY-MM-DD.",
    "schedule_expr": "daily at 7am"
  }' \
  $AMUX_URL/api/schedules

The agent runs every morning before you wake up. The board card tells you whether the data is clean or needs attention. You check it from your phone over coffee — no laptop required until something actually needs fixing.

Monitoring overnight runs from your phone

amux's iOS app and mobile PWA give you full visibility into all running agents:

  • Board view: see which analyses are done, doing, or failed — swipe between columns on mobile
  • Peek panel: tap any session to see the live terminal output, including model training progress
  • Push notifications: get alerted when a critical analysis fails or finishes
  • Send commands: steer a running agent from your phone without opening a laptop

Each agent runs in tmux, so a dropped network connection or closed terminal does not stop it. When a usage limit hits, amux holds delivery and resumes the agent at the provider's reset. If an agent process itself crashes, the amux server does not restart it today; stall detection flags the session so you see it in the morning.

Frequently asked questions

How do data scientists use amux?

Data scientists use amux to run multiple Claude Code agents simultaneously on different parts of a data workflow. One agent handles exploratory data analysis on dataset A while another writes model training code for experiment B, a third converts a notebook to a production Python script, and a fourth generates documentation. All four run in parallel, resume after usage limits, and report to a shared kanban board monitored from a web browser or iPhone. This multiplies effective output without multiplying headcount.

Can Claude Code work with Jupyter notebooks?

Yes. Claude Code can read, modify, and generate Jupyter notebooks (.ipynb) as text files, and can run Python scripts that exercise notebook logic. The standard pattern is to give an amux agent a notebook path and ask it to analyze the code, fix issues, or convert cells to a production script. For interactive work, the agent edits the notebook file and you reload it; for automated runs, the agent generates a .py equivalent that runs headlessly. amux runs the agent in tmux, so it keeps running even if the notebook session drops.

How do I run data pipeline code overnight with AI agents?

Create a workspace with your pipeline code and use amux's scheduler to trigger an agent at a set time. The agent runs the pipeline, writes a summary to the amux board, and resumes on its own if it hits a usage limit. You can monitor progress from the iOS app or mobile PWA — no laptop required. If the pipeline fails overnight, the board shows the failed card with the error output so you can diagnose it in the morning. Use amux's CLAUDE.md to give the agent domain-specific instructions (column conventions, naming rules, acceptable data quality thresholds).

Can AI agents help with model training code?

Yes. The standard amux pattern is to run one agent per experiment: each agent implements a model variant (different architecture, hyperparameters, feature set) in parallel, writes training code, and produces evaluation metrics. A coordinator agent can synthesize the results. Because agents run in isolated tmux sessions with separate working directories, experiments don't interfere. amux's kanban board shows which experiments are running, which finished, and which need human review — useful for managing a grid search across many combinations.

What is the difference between amux and a Jupyter kernel for data science?

A Jupyter kernel is single-session and interactive. amux manages a fleet of long-running, unattended AI agents. They complement each other: use Jupyter for interactive exploration, then hand off to amux when you need the same analysis repeated on 20 datasets, or when you want an agent to work overnight without your laptop staying open. amux runs the agent in tmux, so it keeps going even if the network drops or the terminal disconnects — Jupyter's kernel dies when the connection closes.

Is amux free for data scientists?

The amux orchestration layer is free and open source (MIT + Commons Clause). You pay only for the AI API tokens your agents consume — Claude Code Max ($100/month for unlimited Opus usage), Codex API by the token, or Gemini CLI via Gemini API. amux itself has no seat fees, usage caps, or subscription. The amux cloud offering ($25/month) adds a public dashboard URL and managed hosting for teams who don't want to self-host.

Can I use amux with Gemini CLI or Codex instead of Claude Code?

Yes. amux is multi-runtime: it manages Claude Code, OpenAI Codex CLI, and Gemini CLI sessions in the same dashboard. You can run a Claude Code agent for analysis tasks (better at reasoning and code review) and a Codex agent for boilerplate generation in parallel, distributing work across providers. This also distributes API rate limits — if Claude's rate limit is hit on one session, other sessions using different providers keep running.
