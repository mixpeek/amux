amux for Product Managers

Assign tasks to an AI coding team via a shared kanban board. Track progress from your phone. Ship features without waiting on engineering bandwidth. Updated September 2026.

amux is an open-source control plane for running an AI engineering team from a single dashboard or your phone. For product managers, it means a shared kanban board where you add tasks in plain English and a fleet of Claude Code, Codex, or Gemini CLI agents picks them up, works them, and reports back — while you watch from mobile.

What product managers do with amux

Assign work
Add a card, the agent picks it up

Write the task in plain English on the board. Agents claim cards automatically and post progress as they work. No sprint planning required.

Monitor
Live status from any device

The iOS app and mobile PWA show every session's status, current task, and token spend. Check progress from your phone without opening a laptop.

Steer
Redirect agents mid-task

Send a message to any session in plain English from the peek panel. The agent incorporates the feedback and continues — no restart, no lost work.

Review
Read agent output before merge

The peek pane shows terminal output and git diff. Board cards gate on acceptance criteria you set — agents self-report when they're done and ready for your sign-off.

Overnight
Wake up to shipped features

Queue the sprint backlog before EOD. Agents run overnight with self-healing (auto-compacts context, restarts on crash). Check the board at 9am — done column is full.

Coordinate
Task dependencies and reviewers

Board cards support depends_on and reviewer fields. Agent A waits for Agent B. You are the reviewer for high-stakes cards. The dependency graph is traversed automatically.

The PM workflow: from backlog to shipped

  1. Add tasks to the board. From the amux dashboard or iOS app, add a card with a plain-English description: "Add pagination to the /users endpoint, 20 results per page, cursor-based, include total count." No need to specify how — that's the agent's job.
  2. Agents claim and work tasks. Each registered session picks up the next available card, signals "doing", and starts working. You see the status change in real time on the board.
  3. Read the plan strip before the agent acts. The plan strip shows the agent's next steps in the peek panel before it executes them. If the approach is wrong, send a steering message now rather than after the code is written.
  4. Steer from mobile as needed. From the iOS app or mobile PWA, open the session peek and type a plain-English redirect: "Skip the cursor pagination for now — just use offset/limit. We'll revisit." The agent incorporates it and continues.
  5. Review the board at the end of the day. Cards in the done column have self-reported completion. Read the peek output or diff, move cards to verified, or send a follow-up task if something needs adjustment.
  6. Queue the overnight batch before EOD. Stack tomorrow's tasks on the board. Agents run overnight with self-healing. Check the board at 9am and triage the done column over coffee.

What the board looks like

The amux kanban board has four columns: todo (queued by PM), doing (claimed by an agent), review (agent waiting for PM sign-off), and done. Cards are typed — code, doc, research, investigation — and the gate to advance a card is derived from its type. A code card gates on "implemented and merged" and "tests pass". A research card gates on "findings written up". Type assignment matches reality, so gates stay honest.

The board is shared. PMs add tasks, engineers can add tasks, agents claim and update tasks. Two agents cannot claim the same card — claiming is a CAS (compare-and-swap) atomic operation in SQLite. The board is accessible from any browser, the iOS app, and the REST API.

Visibility without reading code

PMs do not need to read the code to understand what is happening:

  • Session status — each session shows: working / idle / waiting for input / credit-limited. You know immediately if an agent is stuck.
  • Token spend — daily and running totals per session, so you know what each task actually cost.
  • Plan strip — the agent's step-by-step plan visible before it executes. Human-readable, actionable.
  • Terminal peek — scroll through the last 200 lines of the agent's terminal output. Search across all sessions from one box.
  • Board card history — every message, task fold, and gate event is logged on the card. Full audit trail of what the agent did and when.

Parallel fleet: how many agents can work at once?

amux supports dozens of parallel sessions. A typical PM-led sprint might look like:

docs-agentUpdate API docs for the new pagination parametersdoc

All six run in parallel. Each has its own git worktree so code changes do not conflict. The PM queues the board Monday morning and reviews the done column Tuesday morning.

Working with engineering

amux is not a replacement for the engineering team — it is an additional channel. Engineers set up sessions, maintain CLAUDE.md quality gates, and review agent output for architectural decisions. PMs handle task assignment, priority, steering, and acceptance. The division is the same as a human team; what changes is that the "engineers" available for straightforward implementation tasks are available immediately, around the clock, and at zero cost per seat.

For high-stakes or architectural work, engineers stay in the loop. For well-scoped implementation tasks — CRUD endpoints, UI components, test coverage, documentation — agents handle the first pass and engineers review the PR.

What's new — September 2026

Recent releases that directly affect the PM workflow:

Named clearance signals

Board cards can now wait on a named signal — for example, legal-approved or design-signed-off. The agent pauses until you raise the signal from the dashboard. No more "reviewer" dance where an agent finishes and marks done before the PM has seen it.

Deploy-wake (AMUX-5239)

Agents can now suspend after pushing a PR and wake when the deploy lands. The session status shows "waiting for deploy" rather than idle, and the board card advances automatically when the deploy confirms. PMs see the real state without chasing the engineer for a "is it out yet?"

Browser observe-act-verify

Agents now ground their work against a real browser before reporting a task done. They open the page, verify the feature works as specified, and attach a screenshot to the board card. PMs get visual proof, not just a "tests pass" claim.

Idle re-prompt (AMUX-5236)

When an agent says "I'll do X next" and then sits idle, amux re-prompts it automatically. PMs no longer need to nudge sessions that went quiet after announcing a follow-up step.

Pinned notes overlay

The new Pinned tab lets you push sticky notes from any board card to a floating macOS overlay that stays on top of every other window — useful for acceptance criteria you want visible while reviewing agent output, or sprint context that should travel with you across apps.

Getting started

# Engineers set up amux once:
git clone https://github.com/mixpeek/amux && cd amux && ./install.sh
amux register feature-1 --dir ~/Dev/myproject --yolo
amux start feature-1
amux serve  # → https://localhost:8824

Frequently asked questions

How do product managers assign tasks to AI coding agents?

Add a card to the amux kanban board in plain English — title, description, and optional acceptance criteria. A registered AI session claims the card automatically, sets its status to "doing", and begins working. The PM sees the status change in real time on the board or iOS app. No need to write a Jira ticket or wait for sprint planning.

Do I need to be a developer to use amux as a product manager?

No. The amux dashboard and iOS app give PMs a read-and-write interface to the AI agent team without any coding. You add tasks, read agent status, steer with plain-English messages, and review output in the peek pane. Engineers set up the sessions and quality gates once; the PM workflow is entirely GUI and mobile.

How do I steer or correct an agent that is going in the wrong direction?

Open the session peek from the dashboard or iOS app and type a plain-English message in the input box: "Stop — the button should be on the left side, not the right. Also skip the animation." The message is injected directly into the agent's input. The agent incorporates the feedback and continues without restarting.

Can I see the agent's plan before it executes?

Yes. The amux plan strip shows the agent's step-by-step plan in real time inside the peek panel, before it starts executing. If the approach is wrong, send a steering message at the plan stage — much cheaper than after the code is written.

Can product managers and engineers see the same board?

Yes. The amux kanban is a shared board. PMs add tasks, engineers add tasks, AI agents claim and update tasks. All parties see the same state. Two agents cannot claim the same card — the claiming operation is atomic in SQLite. The board is accessible from any browser, the iOS app, and the REST API.

How does amux handle tasks that depend on each other?

Board cards support depends_on and reviewer fields. An agent working on docs-update can depend on feature-1 completing first — the dependency is listed on the card and the session loop respects it. The PM sets the reviewer field on high-stakes cards to gate them on a human sign-off before the agent marks them done.
