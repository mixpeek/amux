Claude Code Account Rotation

Claude Code’s 5-hour usage window kills overnight runs. Account rotation keeps your fleet moving by switching to a fresh verified account when one hits its limit. Published October 2026.

The Rate Limit Problem

Claude Code ships with a generous usage cap, but it is still a cap. Run three or four parallel agents against a heavy codebase for a few hours and you will see this:

Claude Code usage limit reached. Your limit will reset at 3:42 PM.

The process exits. Everything in that session’s queue is now blocked. If this happens at 11 PM on an overnight batch, you wake up to a fleet that has been down for eight hours with nothing to show for it.

There are three ways people deal with this today:

  • Wait it out. The simplest approach, and the most expensive in real time. The 5-hour window resets, you resume. Overnight batches become two-day batches.
  • Switch to API keys. Pay-per-token with no rolling rate cap. Works well, but changes your billing model and requires you to manage API key credentials separately from your Max subscription sessions.
  • Account rotation. Keep a pool of Max accounts. When one hits its ceiling, automatically move sessions to the next available account. The fleet keeps moving. No billing model change, no waking up at 3 AM.

amux shipped account rotation in October 2026. Here is how it works.

How Account Rotation Works

At its core, account rotation is a three-part system:

  1. A credential vault. Each Claude Code account has its own verified OAuth credential stored in amux’s secure vault. The credentials never appear in env vars, config files, or logs.
  2. Window tracking. amux tracks each account’s 5-hour and 7-day usage windows in real time, expressed as percentages with reset times. When an account crosses the rotation threshold (configurable, default: 90%), it is marked as limited.
  3. Automatic session migration. When an account is marked limited, amux migrates all sessions on that account to the next available one. The migration is transparent to the running agent — its conversation context and tool state carry over unchanged.

The result: from the agent’s perspective, the rate limit never happened. From your overnight batch’s perspective, it finished on time.

The 5-Hour and 7-Day Windows

Claude Code Max has two usage windows:

WindowResetsWhat triggers itamux tracking
5-hour rolling 5 hours after first use in the window Token consumption, large context windows, parallel agents Shows % used + exact reset time per account
7-day rolling 7 days after first use in the window Sustained heavy usage across the week Shows % used + days until reset per account

The 5-hour window is the one that bites overnight runs. The 7-day window is the one that bites teams who have been running agents all week. amux tracks both, and the rotation logic considers both before deciding whether an account is available for a new session.

The exact token ceiling for each window is not published by Anthropic, but amux infers it from the rate-limit messages Claude Code emits and adjusts thresholds accordingly.

Setting Up an Account Pool in amux

You need at least two Claude Code Max accounts (each with its own subscription). Here is the setup sequence:

Step 1: Verify each account

Log in to each account via Claude Code’s OAuth flow. amux stores the verified credentials in its vault.

# On each account's machine, or with each account's browser session
$ claude login
Logged in as alice@example.com

Step 2: Register accounts in amux

Add each account to amux’s credential vault. Labels help you track which account is which in the dashboard.

$ amux accounts add alice --label "team-account-1"
$ amux accounts add bob   --label "team-account-2"
$ amux accounts add carol --label "team-account-3"

Step 3: Enable rotation

Add the following to ~/.amux/server.env:

AMUX_ACCOUNT_ROTATION=1
AMUX_ROTATION_POLICY=enabled
AMUX_ROTATION_RESUME_LIMITED=true
AMUX_ROTATION_RESERVE_PERCENT=10

Step 4: Restart amux

The rotation engine starts on the next server launch and immediately begins tracking window usage for every registered account.

Rotation Policy Options

SettingValuesWhat it does
AMUX_ROTATION_POLICY enabled, disabled Master switch. disabled keeps tracking on without any rotation.
AMUX_ROTATION_RESUME_LIMITED true, false When true: sessions that were stalled on a limited account resume on a fresh account as soon as one is available. When false: stalled sessions wait for the original account to reset.
AMUX_ROTATION_ALLOW_UNKNOWN true, false When false (recommended): only accounts registered in the vault can be used. Prevents sessions from silently falling back to an untracked credential.
AMUX_ROTATION_RESERVE_PERCENT 0–50 (integer) Rotate when an account reaches (100 - reserve_percent)% of its window ceiling. Higher values rotate earlier and leave more headroom; lower values squeeze more usage out of each account before rotating.

For most overnight-batch use cases, the defaults above (enabled, resume_limited=true, allow_unknown=false, reserve_percent=10) are the right starting point.

Monitoring Your Account Pool

The amux dashboard shows a real-time account pool view:

  • Per-account usage bars. Each account shows its 5-hour and 7-day windows as progress bars with percentages. Green is safe, yellow is approaching threshold, red is over threshold.
  • Reset times. Each bar shows the exact time the window resets. Before you queue an overnight batch, you can see at a glance whether you have enough headroom or whether rotation will kick in mid-run.
  • Session assignment. The dashboard shows which sessions are currently assigned to which account. After a rotation event, you can see the migration in the session’s activity log.
  • Phone access. The iOS app and the installable PWA show the same pool view. Check headroom from anywhere before starting a long run.

API Keys vs. Account Rotation

Both solve the rate-limit problem. Here is when to use each:

API KeysAccount Rotation
Billing model Pay per token, no cap Flat monthly per account
Best for Bursty workloads, single agents, variable usage Teams with existing Max subscriptions, sustained parallel usage
Complexity Simpler: one credential, set ANTHROPIC_API_KEY More setup: register each account, configure rotation policy
Cost predictability Variable (usage-based) Predictable (N subscriptions, flat monthly)
Rate limits API-tier limits (higher ceilings, different structure) Max plan limits pooled across accounts
Usage visibility Token counts in JSON output Window percentages + reset times per account in dashboard

A common setup for engineering teams: API keys for the primary interactive developer loop, account rotation for the overnight batch fleet. The two approaches are not mutually exclusive.

FAQ

What is the Claude Code 5-hour usage limit?

Claude Code Max plan subscribers have a rolling usage window that resets every 5 hours. When you exhaust the window, Claude Code stops accepting prompts until the window resets. The exact token ceiling is not published, but heavy parallel usage (3+ agents, large contexts) typically hits it within a few hours. There is also a 7-day rolling window for sustained weekly usage.

Is it allowed to use multiple Claude Code accounts?

Each account in the pool must have its own valid Claude Max subscription. Using multiple accounts, each with their own subscription, is standard enterprise and team usage. The key constraint: one subscription = one account. Do not share a single subscription credential across multiple users or sessions.

What happens to a running agent when rotation kicks in?

The agent continues without interruption. amux migrates the underlying credential for that session. The agent’s conversation context, file access, and tool permissions stay intact. From the agent’s side, nothing changed; from the rate-limit window’s side, usage is now accruing against a fresh account.

What is the reserve_percent setting?

It controls when rotation triggers, as a percentage of headroom to keep. reserve_percent=10 means amux rotates when an account reaches 90% of its window ceiling, rather than waiting until it actually hits the limit. This prevents a mid-task stall for a large context job that would exhaust the last 10% partway through. A value of 0 rotates only after the limit is hit, which allows the most usage per account but creates brief stalls at rotation time.

Can I see which account my sessions are using?

Yes. The amux dashboard shows the current account assignment for each session. The session’s activity log records every rotation event, with timestamps and the reason for rotation (5-hour window, 7-day window, or manual override). The iOS app and PWA show the same view from your phone.

What if all accounts in the pool are limited at the same time?

amux queues the affected sessions and resumes them as each account’s window resets, in the order they will become available. The dashboard shows the earliest reset time across the pool, so you can see when the first account comes back. With three or more accounts on staggered schedules, simultaneous limits are rare in practice.

Should I use API keys or account rotation?

API keys (ANTHROPIC_API_KEY) have no rolling rate cap and are simpler to set up: one credential, set the env var, done. Account rotation makes more sense if your team already has multiple Max subscriptions and you want to pool their headroom without changing to per-token billing. For most solo developers, an API key is the easier path. For teams running sustained parallel agents, rotation is more cost-predictable.
