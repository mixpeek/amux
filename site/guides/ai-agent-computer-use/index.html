AI Agent Computer Use with CUA Sandboxes

Rung 3 of the amux browser access ladder — for native dialogs, desktop apps, and anything a headless browser cannot reach. Published September 2026.

The three-rung browser access ladder

Before CUA, AI agents had two options for browser work: headless automation (fast, blocked by many sites) or connecting to a real browser (slower, needs a running Chrome session). CUA adds a third rung — a full sandboxed desktop that handles native apps, OS dialogs, and anything in between.

RungWhat it isBest forCost
1. amux browser Headless Playwright with saved auth profiles Most web tasks: scraping, form submission, UI testing Fastest, cheapest
2. Chrome CDP Connects to your real Chrome with live sign-ins Bot-detection sites, apps that require a real browser fingerprint Medium — needs Chrome running
3. CUA sandbox Full sandboxed desktop environment (github.com/trycua/cua) Native apps, OS dialogs, desktop-only workflows, anything rungs 1–2 cannot reach Heaviest — runs a full VM

amux tries rung 1 first. If it fails or the agent explicitly requests a higher rung, amux escalates. Agents log which rung was used for every browser task.

What CUA enables for AI agents

The CUA sandbox (AMUX-5300, shipped September 2026) gives agents a full desktop to work with. Practical use cases:

  • Native app automation: File tickets in Jira's native client, drag files in Finder, configure Xcode build schemes, run Android Studio emulators.
  • OS-level flows: Grant macOS system permissions via native dialogs, configure system settings that web interfaces cannot reach, respond to OS notification prompts.
  • Desktop-only data: Export from apps with no API (Figma desktop export, local database GUIs, screen recordings from simulator).
  • Login flows that block headless browsers: OAuth flows with CAPTCHA walls, SSO providers that detect non-human browser sessions, enterprise portals with device-based authentication.

Browser profile scoping

CUA agents, like rung-1 agents, can use saved browser profiles — stored credentials that let agents authenticate without entering passwords. AMUX-5307 adds per-worker scope restrictions: an agent for project A cannot read auth profiles saved for project B.

Scope levelWhat it restrictsHow to set
GlobalAll workers can use all profiles (default)Settings → Browser Profiles → Global allow
GroupOnly workers in a named group can use specific profilesSettings → Browser Profiles → Group: frontend-workers → profiles: [prod-google]
Per-workerOnly the named worker can use the profileSettings → Browser Profiles → Session: myworker → profiles: [staging-github]

Chrome CDP profile sync

Saving logins manually into amux browser profiles is tedious. Chrome CDP profile sync (85f32eae, shipped September 2026) reads saved credentials from your real Chrome browser and copies them into amux profiles. Run it once after setting up amux:

# Sync Chrome saved logins into amux browser profiles
node skills/chrome-cdp/scripts/profile-sync.mjs

# amux browser can now use those credentials for rung-1 headless tasks
# CUA agents can use the same profiles under rung-3 (with scoping applied)

Setup: enabling the CUA sandbox

CUA runs as a separate sandboxed process managed by amux. Install amux, then connect the CUA backend:

# 1. Install amux
curl -fsSL https://amux.io/install.sh | bash

# 2. Start the amux server
amux serve

# 3. In amux settings → Integrations → Computer Use, point to your CUA install
#    (see github.com/trycua/cua for CUA setup instructions)

# 4. Test the escalation: trigger a browser task that rung 1 will fail
#    amux will attempt rung 1 → rung 2 → rung 3 automatically

Standing approvals for CUA tasks

CUA agents can do more than a headless browser — which means the approval surface is wider. Configure standing approvals before running unattended CUA tasks:

# Allow CUA agents to navigate the web and read files unattended
export AMUX_ALLOW_BROWSER_NAVIGATION=1
export AMUX_ALLOW_FS_READ=1

# Require owner approval for purchases, account changes, destructive actions
# (these are blocked by default — no configuration needed to stay safe)

The auto-approve layer (AMUX-5301) handles edge cases: if a CUA agent hits an unexpected login prompt at 2 AM, it queues the ask for morning review rather than blocking the whole task.

Monitoring CUA tasks from your phone

Every CUA agent task gets a board card and a live output stream. From the amux iOS app you can:

  • See which rung each agent is currently on
  • Read the agent's live terminal output, including screenshots if the agent captures them
  • Approve or deny escalation requests that the auto-approve policy did not pre-authorize
  • Restart a stuck CUA task with a single tap

Frequently asked questions

What is CUA computer use for AI agents?
CUA (github.com/trycua/cua) is a sandboxed desktop environment that lets AI agents interact with a full computer — clicking native UI elements, navigating OS dialogs, and running desktop apps — beyond what a headless browser can reach. amux integrates CUA as rung 3 of its browser access ladder (AMUX-5300).
When should an AI agent use CUA instead of a headless browser?
Use CUA when: the target site actively blocks headless browsers, the workflow involves native desktop apps (Xcode, Android Studio, Figma, Slack), or the task requires OS-level interactions like file dialogs or system settings. Rung 1 handles most web tasks; rung 3 handles what rung 1 and 2 cannot.
How does the three-rung browser access ladder work in amux?
amux tries rung 1 first (amux browser — headless Playwright with saved auth profiles). If that fails, it escalates to rung 2 (Chrome CDP — connects to your real Chrome). If that also fails, it falls back to rung 3 (CUA — full desktop agent). Agents log which rung was used.
Are browser profiles scoped per agent in amux?
Yes. AMUX-5307 (scoped browser profiles) restricts which agents can access which saved auth profiles. A worker for project A cannot read credentials saved for project B. Scoping is set per-session, per-group, or globally from the amux settings panel.
How do I save my real browser logins into amux profiles?
Chrome CDP profile sync (85f32eae) reads saved logins from your real Chrome and stores them into amux browser profiles. Agents can then authenticate to sites without you entering credentials each time.
Is AI agent computer use safe?
amux standing approvals and auto-approve policies govern what CUA agents can do without asking. You pre-approve safe categories (browsing, file reads) and require confirmation for anything destructive. The CUA sandbox is isolated from the host system beyond what you explicitly authorize.

Run AI agents with full computer access

amux manages the three-rung escalation ladder automatically — headless browser, real Chrome, CUA desktop sandbox. Open source, single Rust binary.
