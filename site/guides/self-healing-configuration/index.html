Recovery Configuration for Unattended AI Agents

How to set up amux so Claude Code agents keep going through usage limits, server restarts and reboots, and so you hear about it when work stalls.

Running AI coding agents while you sleep is simple to describe and harder to do. Agents stop for ordinary reasons: a usage limit, a reboot, a full context window, a prompt nobody answers. This guide shows what amux handles for each, how to configure it, and what it leaves to you.

Crashed agent processes: Restarting a crashed agent process is not built into the amux server today. On macOS, an optional script, scripts/tmux-watchdog.sh, restarts crashed Claude Code workers; it runs as a separate launchd job that the installer does not set up. Nothing does this on Linux or for other providers.

Why unattended agents stop

Each cause needs a different response:

1. Usage limits

When a provider's usage or rate limit hits, every agent on that account stops. Claude Code shows a usage-limit menu and waits, and after the reset nothing moves until someone sends "continue".

2. Server restarts and reboots

The amux server can exit, and the machine can reboot (an overnight OS update is the usual case). Without a service manager, both leave the dashboard down and the workers stopped.

3. Context filling up

A long session fills its context window. Claude Code compacts its own context when it reaches its threshold and continues the task.

4. Tool-approval prompts

By default Claude Code pauses before some tool calls and waits for approval. In an unattended run that pause has no end.

Configuration

Step 1: Install amux

git clone https://github.com/mixpeek/amux
cd amux
./install.sh   # requires tmux 3.2+ and an agent CLI

The installer registers the server as an OS service: the com.amux.server-rs LaunchAgent with KeepAlive on macOS, or the amux-server systemd user service with Restart=always on Linux. On macOS it also adds com.amux.fleet-start, which runs at login and starts every non-archived worker (log: ~/.amux/logs/fleet-boot.log). Set AMUX_NO_FLEET_START=1 when you run the installer to skip that job.

LaunchAgents load at GUI login, so after an unattended reboot the workers come back once someone logs in. Turning on automatic login in System Settings closes that gap, at the cost of the Mac booting to an unlocked desktop.

Step 2: Register workers with YOLO mode

# Tool-approval prompts will block an unattended run
amux register myproject --dir ~/Dev/myproject

# YOLO mode: --yolo is an alias for --dangerously-skip-permissions
amux register myproject --dir ~/Dev/myproject --yolo

# Start the worker and the dashboard
amux start myproject
amux serve  # dashboard at https://localhost:8824

The --yolo flag is per worker, so you can run some workers with it and others without, depending on how much you trust the project's CLAUDE.md constraints. To make it the default, turn on "YOLO by default for new workers" in the dashboard's Settings, Workers tab.

Step 3: Check the usage-limit settings (optional)

Resume after a usage limit is on by default. The settings go in ~/.amux/server.env; AMUX_AUTO_RESUME can also be set per worker, group or globally in the Scope tab.

# ~/.amux/server.env

# Resume an agent at the provider's reset time (default: on; 0 turns it off)
AMUX_AUTO_RESUME=1

# What amux does with Claude Code's usage-limit menu:
# wait (default) picks the wait option, off leaves the menu for you
AMUX_RATE_LIMIT_ACTION=wait

The server reads server.env at startup, so restart it after an edit:

# macOS
launchctl kickstart -k gui/$(id -u)/com.amux.server-rs

# Linux
systemctl --user restart amux-server

Step 4: Set the compaction threshold (optional)

Claude Code compacts its own context. The threshold is Claude Code's autoCompactWindow setting in ~/.claude/settings.json, either top level or per model under modelSettings (the per-model entry wins). A running worker keeps the settings it started with, so restart the worker after a change. amux records the window each launch resolved and logs a warning when a launch resolves a much smaller one than the launch before.

Step 5: Turn on stall alerts

Stall detection surfaces stalled board work and stuck orchestrators, and owner alerts fire. For a worker with a goal, give it a checker: AMUX_GOAL_CHECK is a shell command amux runs in the worker's directory every 10 minutes (exit 0 means met, 1 means not met, and progress such as 44/56 on stdout). When the progress has not moved for AMUX_GOAL_STALL_H hours (default 6, 0 turns it off), the owner gets one push and one email. Set both in the worker's Scope tab.

Step 6 (optional, macOS): restart crashed Claude Code workers

Restarting a crashed agent process is not built into the amux server today. On macOS, an optional script, scripts/tmux-watchdog.sh, restarts crashed Claude Code workers; it runs as a separate launchd job that the installer does not set up. Nothing does this on Linux or for other providers.

Each time it runs, the script checks two things. If the tmux server has died, it starts tmux again and runs amux start-all. If tmux is alive, it looks for Claude Code workers whose pane is left at a bare shell and restarts them with amux start NAME --detach. It skips archived, paused and isolated workers and every non-Claude provider. A worker restarted AMUX_WATCHDOG_RESTART_MAX times (default 3) within AMUX_WATCHDOG_RESTART_WINDOW seconds (default 1800) is held for a human instead of being restarted again. It logs to ~/.amux/logs/tmux-watchdog.log.

To run it, write your own LaunchAgent that calls the script every 30 seconds. Use your clone's path and a PATH that includes tmux:

<!-- ~/Library/LaunchAgents/com.amux.tmux-watchdog.plist -->
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>           <string>com.amux.tmux-watchdog</string>
  <key>ProgramArguments</key>
  <array>
    <string>/Users/you/amux/scripts/tmux-watchdog.sh</string>
  </array>
  <key>EnvironmentVariables</key>
  <dict>
    <key>PATH</key> <string>/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin</string>
  </dict>
  <key>StartInterval</key>   <integer>30</integer>
</dict>
</plist>
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.amux.tmux-watchdog.plist

Step 7: Verify

Confirm the server is up and see each worker's state:

curl -sk https://localhost:8824/health
amux ls

After a reboot, ~/.amux/logs/fleet-boot.log shows which workers the login job started.

Recovery patterns in practice

Pattern 1: Simple overnight run

Queue tasks on the board before bed. Register one worker per major workstream with YOLO on. Start everything. Usage limits resume at reset and stall alerts reach you. In the morning, open the dashboard from your phone:

# Before bed
amux register feature-auth --dir ~/Dev/app --yolo
amux register feature-payments --dir ~/Dev/app --yolo
amux register fix-bugs --dir ~/Dev/app --yolo

# Queue tasks via dashboard or API
curl -sk -X POST -H 'Content-Type: application/json' \
  -d '{"title":"Implement OAuth flow","session":"feature-auth","status":"doing"}' \
  https://localhost:8824/api/board

# Start all sessions
amux start feature-auth
amux start feature-payments
amux start fix-bugs
amux serve

Pattern 2: Monitor agent watching a fleet

For larger fleets, you can register a dedicated monitor worker whose job is to check on other agents. It can read an agent's actual output and decide whether to send a corrective message or re-queue a task that looks stuck, which amux's built-in stall detection does not do:

# Monitor CLAUDE.md prompt
You are a fleet monitor. Every 5 minutes:
1. Peek at all sessions via the amux API
2. If any session's output ends with an error, re-queue its current board task
3. If any session has been idle for 10+ minutes with tasks in doing, send it a "continue" message
4. Log observations to the amux board with session=monitor

Never stop. Never wait for input. Repeat.

Pattern 3: Git safety after a restart

A worker that comes back after a reboot, or after the optional macOS script restarts it, might re-attempt work it had partly finished, including git commits. Protect against duplicate commits by having each agent check for its task ID in the recent commit log before starting work:

# In each agent's CLAUDE.md
Before starting any board task:
1. Read the task ID from the board
2. Run: git log --oneline -20 | grep "TASK-{id}"
3. If found, mark the task done and move to the next one
4. If not found, proceed with the work

Diagnosing recovery problems

Running the server as a persistent service

The installer already does this. On macOS it writes the com.amux.server-rs LaunchAgent with RunAtLoad and KeepAlive, so launchd starts the server at login and restarts it if it exits. On Linux it writes systemd user units from scripts/amux-server.service.template, which sets Restart=always and RestartSec=5:

systemctl --user status amux-server
journalctl --user -u amux-server -f

A systemd user unit stops at logout unless lingering is on for your user (loginctl enable-linger $USER). On Linux nothing starts your workers after a reboot; start them with amux start-all.

What amux does not handle

Being precise about the limits helps you design around them:

  • Crashed agent processes: the server does not restart them. The optional macOS script covers Claude Code workers only.
  • Logic errors: if an agent makes a wrong architectural decision, amux won't notice. Stall detection looks at whether work moves, and says nothing about whether it is correct.
  • Busy on the wrong thing: an agent making steady progress in the wrong direction looks healthy. Use the monitor agent pattern to add semantic checks.
  • Git merge conflicts: if two agents edit the same file and both push, the second will fail. That is a coordination problem. Use the worktree isolation pattern to prevent it.

Recovery and the amux board

The board is where recovery becomes visible. A worker that comes back after a usage limit or a reboot can re-read the board to find its task, still marked doing, and resume. Stall detection flags a card that sits in doing without moving. A monitor agent can move a stuck card back to todo for another worker to pick up.

The board is the single source of truth for what work exists and who owns it. With usage-limit resume, the reboot login job and stall alerts, work left overnight is finished, resumed, or flagged for you in the morning.

Frequently asked questions

What is a self-healing AI coding agent?

The term usually means an agent setup that gets going again after it stops, without a human. In amux that covers specific cases: usage limits hold delivery and resume at the provider's reset, the OS service restarts the amux server, on macOS a login job brings every worker back after a reboot, and stall detection alerts you when work stops moving. Restarting a crashed agent process is not built into the amux server today. On macOS, an optional script, scripts/tmux-watchdog.sh, restarts crashed Claude Code workers; it runs as a separate launchd job that the installer does not set up. Nothing does this on Linux or for other providers.

Why do Claude Code sessions stop overnight?

The common causes are provider usage limits, a machine reboot, a long session filling its context, a tool-approval prompt nobody answers, and occasionally the agent process crashing. Each needs a different response, covered on this page.

How does amux handle usage limits?

amux holds message delivery to the limited agent and resumes it at the provider's reset time, on every platform. Automatic resume is on by default (AMUX_AUTO_RESUME), and AMUX_RATE_LIMIT_ACTION decides whether amux picks the wait option on Claude Code's usage-limit menu (wait, the default) or leaves it for you (off).

What is YOLO mode in amux?

The --yolo flag at amux register is an alias for Claude Code's --dangerously-skip-permissions. Claude Code skips its tool-approval prompts, so an unattended worker never waits on one. With YOLO on there is no prompt for anyone to answer.

How do I set the compaction threshold?

Claude Code compacts its own context. The threshold is Claude Code's autoCompactWindow setting in ~/.claude/settings.json (top level, or per model under modelSettings). A running worker keeps the settings it started with, so restart it after a change. amux logs the window each launch resolved and warns when it shrinks.

Does amux restart an agent that crashes?

Not from the server. Restarting a crashed agent process is not built into the amux server today. On macOS, an optional script, scripts/tmux-watchdog.sh, restarts crashed Claude Code workers; it runs as a separate launchd job that the installer does not set up. Nothing does this on Linux or for other providers. When a crash leaves work stalled, stall detection and owner alerts are how you find out.

Can amux run AI coding agents unattended overnight?

Yes, within the limits on this page. Queue tasks on the board, register workers with --yolo, and start them. Usage limits resume at reset, the server restarts if it dies, a macOS reboot brings the workers back at login, and stall alerts reach you. An agent whose process crashes stays down unless you run the optional macOS script.

Does this work with many parallel agents?

Yes. Usage-limit resume, the reboot login job and stall detection apply to every worker independently, and the amux board keeps agents from picking up the same task.
