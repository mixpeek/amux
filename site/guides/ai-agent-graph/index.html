amux Is a Graph

Board cards are nodes. depends_on and reviewer fields are typed directed edges. Sessions are coordination nodes with send/peek edges between them. Here is the complete topology of a parallel AI agent fleet. July 2026.

When you run 10 or 20 parallel AI coding agents, you are running a distributed system. The hardest coordination problems in distributed systems — ordering, dependencies, sign-off gates, communication topology — are graph problems. amux makes this explicit: every coordination primitive is a typed graph edge, and the board is the adjacency list for your fleet's work.

The two graphs in every amux fleet:
1. Task graph — board cards as nodes, depends_on/reviewer as typed directed edges, status as node state.
2. Session graph — running agent sessions as nodes, send/peek/channels as directed edges.

Graph 1: The task graph

Every board card is a node. The node carries a state (todo → doing → done → verified) and up to two types of outgoing edges:

Edge type Field Semantics Enforced at
Prerequisite depends_on Target cannot START until source reaches done Claim time (atomic, server-side)
Completion gate reviewer Node cannot CLOSE until named reviewer signs off Status transition (done → verified)
Session ownership session Which agent node currently owns this task node Claim time (set atomically)

The graph is a directed acyclic graph (DAG). Circular dependency detection is not enforced at write time — a cycle makes both tasks return 409 indefinitely, which is visible immediately on the board as tasks that never move to doing. Resolve by patching one card's depends_on to remove the cycle.

Building the task graph

# Root node — no prerequisites, claimable immediately
curl -sk -X POST -H 'Content-Type: application/json' \
  -d '{"title":"Write auth module","status":"todo"}' \
  $AMUX_URL/api/board
# → {"id":"TASK-1", ...}

# Dependent node — cannot start until TASK-1 is done
curl -sk -X POST -H 'Content-Type: application/json' \
  -d '{"title":"Write auth tests","depends_on":"TASK-1","status":"todo"}' \
  $AMUX_URL/api/board
# → {"id":"TASK-2", ...}

# Leaf node with reviewer gate — cannot close until human signs off
curl -sk -X POST -H 'Content-Type: application/json' \
  -d '{"title":"Deploy auth to prod","depends_on":"TASK-2","reviewer":"human","status":"todo"}' \
  $AMUX_URL/api/board
# → {"id":"TASK-3", ...}

# The graph: TASK-1 → TASK-2 → TASK-3 (human gate)
# Agents traverse in topological order, automatically

The state machine at each node

Each task node moves through four states. The transition rules are the graph's execution semantics:

State Precondition Who transitions
todo depends_on is done (or absent) Initial state, or set by orchestrator
doing Atomic claim succeeds Agent (via /claim)
done Implementation complete (not yet confirmed) Agent on completion
verified CI green + deployed + reviewer cleared (if set) Human or dedicated verification agent

Graph 2: The session graph

Running agent sessions are nodes in a second graph. Three primitive edge types connect them:

Edge type API call Direction Semantics
Instruction POST /api/sessions/NAME/send Directed (A → B) Deliver a message to a session's next turn
Observation GET /api/sessions/NAME/peek Directed (A reads B) Read another session's terminal output
Channel POST /api/sessions/NAME/send + @mention Bidirectional (A ↔ B) Persistent named 1:1 conversation thread

The session graph is dynamic — edges are created and destroyed as sessions start, communicate, and stop. The task graph is declared — edges are set at card creation time and persist until the work is done. Both graphs coexist in the same SQLite database and are accessible through the same REST API.

The orchestrator pattern: one session builds the graph, many traverse it

# Orchestrator session: build the task graph
# (runs as its own amux session with $AMUX_SESSION = "orchestrator")

# 1. Decompose the sprint into nodes
TASK_A=$(curl -sk -X POST -H 'Content-Type: application/json' \
  -d '{"title":"Parse user requirements","status":"todo"}' \
  $AMUX_URL/api/board | python3 -c "import json,sys; print(json.load(sys.stdin)['id'])")

TASK_B=$(curl -sk -X POST -H 'Content-Type: application/json' \
  -d "{\"title\":\"Implement feature spec\",\"depends_on\":\"$TASK_A\",\"status\":\"todo\"}" \
  $AMUX_URL/api/board | python3 -c "import json,sys; print(json.load(sys.stdin)['id'])")

TASK_C=$(curl -sk -X POST -H 'Content-Type: application/json' \
  -d "{\"title\":\"Write tests\",\"depends_on\":\"$TASK_B\",\"status\":\"todo\"}" \
  $AMUX_URL/api/board | python3 -c "import json,sys; print(json.load(sys.stdin)['id'])")

# 2. Kick worker sessions (session graph edges: orchestrator → worker-1, worker-2...)
amux send worker-1 "Start working — check the board for available tasks"
amux send worker-2 "Start working — check the board for available tasks"

# 3. Worker agents traverse the graph automatically
# worker-1 claims TASK_A (first available root), completes it
# TASK_B unlocks; worker-1 or worker-2 claims it
# TASK_C unlocks after TASK_B; whichever worker is free claims it

How automatic prompt decomposition creates the graph

When a session receives a multi-task prompt, amux now automatically creates one board card per identified unit of work. The decomposition is structural: if a prompt says "implement auth, write tests, and document the API", three nodes are created, not one umbrella card labeled "auth sprint".

The resulting nodes are independent by default — no automatic dependency inference from natural language. If you want edges between them, add depends_on after decomposition. The decomposition gives you the nodes; you give the nodes their edges.

Why one card per task, never one umbrella card: A node with 50 tasks folded in is not a node — it is a log. A gate cannot be applied to it honestly (half the tasks might be done), no agent can claim "this" without ambiguity, and the graph's traversal semantics break down. amux enforces the invariant: a card is something that can be honestly done or not done as a single unit.

Reading the graph via the REST API

# Read the full task graph (all nodes + their edge fields)
curl -sk $AMUX_URL/api/board | python3 -c "
import json, sys
cards = json.load(sys.stdin)
for c in cards:
    deps = c.get('depends_on') or []
    rev  = c.get('reviewer') or '-'
    print(f\"{c['id']:10} {c['status']:8} deps={deps} reviewer={rev}  {c['title'][:50]}\")
"

# Read a single node by ID
curl -sk $AMUX_URL/api/board/TASK-1

# Read the session graph (all live nodes)
curl -sk $AMUX_URL/api/sessions | python3 -c "
import json, sys
[print(s['name'], s.get('status',''), s.get('desc','')) for s in json.load(sys.stdin)]
"

Composing the two graphs: a complete fleet topology

The patterns below describe how the task graph and session graph interact in real fleet deployments:

Fan-out (independent parallel work)

Many root nodes, no edges between them. All tasks are claimable simultaneously. N agents claim N tasks at time zero. Total time = max(task durations), not sum. Best for work that truly does not depend on other work.

Pipeline (sequential stages)

A linear chain: A → B → C. Work flows in one direction. One agent handles each stage, or different agents hand off between stages. Use when each stage produces output that the next stage consumes.

Diamond (merge after parallel work)

Root A → parallel B and C → merge node D (depends_on both B and C). Agents work B and C simultaneously. D unlocks only after both are done. Classic map-reduce pattern for agent work: decompose into parallel tasks, then merge results.

Hub-and-spoke (orchestrator coordinates workers)

One orchestrator session in the session graph; many worker sessions. Orchestrator builds the task graph; workers claim and complete tasks. Orchestrator observes via peek and sends corrections via send edges. This is the most common pattern for large overnight agent fleets.

The graph and the mobile board

The amux iOS app and PWA render the task graph as a kanban. Columns are node states (todo / doing / done / verified). Cards show their depends_on link, session owner, and reviewer. Swipe between columns to scan the graph state from your phone. The graph updates live via SSE — any agent completing a task immediately unlocks downstream nodes and the mobile view reflects it within ~2 seconds.

Complete graph API reference

Operation Endpoint Graph meaning
Add node POST /api/board Create a new task node (with optional edges)
Add/update edge PATCH /api/board/:id Set or change depends_on / reviewer
Traverse node POST /api/board/:id/claim Atomically take ownership of a node (enforces dependency edges)
Advance state PATCH /api/board/:id {status: "done"} Move node forward; unlocks downstream dependents
Read graph GET /api/board Full adjacency list: all nodes and their edge fields
Add session node POST /api/sessions Start a new agent node in the session graph
Send instruction edge POST /api/sessions/NAME/send Create a directed message edge between sessions
Read observation edge GET /api/sessions/NAME/peek Read another session node's output

Frequently asked questions

What does it mean to say amux is a graph?

amux represents a multi-agent fleet as two interlocking graphs. The task graph: board cards are nodes; depends_on and reviewer fields are typed directed edges; the status lifecycle is the node state machine. The session graph: running agent sessions are nodes; send/peek/channel calls are directed edges. Together they give you a complete typed graph of what every agent is doing, what it depends on, who it talks to, and what state it's in.

How does depends_on work at the API level?

Set depends_on to another board card's ID when creating or updating a card. The claim endpoint checks whether the dependency is in done or verified inside the same SQLite transaction that grants the claim. If not, the claim returns HTTP 409. Agents treat 409 identically to a race condition: move to the next available task. Dependency enforcement is zero-cost in agent prompts — no logic needed.

Can amux detect circular dependencies?

amux does not run cycle detection at write time. A circular dependency (A depends_on B, B depends_on A) causes both tasks to return 409 indefinitely — agents skip them and the tasks stay in todo. This is immediately visible on the board as tasks that never move to doing in the presence of idle agents. Fix by patching one card's depends_on to remove the cycle.

What is the reviewer edge and how is it different from depends_on?

depends_on is a prerequisite edge — the task cannot START until the dependency is done. reviewer is a completion edge — the task cannot CLOSE (reach verified) until the named reviewer clears it. Set reviewer to a session name (agent signs off) or human (blocks until a human manually moves the card to verified). They compose: a task can have both.

How does the session graph relate to the task graph?

They are separate graphs that interact through the board. An orchestrator session creates task nodes and dependency edges. Worker sessions traverse the task graph by claiming and completing tasks. A reviewer session closes completion edges on cards with reviewer set to its name. The session graph drives the task graph; the task graph records the outcome.

Does amux have a visual graph view?

The board renders as a kanban (columns: todo / doing / done / verified) rather than a node-link diagram. Each card shows its depends_on link and reviewer. The REST API (GET /api/board) returns the full graph as JSON — all nodes with their edges — so you can render a custom DAG view with any visualization library. The SSE endpoint keeps the data live.

How deep can dependency chains go?

No enforced limit. A chain A → B → C → D → E works correctly. Very deep chains serialize the work the same way a single agent would. For overnight runs, shallow fan-out graphs (roots fan to many leaves, few intermediate nodes) maximize parallelism. Deep sequential chains are appropriate when each stage genuinely requires the previous stage's output.
