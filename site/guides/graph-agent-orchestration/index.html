Graph Agent Orchestration

Graph-based architecture has become the dominant pattern for production AI agent systems. This guide explains what a graph agent is, why graphs beat chains and trees, and how amux implements the full graph as a control plane for AI agent fleets. August 2026.

amux is a graph control plane for AI agent fleets. Workers, board issues, schedules, groups, and shared notes form a live, mutable graph your agents traverse and extend at runtime — open source, zero external dependencies.

The shift to graph-based agent architecture

Enterprise AI adoption did not grow linearly. Between Q1 2024 and Q2 2025, Gartner tracked a 1,445% increase in enterprise inquiries about multi-agent AI systems — the steepest growth signal in enterprise software since cloud adoption. By mid-2025, 72% of enterprise AI projects involved multi-agent architectures, up from 23% the year before.

The pattern that emerged as the production standard across those deployments is graph-based orchestration. LangGraph reached over 32,000 GitHub stars and is in production at Uber, LinkedIn, Replit, and Klarna (85 million users, 80% reduction in resolution time). Salesforce built Agentforce around an explicit Agent Graph. Amazon Strands documents a Graph Multi-Agent Pattern. Microsoft's research arm released GraphRAG in mid-2024 and integrated graph-native memory into its Agent Framework.

The question is no longer whether to use graph architecture for multi-agent AI. It is which layer of the graph your tooling operates at.

What is a graph agent?

A graph agent is an AI agent that operates within a graph-structured coordination system. The term applies at two levels:

Internal graph — the agent's own reasoning steps are arranged as a directed graph rather than a linear chain. LangGraph's StateGraph is the canonical example: nodes are LLM calls or tool invocations, edges are routing rules (direct or conditional), and state flows through the graph with checkpointing between steps. A directed cyclic graph (DCG) allows feedback loops; a DAG does not.

External graph — multiple agents are nodes in a larger coordination graph. Their relationships — which agent owns which task, which agent can talk to which, which schedule triggers which agent, which shared knowledge connects them — are the graph's edges. This is where amux operates.

The two levels compose. You can run LangGraph-based agents (internal graph) inside an amux fleet (external graph). What matters is understanding which layer a given tool addresses.

Why graphs beat chains and trees

Sequential chains — the original pattern for LLM workflows — break on three problems that graphs solve naturally.

Concurrency. A chain runs one step at a time. When two tasks are independent, a chain still serializes them. A graph represents parallel work as two disconnected subgraphs; both execute simultaneously without any special-case logic.

Peer coordination. A tree enforces a strict parent-child hierarchy. The moment two agents need to coordinate as peers — an orchestrator handing off to a reviewer who then updates the task graph — the tree model breaks down. Graph edges are typed and directional; there is no required hierarchy. An agent can be both a worker (receiving tasks) and an orchestrator (creating tasks for others).

Feedback loops. Neither chains nor trees can represent cycles without becoming something else. Iterative refinement — an agent produces output, a reviewer requests changes, the agent revises — is a directed cycle. Graphs model it directly. This is why LangGraph uses a directed cyclic graph rather than a DAG: real agent workflows loop.

The five node types in amux's graph

amux models every coordination primitive as a typed node. Five types form the complete graph:

WORKER

Workers — active compute nodes

A worker is one durable AI agent lane: a tmux session running Claude Code, Codex, Gemini, or any terminal-based agent. Workers are addressable actors — they receive prompts via POST /api/workers/:name/send, expose history via /peek, and persist their identity across restarts. The API still accepts the legacy name session; both spellings are counted and routed identically. Workers are the nodes that traverse and mutate the rest of the graph.

BOARD ISSUE

Board issues — durable work nodes

Every task, bug, and decision is a board issue node. Each node carries a lifecycle state (todo → doing → done → verified) and two types of typed outgoing edges: depends_on (prerequisite — the target cannot start until this node reaches done) and reviewer (completion gate — the node cannot close until the named reviewer signs off). Claiming is atomic: SQLite compare-and-swap ensures no two workers can claim the same node. The board is the coordination memory that prevents duplicate traversal of the same work.

SCHEDULE

Schedules — temporal trigger nodes

A schedule is a time-based trigger edge connecting a moment in time to a worker node. It contains a target worker, a command to inject, and either a one-time timestamp or a cron expression. The schedule does not execute the cognitive work — it injects a message into the worker, which interprets and acts on it. This decouples the timing concern from the execution concern. A schedule can also watch the worker's output for a completion pattern and then disable itself or create a follow-up, producing a small control loop back through the graph.

NOTES & MEMORY

Shared context nodes

Notes and global memory are durable context nodes that survive individual agent context windows. Multiple workers can read and write the same note; board issues can reference notes by slug. This creates a third class of graph relationship — contextual edges — where workers share knowledge without direct communication. A worker can leave behind reusable state (an API contract, a research finding, a decision record) that any later worker can pick up without being told about it explicitly.

GROUP

Groups — topology partitions

A group is a label shared by several workers. Groups partition the session graph into coordination neighborhoods: a worker's peer-discovery, scope visibility, and channel access are scoped to its group. Instead of every worker being equally related to every other, groups create local subgraphs. A project, phase, or team maps to a group. Workers inside a group can coordinate directly; workers outside need explicit routing through the board or the send API.

The edge types amux enforces

WORKER ──claims──▶ BOARD ISSUE (atomic, server-enforced; prevents double-claim) BOARD ISSUE ──depends_on──▶ BOARD ISSUE (prerequisite; blocks claim until source reaches done) BOARD ISSUE ──reviewer──▶ WORKER (completion gate; blocks done→verified transition) WORKER ──sends──▶ WORKER (directed message; POST /api/workers/:name/send) WORKER ──peeks──▶ WORKER (directed observation; GET /api/workers/:name/peek) SCHEDULE ──triggers──▶ WORKER (time-based; injects command at T) SCHEDULE ──watches──▶ WORKER (feedback; pattern-match on output → action) WORKER ──member-of──▶ GROUP (topology; scopes peer discovery and context) WORKER ──reads/writes──▶ NOTE (context; shared durable knowledge)

These edges are not stored in a generalized graph database. Each relationship is represented in the most appropriate store: issue edges in SQLite columns, communication edges as REST calls, schedule edges in schedule rows containing a worker name, context edges in Markdown files on disk. The graph is real; the representation is pragmatic.

How agents traverse and extend the graph

Workers have access to the same REST API the dashboard uses. A running agent can:

  • Read the graph state — GET /api/board returns all task nodes with their edge fields; GET /api/workers lists all active nodes in the session graph.
  • Claim a task node — POST /api/board/:id/claim acquires an atomic ownership edge. Returns 409 if the node is already owned or if a depends_on prerequisite is not yet done.
  • Create new task nodes — POST /api/board with depends_on and reviewer fields adds nodes and typed edges to the graph in a single write.
  • Route work to another worker — POST /api/workers/:name/send creates a directed communication edge, passing a task or message to a peer.
  • Observe another worker — GET /api/workers/:name/peek reads the terminal history of a peer, without interrupting it.
  • Schedule future work — POST /api/schedules adds a trigger node that will fire later, even after the current worker exits.
  • Write shared context — POST /api/notes/:slug leaves knowledge on a context node that outlives the current context window.

The graph is open-ended and dynamic. An orchestrator worker typically builds initial structure; specialist workers traverse and extend it. No agent needs a pre-authored workflow to participate — it reads the graph, claims available nodes, and adds to it as it works.

amux vs LangGraph: different layers of the graph

LangGraph is the most widely deployed graph agent library. Understanding how amux relates to it clarifies where each tool fits.

Dimension LangGraph amux
Layer Inside a single agent turn — controls the agent's internal reasoning graph Across an agent fleet — controls how multiple agents coordinate over time
Graph model StateGraph: directed (cyclic) graph of LLM calls and tool invocations, typed state flowing through nodes Property graph: workers, board issues, schedules, groups, and notes as typed nodes with typed edges
State persistence Checkpointed in-memory or external store, per-run SQLite on disk — survives agent restarts, server restarts, and multi-day runs
Who uses the graph The application code that instantiates and runs the graph The agents themselves, via REST API — they can read and mutate the graph while running
Dependency enforcement Manual in graph edge definitions Automatic at claim time — a worker cannot claim a task whose depends_on is incomplete
Composition Can be used inside an amux-managed worker Can manage LangGraph-based agents as worker nodes
Human-in-the-loop Interrupt/resume hooks inside a single graph run Reviewer edges on board issues; needs:you queue; mobile alerts
Agent providers Any LangChain-compatible LLM Any terminal-based agent: Claude Code, Codex CLI, Gemini CLI, Aider

The right mental model: LangGraph defines what happens inside one agent's turn. amux defines what happens between agents, across turns, over time. Teams building production multi-agent systems often use both.

The architectural insight: coordination state vs execution state

The graph pattern works because amux separates two kinds of state that are usually conflated:

COORDINATION STATE
  • Board issues and their edges
  • Task ownership and lifecycle
  • Group membership
  • Schedule definitions
  • Shared notes and memory
  • Review and dependency gates
EXECUTION STATE
  • Running tmux process
  • Terminal history and output
  • Agent context window
  • Browser session
  • Token consumption
  • Stall status

A board issue can exist without a running worker. A worker can restart without losing the board. A schedule can reactivate a worker days later. A note outlives every worker that wrote it. This is what makes the pattern durable: the graph persists independent of any individual execution.

The academic foundation: Graph of Agents

The graph agent pattern has formal academic backing. The Graph-of-Agents (GoA) framework (Yun et al., arXiv:2604.17148, submitted ICLR 2026) formalizes multi-agent collaboration as a directed graph with node sampling (selecting relevant agents), directed message passing (flowing information from high-relevance to low-relevance nodes), and graph-based pooling (aggregating outputs). The key finding: graph-structured agent selection achieves superior performance using 3 agents versus baselines requiring 6 — the topology enables efficiency gains that flat ensembles cannot.

Separately, the broader taxonomy paper "Graphs Meet AI Agents" (arXiv:2506.18019) maps the space from static knowledge graphs through graph RAG to fully agentic graph systems where agents construct and traverse the graph at runtime. amux sits at the agentic end of that spectrum: the graph structure is not predefined — agents build it as they work.

Frequently asked questions

What is a graph agent?

A graph agent is an AI agent that operates within a graph-structured coordination system. The term applies at two levels: the agent's internal reasoning (LangGraph's StateGraph — nodes are LLM calls, edges are routing rules) and the external coordination between multiple agents (amux — workers, board issues, schedules, and groups form a live property graph). The two levels compose: LangGraph-based agents can be nodes in an amux fleet.

Why are graph-based agent architectures replacing chains and trees?

Chains are sequential — they cannot represent concurrent work without becoming a graph. Trees impose a strict hierarchy that breaks when two agents need to coordinate as peers. Neither can represent feedback loops. Graph structures handle concurrency, peer coordination, and feedback loops natively. The production evidence confirms the shift: LangGraph (directed graph model) is in production at Uber, LinkedIn, Replit, and Klarna; Salesforce Agentforce runs on an explicit Agent Graph; Amazon Strands documents a Graph Multi-Agent Pattern.

What is the difference between amux and LangGraph?

LangGraph is a Python library you embed in your application code to define an individual agent's reasoning as a directed graph of LLM calls and tool invocations. amux is a control plane you run alongside your agents to coordinate a fleet of them. LangGraph controls what happens inside one agent turn; amux controls what happens across many agents running in parallel over days or weeks. You can run LangGraph-based agents inside an amux fleet — the two operate at different levels.

How does amux prevent two agents from claiming the same task?

Claiming a board issue is a compare-and-swap operation enforced by SQLite. The server atomically checks that the issue's status is still todo and no other worker has claimed it. If both hold, status transitions to doing and the claiming worker's identity is recorded. A second worker calling claim at the same time receives 409. This is equivalent to acquiring a distributed lock on a graph node.

Can agents modify the graph at runtime?

Yes. Workers access the same REST API the dashboard uses. An agent can create board issues (adding nodes), set depends_on relationships (adding edges), send tasks to other workers (traversing communication edges), create schedules (adding trigger nodes), and write shared notes (updating context nodes). The graph is mutable and open-ended — not a static workflow defined before execution begins.

Is there academic evidence that graph agents outperform other architectures?

The Graph-of-Agents (GoA) paper (Yun et al., arXiv:2604.17148) shows graph-structured multi-agent collaboration achieves superior performance using 3 agents versus baselines requiring 6. The graph topology enables efficiency gains that flat ensembles cannot: relevant agents are selected by node sampling, information flows directionally rather than broadcasting, and outputs are aggregated by graph-based pooling rather than naive voting.

What is the difference between GraphRAG and an agentic graph?

GraphRAG (Microsoft Research, 2024) uses an LLM to induce a graph structure over a document corpus, then retrieves across that graph during queries — it is a retrieval method, not an agent orchestration method. An agentic graph (the pattern amux implements) is a live system where agents are the nodes and their coordination relationships are the edges. GraphRAG improves what an agent knows; an agentic graph coordinates what multiple agents do.
