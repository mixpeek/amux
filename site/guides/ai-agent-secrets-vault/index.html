AI Agent Secrets Management: Securely Pass API Keys to Coding Agents

Updated October 2026

AI coding agents need secrets to do real work — Stripe keys, database URLs, API tokens. But agents also read files, write code, and produce conversation logs, which creates exposure risks that don't exist with human developers. The right approach: inject secrets as environment variables at agent launch, scoped to the agents that need them, encrypted at rest. Never in prompts. Never in files the agent can read or commit.

Quick answer: Use amux vault to store secrets encrypted and inject them per-session: amux vault set STRIPE_SECRET=sk_live_... --scope worker:billing-agent. The agent sees the variable in its environment; the value is never written to disk in your project.

Why Agents Are Different from Human Developers

A human developer with a .env file knows not to log secrets, commit them to git, or paste them into chat. AI coding agents don't have that intuition — they treat files in the working directory as readable context, they may reference environment variables in code comments, and their conversation logs are persistent records that could include anything that appeared in context.

This creates three risks that don't exist with human developers:

  • File read: If your .env is in the project directory, the agent may read it as context when exploring the codebase. The value could appear in summaries, in code it writes ("// using key from .env"), or in error messages it logs.
  • Conversation capture: Secrets passed in a system prompt or CLAUDE.md appear in the model's context window for the entire session. The agent may reproduce them in output, tests, or documentation.
  • Fleet blast radius: In a fleet of 10+ agents, a globally available secret means 10+ agents each have access to it. If one agent behaves unexpectedly or is manipulated by injected content, all your secrets are in scope.

Four Approaches, Ranked by Safety

1. Vault injection at launch (most secure)

Secrets are stored encrypted in a dedicated store. At agent session launch, the orchestrator injects matching secrets as environment variables into that process's environment. The agent can USE the variables (read their values in code) but: the values are never written to any file in the project, they don't appear in conversation logs, and they're scoped to specific agents. This is what amux vault does.

2. External secrets manager (secure, more complex)

Use AWS Secrets Manager, HashiCorp Vault, or 1Password CLI to fetch secrets at runtime. The agent calls the secrets manager CLI to retrieve a value when it needs it. More complex to set up but integrates with existing enterprise infrastructure. The agent still needs credentials to access the secrets manager itself.

3. Environment variables in shell (moderate)

Export secrets as environment variables in the shell that launches the agent. export STRIPE_KEY=sk_live_... && claude. The value is in the process environment but not in any file. Risk: the value appears in shell history, the environment is visible to any process the agent spawns, and in a fleet you need to manage injection per-session manually.

4. .env files (least secure)

Storing secrets in a .env file in the project directory is the riskiest approach with AI agents. The agent can read the file as part of exploring the codebase. Even with .gitignore, the file is in the working directory and may appear in the agent's context. Acceptable for local development with a single agent and throwaway credentials; not acceptable for production keys or multi-agent fleets.

amux Vault: Scoped Encrypted Secrets

amux ships a built-in vault for AI agent secrets. Secrets are stored encrypted in the amux SQLite database (not in your project directory). At session launch, amux injects matching secrets as environment variables into the agent's process environment based on scope rules.

# Store a secret (encrypted at rest)
amux vault set STRIPE_SECRET=sk_live_abc123 --scope global
amux vault set DB_URL=postgres://prod/main --scope group:backend
amux vault set TWILIO_AUTH=AC... --scope worker:notification-agent

# List secrets (shows names, not values)
amux vault list

# The agent uses it as a normal env var
os.environ['STRIPE_SECRET']  # works in agent code

The three scopes map to your fleet topology:

  • global — injected into every agent session. For secrets every agent needs (your own service's auth token, a shared read-only credential).
  • group:name — injected only into sessions belonging to a named group. For secrets relevant to a team or project (all backend agents share a DB URL; frontend agents don't get it).
  • worker:name — injected only into a specific named session. For highly sensitive credentials that one agent needs (payment processing key scoped to the billing worker).

The vault is managed from the amux dashboard or CLI. Updates take effect on the next session launch without requiring any restart of the amux server.

Secret Scoping: Least Privilege for Agent Fleets

In a fleet of 10+ parallel agents, blanket secret availability is a risk multiplier. Apply least-privilege the same way you would for human team members:

  • Infrastructure credentials (cloud provider API keys) belong to the worker that deploys, not the workers that write tests.
  • Customer data access credentials belong to the specific agent doing data migrations, not the whole fleet.
  • Payment credentials (Stripe, Braintree) belong to the billing worker. The docs agent doesn't need them.
  • External communication credentials (Twilio, SendGrid) belong to notification workers. Code-review agents don't need them.

Step-by-Step Setup with amux Vault

  1. Install amux if you haven't already: 
    curl -fsSL https://amux.io/install.sh | bash
curl -fsSL https://amux.io/install.sh | sh
  2. Audit your current secrets exposure — check for .env files in working directories, secrets in CLAUDE.md or system prompts, and any hardcoded values in config files your agents can read.
  3. Move secrets into the vault: 
    amux vault set ANTHROPIC_API_KEY=sk-ant-... --scope global
amux vault set DATABASE_URL=postgres://... --scope group:backend
amux vault set STRIPE_SECRET_KEY=sk_live_... --scope worker:billing
  4. Remove the secrets from agent-readable locations. Delete or empty .env files in project directories. Remove any keys from CLAUDE.md or hook scripts. Add .env to your agent's ignore list.
  5. Start an agent session — amux injects the matching scoped secrets automatically: 
    amux start billing-agent  # gets global + group:backend + worker:billing
amux start docs-agent     # gets global only
  6. Verify without exposing values — ask the agent to call an API using the environment variable and confirm it works. Never ask it to print or log the value.

FAQ

How do I securely pass API keys to an AI coding agent?

The safest approach: inject secrets at agent launch time as environment variables scoped to that specific session, rather than hardcoding them in config files or passing them in prompts. Tools like the amux vault encrypt secrets at rest and deliver them only when a matching agent session starts. The agent sees the variable in its environment but the value is never written to any file the agent can read or commit. Avoid: .env files checked into git, secrets in CLAUDE.md or system prompts, and manually pasting keys into agent conversations.

Can an AI coding agent leak my secrets?

Yes, in several ways. If a secret is in a file the agent can read (like .env or a config file), the agent may include it in code it writes, log it to conversation history, or reference it in comments. If passed in a system prompt or CLAUDE.md, it appears in the model's context window and may be reproduced in output. The safest delivery mechanism is environment variable injection at process launch — the agent can USE the variable but cannot easily introspect where it came from or what other secrets exist.

Should I use .env files with AI coding agents?

Plain .env files are risky with AI coding agents. Unlike a human developer, an AI agent actively reads files in the working directory, writes code that may reference those files, and produces conversation logs that could capture their contents. If your .env is in the agent's working directory, treat it as potentially readable by the agent. Better options: inject secrets as environment variables at launch (not read from files), use a dedicated secrets manager, or use amux vault which encrypts secrets and injects them only at session start without ever writing them to disk in the project.

What is secret scoping for AI agents?

Secret scoping means assigning credentials to specific agents or groups of agents rather than making them globally available. In a fleet of 10 agents, your Stripe secret key should only be injected into agents working on payment features. amux vault supports three scopes: global (all sessions), group (a named set of workers), and worker (a single named session). This limits blast radius if an agent behaves unexpectedly.

How does the amux vault differ from a .env file?

Three key differences: (1) amux vault secrets are encrypted at rest in the amux database, not stored as plain text in your project directory; (2) they're scoped — you control which agents get which secrets; (3) they're injected at session launch as process environment variables, not loaded from a file the agent can read. A .env file in your project is a file your agent can discover and read as part of exploring the codebase.
