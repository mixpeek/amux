Clone or Fork an AI Agent Session

Duplicate a live worker to run parallel experiments, split a task in two, or test different implementation paths — without re-queuing from scratch.

Last updated: August 26, 2026

Quick answer: Use POST /api/sessions/<name>/clone or the dashboard's "Duplicate" button to fork any live amux session. The twin is registered immediately, inherits the source project's config, and can receive messages right away. Send each twin a different task and both run in parallel — no additional setup required.

What session cloning is for

A running amux session holds a live agent (Claude Code, Codex CLI, or Gemini CLI) inside a tmux pane with its project context loaded. Cloning duplicates that registration — the twin gets its own tmux session, its own board card, and its own send queue, all sharing the same base project and working directory as the original.

The primary use cases are:

  • Prompt A/B testing. Send one prompt variant to the original and a different variant to the clone. Both run in parallel and you compare the outputs side-by-side in the dashboard or iOS app. This gives you both results in the time of one run.
  • Task splitting. A long-running task can be split between two agents mid-flight. Clone the session, send the first half of the remaining work to the original and the second half to the twin. Both finish faster, and you merge the results.
  • Implementation path exploration. When two architectural approaches both seem viable, run them simultaneously instead of sequentially. Both agents explore their path without knowledge of the other; you pick the better result.
  • Regression guard. Clone a known-good session before changing its CLAUDE.md or system prompt. Run the same test task on both — the clone preserves the original behavior as a reference while you test the new config.

How to clone a session

Via the dashboard

Open the session card in the amux web dashboard. Click the Duplicate button (or the three-dot menu → "Clone session"). The twin appears in the fleet list immediately, named with a -copy suffix unless you specify a name. The twin starts idle — send it a message to begin work.

Via the REST API

# Clone a session by name
curl -sk -X POST $AMUX_URL/api/sessions/my-worker/clone

# Clone and specify a name for the twin
curl -sk -X POST -H 'Content-Type: application/json' \
  -d '{"name":"my-worker-v2"}' \
  $AMUX_URL/api/sessions/my-worker/clone

# The response includes the twin's name and ID:
# {"name":"my-worker-v2","session_id":"...","status":"idle"}

Send different tasks to each twin

# Send approach A to the original
amux send my-worker "Implement this using the repository pattern"

# Send approach B to the clone
amux send my-worker-v2 "Implement this using the service layer pattern"

# Watch both in parallel
amux peek my-worker
amux peek my-worker-v2

Step-by-step: running a prompt experiment

  1. Pick a session that is idle or at a task boundary. The clone works best when the source agent is between tasks — after completing one board card, before starting the next. This gives you a clean fork point with no in-flight state to reconcile.
  2. Clone via the dashboard or API. The twin registers instantly and appears in the fleet view alongside the original.
  3. Send different messages to each. Use amux send <name> or POST /api/sessions/<name>/send for each twin. Both agents are now working independently in parallel.
  4. Monitor both in the dashboard or iOS app. The web dashboard streams live terminal output from every session simultaneously. On the iOS app, swipe between session cards to compare progress.
  5. Pick the result and retire the other. When one approach succeeds, mark its board card done. Stop and deregister the unused twin: 
    amux stop my-worker-v2
amux deregister my-worker-v2

Common patterns

Use case What you send to original What you send to clone
Prompt comparison Concise, direct instruction Same task with a detailed chain-of-thought prompt
Model comparison Same task (original uses Claude Code) Same task (clone uses Codex CLI or Gemini CLI)
Architecture A/B "Use the repository pattern" "Use the service layer pattern"
Task split Files A–F of a refactor Files G–L of the same refactor
Config change test Existing CLAUDE.md unchanged Updated CLAUDE.md — run the same test task on both

How cloning relates to the fleet model

amux's fleet model is built around a shared kanban board: agents atomically claim tasks so no two sessions ever duplicate work. Session cloning fits into this model — each twin can claim its own task from the board, or you can route tasks to specific workers by name via POST /api/sessions/<name>/send. The two are complementary: use the board for routine fleet-scale batch work, use explicit send for directed experimentation.

When you clone a session that has an active board card, the original keeps the card. The clone starts without a claimed task — you can assign it one manually or let it pick up the next available todo item on the board.

Frequently Asked Questions

Can I fork a Claude Code session mid-task?
Yes. The clone is registered at any point — the source session keeps running unaffected. The twin starts idle and receives its first message when you send one. If the original is mid-task, the clone starts fresh within the same project rather than mid-conversation: it is a project fork, not a conversation continuation.
What does the clone inherit from the original?
Project registration (working directory, session config, group membership, board association). It starts a fresh tmux session rather than inheriting the in-flight terminal state. This gives you a clean agent running against the same codebase — ideal for parallel experimentation.
How is session cloning different from just starting a second worker?
Starting a second worker requires re-running amux register and configuring the project manually. Cloning takes one API call: the twin inherits the full project config, gets a coherent name, appears on the board and in the fleet view, and is ready for messages immediately. It is the difference between a few seconds and a few commands.
Can I use session cloning to A/B test prompts?
Yes — this is the primary use case. Clone the session, send prompt variant A to the original and variant B to the clone, watch both in the dashboard, and compare outputs. Parallel execution gives you both results in the time it would take to run one sequentially.
Does cloning work with Codex CLI and Gemini CLI sessions?
Yes. amux manages Claude Code, Codex CLI, and Gemini CLI sessions through the same interface. The clone feature works for any session regardless of which underlying runtime it uses. You can clone a Claude Code session and start the twin with Codex CLI to compare runtimes on the same task.
How many clones can I run in parallel?
No hard limit from amux. Practical limits are your machine's CPU/RAM and your API rate limits. Running 3–5 clones in parallel for prompt experiments is routine; 10–50 parallel sessions for overnight batch work is the intended fleet-scale use case. The self-healing watchdog monitors all of them.
