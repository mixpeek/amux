AI Agent Deploy Notifications — Wake Your Coding Agents When Their Code Ships (2026)

AI coding agents write and commit code, then go idle. They have no way of knowing whether their work deployed successfully, whether it broke anything, or whether the next task in the queue should start. amux’s deploy-wake feature (AMUX-5239, September 2026) automatically resumes the worker sessions that authored each deployed commit, giving agents immediate awareness of their own deployments. Updated September 2026.

Quick answer: amux watches its own build health endpoint (GET /api/health). When the running commit hash advances (a new build went live), amux identifies which worker sessions authored commits in that range using the Amux-Session git trailer, and sends a wake message to each one. The agent resumes with deploy context and can run smoke tests, update board cards, or start the next task — automatically, with no webhook configuration or CI changes required.

The gap: agents ship code and go dark

Every AI coding workflow today has the same blind spot: agents write and commit code, but they have no awareness of what happens to that code after the commit. They don’t know when the CI pipeline finishes. They don’t know when the build goes live. They certainly don’t know whether a smoke test passed or the deploy rolled back.

The consequence is a manual loop that puts humans back in the middle of what was supposed to be an autonomous workflow:

  1. Agent commits code, goes idle
  2. CI pipeline runs (invisible to the agent)
  3. Deploy completes or fails (invisible to the agent)
  4. Human notices the deploy status
  5. Human manually tells the agent what happened
  6. Agent responds and either continues or investigates the failure

Steps 4 and 5 are the bottleneck. On a team running a dozen parallel agents overnight, this is a dozen manual follow-ups every morning before the agents can proceed. The agents did the work, but a human has to be the messenger between the deploy system and the agent fleet.

Deploy-wake removes this bottleneck entirely for the local auto-builder case and integrates with external CI via the API.

How deploy-wake works

The mechanism is three parts working together:

Component What it does How to configure
Build watcher Polls GET /api/health and compares the running commit hash. When it advances, triggers a wake pass for the new range. Automatic; built into the amux server. No configuration needed for the local auto-builder.
Session attribution Reads the Amux-Session: <name> trailer that amux appends to every commit made inside a session. Maps commits in the deployed range back to their authoring sessions. Automatic; every amux session appends the trailer via the git commit hook. No manual tagging needed.
Wake delivery Sends a configurable message to each attributed session via POST /api/sessions/<name>/send. The message arrives at the agent’s next turn boundary. If the session is paused or stopped, the message is queued for when it resumes. Default message: “Your commits from [range] went live. Build is healthy. Verify your changes if needed.” Customisable via AMUX_DEPLOY_WAKE_MSG in server.env.

The key design decision: wake delivery uses the same send mechanism as any other message to a session. There is no special wake protocol, no polling loop the agent has to run, and no webhook endpoint the CI system has to call. The agent just gets a message at its next turn and can act on it like any other prompt.

Setting up deploy notifications in 5 steps

  1. Install amux and start the server. 
    curl -fsSL https://amux.io/install.sh | bash
amux serve   # starts at https://localhost:8824
    The auto-builder watches for new commits and deploys them automatically. The deploy-wake feature activates with it.
  2. Start workers with stable names. 
    amux start --name backend
amux start --name frontend
    Named sessions persist across restarts and are how the attribution system finds the right session to wake.
  3. Commit from inside a session. Every commit made inside an amux session gets an Amux-Session: <name> trailer automatically. You can verify this with: 
    git log --format="%H %s%n%b" -1
    The last line of the commit message will include the session trailer.
  4. Watch the first wake event. After your next commit builds and goes live, check the session’s message history: 
    amux send backend --stdin <<'EOF'
What is the most recent message you received about a deploy?
EOF
    Or check the amux dashboard’s Messages tab for the session.
  5. Add a verification step to CLAUDE.md. 
    # In ~/.amux/sessions/backend/CLAUDE.md (or your project CLAUDE.md)
# Standing instruction:
When you receive a deploy notification, run `make smoke-test` and
post the result to your active board card. If the test fails, move
the card back to doing and investigate.
    The agent now self-verifies every time its work ships.

Building a self-verifying deploy workflow

The deploy-wake feature becomes most powerful when combined with standing instructions and the amux board. Here is a typical overnight workflow that requires zero human intervention between “agent commits code” and “deploy verified”:

  1. Agent works overnight. It writes code, runs local tests, and commits. The commit gets the Amux-Session trailer.
  2. Auto-builder picks it up. The amux builder detects the commit and rebuilds the server binary (for amux itself) or triggers whatever build hook is configured for your project.
  3. Build goes live. The server starts serving the new binary. GET /api/health reflects the new commit hash.
  4. Deploy-wake fires. amux identifies the session that authored the commits in the range and sends the wake message.
  5. Agent verifies. Per its CLAUDE.md standing instruction, it runs the smoke test, captures the result, and posts to the board.
  6. You wake up to a verified deploy. The board card shows: committed, built, deployed, smoke test green. Or, if something is wrong, the agent has already filed a new card with the failure details and started investigating.

This loop works for any project where amux manages both the commit side (agent sessions) and the build/serve side (amux server or the project’s own auto-builder). For external CI pipelines, see the next section.

Integrating with external CI/CD

For projects that deploy via GitHub Actions, CircleCI, or another external pipeline, the deploy-wake system can be triggered directly from the pipeline’s “deploy successful” step:

# In your GitHub Actions workflow (deploy.yml)
- name: Wake amux sessions after deploy
  if: success()
  run: |
    # Replace <session> with the name of the worker session to wake
    curl -sk -X POST \
      -H 'Content-Type: application/json' \
      -H "X-Amux-Session: ci-pipeline" \
      -d '{"text":"Deploy complete. Commit ${{ github.sha }} is live in prod. Run smoke tests and verify."}' \
      https://your-amux-server/api/sessions/backend/send

For the full GitHub Actions recipe including how to expose your amux server securely, see the AI agents in GitHub Actions guide.

If you want to wake multiple sessions based on which files changed in the deploy, the amux API supports this via commit range attribution:

curl -sk "$AMUX_URL/api/sessions?commit_range=$BASE_SHA..$HEAD_SHA" | \
  python3 -c "import json,sys; [print(s['name']) for s in json.load(sys.stdin)]"

This returns the sessions that authored commits in the range, which you can then loop over to send targeted wake messages.

Frequently asked questions

How do AI agents know when their code has been deployed?

Most AI coding agents never find out. They write code, commit it, and then go idle. The deployment loop is invisible to them unless a human loops them back in manually. amux’s deploy-wake feature (AMUX-5239, September 2026) closes this gap: the server watches the running build’s commit hash and sends a wake message to every session that authored commits in the newly deployed range. The agent resumes with deploy context and can verify immediately, without waiting for anyone to tell it what happened.

Does amux integrate with GitHub Actions or CI/CD pipelines for deploy notifications?

Yes, in two ways. The local deploy-wake system works automatically with amux’s own auto-builder: no configuration required. For external CI systems, you can call POST /api/sessions/<name>/send from a deploy-success step in your workflow to deliver a targeted wake message. See the AI agents in GitHub Actions guide for the full recipe including authentication and securing the endpoint.

Can an AI agent run smoke tests automatically after a deploy?

Yes. Add a standing instruction to the session’s CLAUDE.md: “After receiving a deploy notification, run [your smoke test command] and post the result to your active board card.” When amux wakes the agent, the agent reads this instruction and executes the test as part of its next turn. The board card captures the test result, so you have a complete record of what shipped and whether it passed verification, without any manual follow-up.

What happens if the agent is stopped when a deploy notification arrives?

The message is queued and delivered when the session resumes. amux’s send queue (AMUX-5237, September 2026) holds messages for paused or stopped sessions and delivers them at the next turn boundary after the session restarts. This means overnight deploys that complete after the agent has been stopped for the night are still picked up first thing in the morning when the session resumes.

Which AI coding runtimes support deploy notifications?

Deploy notifications work with any runtime amux manages: Claude Code, OpenAI Codex, and Gemini CLI. The wake mechanism operates at the amux session layer and sends a message via the same path as any other prompt. The runtime does not need any special configuration. The agent reads the deploy message as its next prompt and responds accordingly.

Do I need to configure anything for deploy notifications to work?

No configuration is required for the local deploy-wake feature. amux tracks session authorship via the Amux-Session git trailer that is automatically appended to every commit made inside an amux session. The server watches its own build hash and delivers wakes automatically when it advances. If you want agents to take a specific action on wake (run smoke tests, update a card), add that instruction to the session’s CLAUDE.md or the project’s shared CLAUDE.md.
