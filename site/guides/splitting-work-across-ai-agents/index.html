How to Split a Software Project Across Multiple AI Coding Agents

Finish in parallel what one agent would take all week.

A team of AI coding agents completes a sprint's worth of features in hours instead of days — but only if the work is split correctly. Split it wrong and agents block each other, duplicate effort, or create git conflicts that cost more time than parallelism saves. This guide covers how to decompose a project into parallel workstreams, model dependencies, prevent duplicate work, and coordinate from a single dashboard or your phone.

amux is an open-source control plane for running an AI engineering team from a single dashboard or your phone. It handles session management, a shared kanban board with atomic task claiming, a dependency graph, and self-healing — for any runtime: Claude Code, Codex CLI, or Gemini CLI.

Last updated: August 2026

The core principle: one agent, one branch, one task

The simplest rule that prevents most parallel coordination problems:

  • One agent owns one feature branch. No two agents write to the same branch simultaneously.
  • One agent claims one board card. Cards are claimed atomically — once an agent takes a card, no other agent can pick it up.
  • Shared files are sequenced, not parallelized. If two features both need a new database table, one agent writes the schema migration first, and the other's card is marked blocked-on until the migration card completes.

This structure lets amux coordinate dozens of agents without a central lock broker. The board is the coordination layer, and SQLite's compare-and-swap is the lock.

How to decompose a project for parallel agents

Step 1: Identify independent work units

Good split points are boundaries where two agents could work for hours without touching the same files. Common ones:

Split strategy When to use it Example
Feature boundary Each feature touches its own files Auth, search, payments, notifications
Layer boundary API and UI evolve against a shared interface One agent writes the REST API, another builds the React UI against a fixed schema
Service boundary Microservices or packages with stable interfaces Agent A owns the billing service, Agent B owns the notification service
File-ownership boundary Large refactors on distinct file sets Agent A migrates files in src/api/, Agent B migrates files in src/ui/
Test boundary One agent writes code, another writes tests Agent A ships the feature, Agent B writes the test suite

Avoid splitting at boundaries that require constant cross-agent coordination. If Agent A needs to wait for Agent B's output every 10 minutes, those are not independent — they should be sequenced, not parallelized.

Step 2: Map dependencies

List which tasks must complete before others can start. Draw this as a directed graph:

schema-migration → auth → payments
                 → search → search-ui
readme-update (no dependencies — runs anytime)

Any task with zero incoming edges can start immediately. Tasks with incoming edges wait for their prerequisites.

Step 3: Register sessions and post board cards

Each task unit gets one amux session and one board card. Register the sessions first:

amux register schema-migration --dir ~/Dev/app --yolo
amux register auth             --dir ~/Dev/app --yolo
amux register payments         --dir ~/Dev/app --yolo
amux register search           --dir ~/Dev/app --yolo
amux register search-ui        --dir ~/Dev/app --yolo
amux register readme           --dir ~/Dev/app --yolo

Then post cards to the board:

SCHEMA=$(amux board add "Write DB migration for auth + search tables" | grep -o 'AH-[0-9]*')
AUTH=$(amux board add "Implement JWT auth endpoints" | grep -o 'AH-[0-9]*')
PAY=$(amux board add "Stripe checkout flow" | grep -o 'AH-[0-9]*')
SRCH=$(amux board add "Full-text search API" | grep -o 'AH-[0-9]*')
SRCHUI=$(amux board add "Search UI components" | grep -o 'AH-[0-9]*')
amux board add "Update README and docs"

Step 4: Set dependencies on the board

Mark blocked-on relationships so agents pull work in the right order:

# auth must wait for schema-migration to complete
curl -sk -X PATCH -H 'Content-Type: application/json' \
  -d "{\"blocked_on\":\"$SCHEMA\"}" \
  $AMUX_URL/api/board/$AUTH

# payments must wait for auth
curl -sk -X PATCH -H 'Content-Type: application/json' \
  -d "{\"blocked_on\":\"$AUTH\"}" \
  $AMUX_URL/api/board/$PAY

# search API must wait for schema-migration
curl -sk -X PATCH -H 'Content-Type: application/json' \
  -d "{\"blocked_on\":\"$SCHEMA\"}" \
  $AMUX_URL/api/board/$SRCH

# search-ui must wait for search API
curl -sk -X PATCH -H 'Content-Type: application/json' \
  -d "{\"blocked_on\":\"$SRCH\"}" \
  $AMUX_URL/api/board/$SRCHUI

Now GET /api/board/ready returns only tasks with no incomplete dependencies. Agents that poll this endpoint will never start work out of order.

Step 5: Launch all agents and monitor

amux start-all

All sessions start simultaneously. Each agent reads the ready queue, claims the first available card atomically, and begins working. Agents with no ready tasks wait — they do not spin on empty loops; they check the board at each new message boundary.

Open the dashboard at https://localhost:8824 or the iOS app. You see:

  • Which agent is working which card
  • Which cards are blocked (and on what)
  • Which sessions are idle, running, or have crashed
  • Time-in-state for each card — so you know if a task is running unusually long

Handling shared files safely

Some tasks inherently touch the same files. The safest approach:

  1. Sequence them. The first agent completes the shared file, the second starts only after the first card is done.
  2. Use the continuation contract. If the first agent crashes mid-write, the card stores what it was doing at the time of interruption. When the session restarts (auto, via the self-healing watchdog), it reads the continuation and resumes. The second agent's blocked-on dependency means it does not start until the first fully completes.
  3. Never use git add -A in a shared directory. amux's shared-checkout guard blocks it. Stage specific files by name.

What the continuation contract does

One of the hardest parts of multi-agent coordination is handling an agent that dies mid-task. Without a continuation mechanism, the next agent to pick up the card has to figure out what was done and what was not — expensive and error-prone.

amux's continuation contract lets a claimed card record exactly what the working agent was doing: which files it had edited, what the next step was, and any context a fresh agent needs to resume cleanly. When the card is eventually handed off (due to a crash, context exhaustion, or an explicit reassignment), the new agent reads the continuation and picks up at the same point.

This makes the fleet robust to single-agent failures without requiring human intervention. The owner of the board card does not need to be the same session throughout the task's lifetime.

Reading the board ready queue from an agent

If you want agents to self-schedule — reading from the board and claiming tasks rather than being told what to do — point them at the ready endpoint:

# Returns only tasks with all dependencies complete and status = todo
curl -sk $AMUX_URL/api/board/ready | python3 -c "
import json, sys
tasks = json.load(sys.stdin)
for t in tasks[:3]:
    print(t['id'], t['title'])
"

An agent can claim the first result and start working. If two agents race to claim the same card, only one succeeds — the other gets a 409 and retries with the next available task.

How many agents can run in parallel?

Machine Practical parallel agents Notes
8 GB MacBook 4-6 Leave headroom for the OS and IDE
16 GB MacBook / Linux box 8-12 Comfortable for a full sprint
32 GB desktop / cloud VM 20-40 amux watches memory headroom and refuses new sessions before OOM
64 GB+ server 50+ Production fleet size; monitor per-agent API call rate to stay under provider limits

amux monitors available memory before each new session start. If the host is low on RAM, new session creation is refused and the reason surfaces in the dashboard and GET /api/health/invariants. Existing agents keep running.

Common mistakes and how to avoid them

  • Splitting at too fine a granularity. If each task is under 30 minutes of AI work, the coordination overhead (branch setup, PR review, merge) outweighs the parallelism benefit. Split at the feature level, not the function level.
  • Forgetting to set blocked-on relationships. Two agents that both depend on the same migration will both try to write it, creating a conflict. Map your dependency graph before launching.
  • Using git add -A in a shared directory. This is blocked by the amux guard for exactly this reason. Always stage specific files.
  • Not reading the continuation before resuming a crashed agent's task. Check the card for a continuation note before sending a fresh prompt. The continuation tells you where the previous session left off.

Split your next sprint across a fleet

Install amux, decompose your project into board cards, and start all agents in one command. Open source, self-hosted, zero vendor lock-in.

curl -fsSL https://amux.io/install.sh | bash
amux register task-1 --dir ~/Dev/myapp --yolo
amux register task-2 --dir ~/Dev/myapp --yolo
amux start-all
