Declarative AI Agent Setup

Configure your entire AI engineering team with a single YAML file — workers, groups, schedules, skills. Apply it idempotently. Commit it to git.

Declarative AI agent setup means defining your entire AI engineering team in a configuration file — what workers exist, how they are grouped, what skills they have, and when they run — and letting the tool reconcile the current state to the declared state automatically. amux IaC (Infrastructure as Code) does this with a single YAML file called a vertical. Run amux iac apply vertical.yaml to apply it idempotently: the team is created if it does not exist, updated if the configuration changed, and left untouched if it already matches. Commit vertical.yaml to git and your AI engineering team is version-controlled just like your application code.

New in August 2026 — amux iac shipped in amux v0.9.x. See the changelog for details.

What is declarative AI agent setup?

There are two ways to configure an AI engineering team:

Imperative (manual): Run a series of commands. amux register worker-1. amux register worker-2. Manually assign workers to groups. Configure schedules one at a time in the dashboard. Update CLAUDE.md on each worker. If you need to recreate the team on a new machine, you remember what you did (or you don't). No history. No rollback. No review.

Declarative (amux IaC): Write a vertical.yaml that describes the desired state of your team. Run amux iac apply vertical.yaml. amux figures out what needs to be created, changed, or left alone. Run it again — nothing changes if the state already matches. Commit the file — your team configuration is now in version control with full history and review.

The declarative approach is how professional engineering teams manage infrastructure. Kubernetes, Terraform, and Ansible all apply the same principle. amux IaC brings it to AI agent teams.

The vertical YAML format

A vertical is the unit of AI engineering team configuration in amux. One vertical.yaml file describes a complete team — typically corresponding to one product area, one codebase, or one business function.

# vertical.yaml — a complete AI engineering team configuration
name: backend-team
description: "AI engineering team for the core API and data pipeline"

workers:
  - name: api-worker-1
    dir: ~/Dev/myproject
    runtime: claude-code        # claude-code | codex | gemini-cli
    skin: senior-backend        # persona template (optional)
    flags: ["--yolo"]

  - name: api-worker-2
    dir: ~/Dev/myproject
    runtime: claude-code
    skin: senior-backend

  - name: doc-writer
    dir: ~/Dev/myproject
    runtime: gemini-cli         # long-context doc tasks
    skin: documentation-writer

  - name: security-reviewer
    dir: ~/Dev/myproject
    runtime: codex
    skin: security-reviewer

groups:
  - name: backend-team
    members: [api-worker-1, api-worker-2, doc-writer, security-reviewer]
    description: "Core backend engineering group"

schedules:
  - name: daily-standup
    cron: "0 9 * * 1-5"        # weekdays at 9am
    target_group: backend-team
    command: "Run standup: what did you complete yesterday, what are you working on today, any blockers?"

  - name: weekly-review
    cron: "0 17 * * 5"         # Fridays at 5pm
    target_group: backend-team
    command: "Create a weekly summary of completed tasks, open PRs, and next week priorities. Post to board."

env:
  ANTHROPIC_API_KEY: "${ANTHROPIC_API_KEY}"
  GITHUB_TOKEN: "${GITHUB_TOKEN}"

skills:
  - pr-review
  - code-review
  - documentation

How to configure AI agents as code: step by step

Step 1 — Install amux

curl -fsSL https://amux.io/install.sh | bash


# From source
git clone https://github.com/mixpeek/amux && cd amux && ./install.sh

amux serve  # → https://localhost:8824

Step 2 — Write your vertical.yaml

Start with the minimal form — just workers and a group. You can add schedules, skins, and environment variables incrementally:

# minimal-vertical.yaml — start here
name: my-team

workers:
  - name: worker-1
    dir: ~/Dev/myproject
    runtime: claude-code

  - name: worker-2
    dir: ~/Dev/myproject
    runtime: claude-code

groups:
  - name: my-team
    members: [worker-1, worker-2]

Step 3 — Apply the vertical

amux iac apply minimal-vertical.yaml

# Output:
# ✓ Created worker: worker-1 (claude-code, ~/Dev/myproject)
# ✓ Created worker: worker-2 (claude-code, ~/Dev/myproject)
# ✓ Created group: my-team (2 members)
# Applied in 0.4s

Run it again immediately:

amux iac apply minimal-vertical.yaml

# Output:
# ✓ worker-1 — no change
# ✓ worker-2 — no change
# ✓ group my-team — no change
# Nothing to do (0.1s)

This is idempotency. The second apply is a no-op because the current state already matches the declaration.

Step 4 — Commit to git

git add vertical.yaml
git commit -m "feat: add backend AI engineering team configuration"
git push

Your AI engineering team is now version-controlled. Every change to the team configuration goes through the same review process as your application code. New team members can clone the repo and apply the vertical to spin up the same configuration in minutes.

Step 5 — Apply skins for consistent worker personas

Skins are reusable persona templates stored on disk. A skin bundles a CLAUDE.md instruction set, environment variables, and skill assignments into a named template. Create skin files in your amux skills directory and reference them by name in the vertical:

# In vertical.yaml — reference skins by name
workers:
  - name: backend-lead
    skin: senior-backend          # applies senior-backend skin to this worker
    runtime: claude-code
    dir: ~/Dev/myproject

  - name: security-reviewer
    skin: security-reviewer       # different persona for security tasks
    runtime: codex
    dir: ~/Dev/myproject

Now backend-lead and security-reviewer behave consistently with their defined personas every time the vertical is applied — regardless of which machine or environment they run on.

GitOps for AI engineering teams

GitOps is the practice of using a Git repository as the single source of truth for your operational state. Every change is proposed as a pull request, reviewed, merged, and then automatically applied by a pipeline. Infrastructure teams use GitOps with Terraform and Kubernetes to manage cloud resources. amux IaC brings GitOps to AI engineering teams.

A complete GitOps workflow for an AI engineering team:

  1. All team configuration lives in vertical.yaml — committed to the same repository as the application code it builds
  2. Changes proposed as pull requests — adding a worker, changing a schedule, assigning a new skin — all go through review before being applied to the running team
  3. CI pipeline validates the YAML — syntax check, schema validation, amux iac apply --dry-run in CI to catch errors before merge
  4. Apply on merge — the pipeline runs amux iac apply vertical.yaml on merge to main, automatically reconciling the running team to the declared configuration
  5. Audit trail in git history — who made the change, when, why (commit message), reviewed by whom (PR review)

Version-controlling your AI engineering team

The most immediate benefit of declarative setup is version control. When you store vertical.yaml in git, you get:

History — who added the security-reviewer worker, and when. Who changed the daily standup schedule from 9am to 8:30am. Why the doc-writer was reassigned from Gemini CLI to Claude Code.

Rollback — if a configuration change causes problems (a new worker is assigned a skin that produces bad output; a schedule fires too frequently), git revert and amux iac apply restores the previous state in seconds.

Branching for experiments — test a new team structure on a feature branch before committing to it. Apply the branch's vertical.yaml to a staging environment. Merge if it works; discard if it doesn't.

Onboarding — new engineers joining the team can apply the production team configuration to their local environment with two commands. No walking through setup. No "ask Alice what the flags were."

Multi-runtime teams: Claude Code, Codex, and Gemini CLI

amux is multi-runtime: a single vertical.yaml can declare workers using different AI runtimes for different tasks. Specify runtime per worker:

workers:
  - name: complex-reasoning
    runtime: claude-code          # Claude Code (Anthropic) — best for complex reasoning
    dir: ~/Dev/myproject

  - name: fast-codegen
    runtime: codex                # Codex CLI (OpenAI) — fast code generation
    dir: ~/Dev/myproject

  - name: long-context-docs
    runtime: gemini-cli           # Gemini CLI (Google) — 1M token context for large docs
    dir: ~/Dev/myproject

amux monitors, self-heals, and manages all three runtimes from a single dashboard and mobile app — one team, one vertical.yaml, one control plane, regardless of which underlying model each worker uses.

Frequently asked questions

What is declarative AI agent setup?

Declarative AI agent setup means defining the desired state of your AI engineering team in a configuration file rather than running commands manually. You describe WHAT you want — 10 workers, 3 groups, a daily standup schedule — and the tool reconciles the current state to your declaration. amux IaC uses a YAML file called a vertical. Run amux iac apply vertical.yaml to apply it idempotently: the team is created if missing, updated if changed, untouched if already correct.

How does amux IaC differ from Kubernetes or Terraform?

amux IaC applies the same declarative, idempotent reconciliation principle — but for AI engineering teams rather than infrastructure. Where Kubernetes reconciles pod counts, amux reconciles worker sessions. Where Terraform manages cloud resources, amux manages AI agent workers, groups, schedules, and skills. amux IaC runs entirely on your machine with no cloud dependency — it is self-hosted infrastructure-as-code for your AI team.

Can I use amux IaC in a CI/CD pipeline?

Yes. amux iac apply is a CLI command — add it to any CI/CD pipeline step. A common pattern: store vertical.yaml in your repository; add a step that runs amux iac apply vertical.yaml on merge to main. Every team configuration change is applied automatically after PR review. Use --dry-run in CI to validate changes without applying them.

What is a skin in amux?

A skin is a reusable persona template stored on disk. It bundles a CLAUDE.md instruction set, environment variables, and skill assignments into a named template. Reference skins in vertical.yaml to apply consistent personas to multiple workers — senior-backend, security-reviewer, documentation-writer — all defined once, applied everywhere, version-controlled with your config.

Does declarative setup work with Claude Code, Codex, and Gemini CLI?

Yes. amux is multi-runtime. Specify runtime: claude-code, runtime: codex, or runtime: gemini-cli per worker in your vertical.yaml. A single team can mix runtimes — Claude Code for complex reasoning, Codex for fast code generation, Gemini CLI for long-context document work. amux monitors and self-heals all three from one dashboard.

Can I version-control my AI team configuration?

Yes — this is the primary value of declarative setup. Commit vertical.yaml to git. Now your AI engineering team configuration has full version history, code review, rollback, and branching. Who changed what, when, and why. Roll back a bad configuration with git revert && amux iac apply. Apply the same configuration on any machine with two commands.

How is amux IaC different from a shell script that registers workers?

A shell script is imperative: it runs commands in sequence. Run it twice and you get duplicate workers. Add a worker and the script doesn't know which workers already exist. amux IaC is declarative and idempotent: it compares the desired state (YAML) to the current state (running workers), and applies only the difference. Run it twice — nothing changes. Add a worker — only that worker is created. This makes it safe to apply on every deployment without side effects.

Is amux IaC only for local setups, or can it apply to cloud deployments?

amux runs locally and on cloud VMs (amux cloud). The vertical.yaml format is the same for both — the runtime environment (local vs. cloud container) is configured separately. Apply the same vertical.yaml to your local development environment and to a cloud amux deployment, and you get the same team configuration in both places. This makes environment parity straightforward for teams that test locally and run production agents in the cloud.
