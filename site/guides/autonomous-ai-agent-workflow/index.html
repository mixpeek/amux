How to Build an Autonomous AI Engineering Team That Self-Manages

Your agents should work through a backlog, resume after usage limits, and alert you only when they genuinely need you. This is the setup that makes it happen. Updated September 2026.

Build an AI engineering team that runs itself overnight. Get started free

An autonomous AI engineering team runs a shared backlog without a human assigning each task. Agents claim work atomically, so no two agents take the same card. Agents resume after usage limits, and stall detection flags work that stops moving. Telegram alerts surface only the issues that require your attention. amux provides all of this as a single open-source control plane: one Rust binary, zero external dependencies, MIT + Commons Clause.

This guide covers the five-step setup and explains the mechanics behind each layer: board auto-drain, recovery and stall detection, group-scoped work queues, and Telegram routing.

Manual vs Autonomous: What Changes

Most teams start with manual agent management: assign a task, watch the terminal, reassign when done. That works for one or two agents. At five or more, the overhead becomes the bottleneck.

Dimension Manual management Autonomous workflow
Task assignment You assign each card to a specific session Sessions claim from the backlog automatically when they finish
Recovery You notice the crash, restart manually, re-send the task Stall detection flags the stopped card and an owner alert fires; agents resume on their own after usage limits
Overnight monitoring You stay up or accept lost progress until morning Agents run through the backlog; Telegram alerts only on real problems
Cost visibility Check each terminal manually; no aggregate view Dashboard shows per-session and fleet-wide token spend in real time
Mobile access SSH into a server or VPN to a terminal iOS app or mobile PWA; Telegram for alerts and steering
Scaling Linear: each new agent adds coordination overhead Sub-linear: the backlog and stall detection absorb the overhead

The goal is to shift the human role from coordinator to reviewer. You write the backlog and set quality gates. The agents work through it.

Step 1: Set Up the Shared Board Backlog

The board is a SQLite-backed kanban shared across every session. Each card in the todo column is a unit of work an agent can claim.

Write cards as self-contained prompts. The agent that picks one up has only the card's title and description to work from, so include everything it needs:

  • Clear scope. "Implement the /api/users/search endpoint with pagination" is claimable. "Work on the API" is not.
  • Success condition. "All existing tests pass and a new integration test covers the pagination edge case" gives the agent a checkable stop condition.
  • No external assumptions. If the agent needs a file path, a branch name, or a reference to another card, put it in the description.
# Add a card via CLI
amux board add "Implement /api/users/search with cursor-based pagination"

# Or via REST API
curl -sk -X POST -H 'Content-Type: application/json' \
  -d '{"title":"Implement /api/users/search with cursor pagination",
       "desc":"Add GET /api/users/search?q=&cursor= endpoint. Must support: full-text search on name/email, cursor-based pagination (50 results per page), < 200ms p99 on 100k users. Tests: all existing pass + new integration test for pagination boundary."}' \
  $AMUX_URL/api/board

Populate the backlog before your evening session. Ten cards is a reasonable overnight batch for a five-agent team. Add more with the scheduler if you want the backlog to replenish automatically on a schedule.

Step 2: Enable Auto-Drain on Each Session

Auto-drain is the mechanism that makes agents self-assign. When a session finishes its current card and the auto-drain toggle is on, it claims the next available card from the todo column without waiting for you.

Enable it per session from the dashboard: open the session card, click the settings icon, and toggle "Auto-drain from backlog." You can also enable it globally in the Settings tab under Fleet defaults, which applies to all new sessions.

The claim is atomic. When two sessions finish simultaneously and both try to claim the same next card, SQLite's row-level locking ensures exactly one succeeds. The other session moves to the next open card. No duplicate work, no coordination logic on your side.

Auto-drain respects card type and group scope. A session in the "frontend" group only drains cards tagged for that group. A session with no group assignment drains any untagged card. This lets you keep backend agents on backend work without manual assignment.

When to leave auto-drain off

Sessions doing exploratory or open-ended work often should not auto-drain. A session debugging a production incident needs focused attention, not a queue of unrelated backlog items waiting to start the moment it finishes. Toggle auto-drain at the session level to match each agent's role.

Step 3: Understand Recovery and Stall Detection

Recovery runs on every session by default. Understanding what it covers, and what it does not, lets you tune the backlog card size for overnight throughput.

amux covers three failure modes:

Failure modeWhat triggers itamux response
Context window full Claude Code hits its context limit mid-task Claude Code compacts its own context; amux lets you set the compaction threshold
Usage limit The provider's usage or rate limit hits Delivery is held; the agent resumes at the provider's reset time
Stalled work A card stops moving for longer than AMUX_GOAL_STALL_H, or an orchestrator is stuck Stall detection flags it and an owner alert fires

Write backlog cards at a size where a session can finish them in one context window. For most coding tasks, that means cards scoped to one endpoint, one test suite, or one component. Cards that span multiple files and require many tool calls will hit context limits more often and benefit most from a lower compaction threshold.

Restarting a crashed agent process is not built into the amux server. On macOS, the optional scripts/tmux-watchdog.sh (not installed by default) restarts crashed Claude Code workers. Otherwise a crashed session shows up as stalled work, and you restart it from the dashboard or your phone.

Step 4: Set Up Telegram Alerts

The goal of Telegram integration in an autonomous workflow is selective: you want to know when something genuinely needs you, not when every task completes. Set up the connection first, then configure each session for its alert level.

Connect Telegram:

  1. Create a bot via BotFather on Telegram. Copy the token.
  2. Add TELEGRAM_BOT_TOKEN=your_token to ~/.amux/server.env.
  3. Start a chat with your bot and send /start. This links your chat ID to the amux instance.
  4. Reload the server: launchctl kickstart -k gui/$(id -u)/com.amux.server-rs.

For group chats: link the group by sending /start from inside the group after you have an existing private link. Group delivery requires a @lane mention so only the intended session responds.

Useful alert patterns for autonomous workflows:

  • Stall alert: fires automatically when board work stops moving or an orchestrator is stuck. No setup needed.
  • Task completion summary: have each session send a brief summary card to a group chat when it marks a card done. Gives you a morning digest without polling the dashboard.
  • Human gate trigger: for cards that touch production, set a quality gate requiring approval before the card moves to done. The session alerts you and waits.

See the full Telegram notifications guide for the complete setup and routing options.

Step 5: Run Overnight and Review in the Morning

With auto-drain, stall detection, and Telegram configured, the overnight workflow is:

  1. Before bed: populate the backlog with tomorrow's tasks. Verify each session has auto-drain enabled. Check the dashboard shows all sessions as active.
  2. During the night: agents work through cards in order. Usage limits pause and resume on their own. If a card genuinely blocks, you get a Telegram message.
  3. In the morning: open the board. Done cards show completed work. Any card still in-progress has a timestamp. Cards that stopped moving were flagged by stall detection.
# Morning review: see what finished overnight
curl -sk $AMUX_URL/api/board | python3 -c "
import json, sys
items = json.load(sys.stdin)
done = [i for i in items if i['status'] == 'done']
todo = [i for i in items if i['status'] == 'todo']
print(f'{len(done)} done, {len(todo)} remaining')
for i in done: print(' ', i['title'][:60])
"

A well-loaded backlog of 10 cards for 5 agents typically completes in 4-6 hours for average-complexity coding tasks. Adjust card granularity based on what you see in the morning: if agents are finishing in under 30 minutes each, cards are too small. If stall alerts fire frequently, cards are too large.

Group-Scoped Drain: Keeping Agents in Their Lane

Without group scoping, every auto-drain session competes for every card. That works for homogeneous teams (all backend, all same codebase) but breaks for mixed teams where a frontend agent should not pick up a database migration card.

amux groups solve this. Assign each session to a group in its settings. Tag each board card with a group. Auto-drain then only claims cards matching the session's group, or cards with no group tag if the session is ungrouped.

Typical group setup for a five-agent team:

frontend-1frontendCards tagged "frontend" or untagged

backend-1backendCards tagged "backend" or untagged

testsqaCards tagged "qa" or untagged

Quality Gates and Human Checkpoints

Autonomous does not mean unsupervised. Quality gates let you insert human checkpoints at the right moments without slowing down the rest of the backlog.

The board supports per-card and per-type gates. A gate blocks the card from moving to done until the condition is acknowledged:

  • Peer review gate: requires another session to review the work before done. Useful for complex or risky tasks.
  • Human approval gate: requires a human to run amux board done CARD_ID --checked "..." with evidence. Good for anything that deploys or sends external messages.
  • Test gate: requires test output to be recorded as evidence. The session cannot mark done without pasting the test result.

Gates pair naturally with auto-drain: the blocked session stops on its current card and does not drain new work until the gate is resolved. Stall detection flags the waiting card so you know it needs you.

For overnight runs, a pragmatic setup:

  • Feature cards: peer review gate (another session verifies before done)
  • Deploy cards: human approval gate (you confirm in the morning)
  • Test-only cards: test gate (the session provides the pass line as evidence)

FAQ

What is an autonomous AI engineering team?

An autonomous AI engineering team is a set of AI coding agents that self-assign tasks from a shared backlog, resume after usage limits and flag stalled work, and run continuously without anyone watching each terminal. The key capabilities: a shared task queue agents claim atomically, a recovery layer that resumes agents after usage limits and flags stalled work, and a notification channel that surfaces only the issues that require human attention. amux provides all three in a single open-source control plane.

How does auto-drain work in amux?

Auto-drain is a per-session toggle. When enabled, a session that finishes its current task automatically claims the next open card from the board's todo column. The claim is atomic: SQLite row-level locking ensures no two sessions take the same card. You can scope drain to a group so frontend sessions only drain frontend cards. The feature shipped in AMUX-4055 on 2026-09-02.

What happens when an agent crashes overnight?

Restarting a crashed agent process is not built into the amux server today. On macOS, an optional script (scripts/tmux-watchdog.sh, not installed by default) restarts crashed Claude Code workers. What amux does do is make the stop visible: stall detection flags a card that stops moving and any stuck orchestrator, and an owner alert fires so you can restart the session from the dashboard or your phone. If the stop was a usage limit, amux holds delivery and resumes the agent at the provider's reset. After a macOS reboot, a login job brings every non-archived worker back in its own conversation.

Can agents steal each other's tasks?

No. The board uses atomic claiming backed by SQLite transactions. When a session claims a card, it transitions from todo to doing in a single transaction. Any concurrent claim attempt by another session fails, and that session moves to the next available card. This holds even when dozens of sessions drain the same backlog simultaneously.

How do I get notified when an agent finishes?

Connect your amux instance to Telegram by adding a bot token and linking a chat. Each session can send you a message when it completes a task or encounters a problem. amux supports both private Telegram chats and group chats where @lane mentions route messages to specific sessions. You can also check board status from the iOS app or mobile PWA without Telegram.

Is it safe to leave agents running unattended overnight?

Yes, with standard precautions. amux handles the infrastructure safety: usage-limit resume, atomic task claiming, and stall alerts. For the agents themselves, scope cards to reversible operations or use approval gates before irreversible steps. The practical baseline: agents that write and test code can run fully unattended. Agents that deploy to production or send external messages should have a human review gate before those specific steps.
