AI Agent Resource Limits: Worker Boundaries for Claude Code Fleets

One runaway agent can exhaust a machine and stall every other worker in the fleet. Declarative resource limits in boundaries.toml give each worker an explicit execution envelope the harness enforces from the outside.

Why Resource Limits Matter for Agent Fleets

A single-agent setup tolerates resource waste. If your one Claude Code session burns 90% of a CPU core doing a large refactor, that is fine; the machine has nothing else to protect. Scale to ten agents and the math changes: one agent compiling a monorepo, running a full test suite, or opening hundreds of file descriptors can degrade every other worker on the machine.

Without limits

Resource contention

One agent triggers a cargo build. Memory climbs to 18 GB. Five other workers swap. Their completions stall. Overnight run degrades silently.

With boundaries.toml

Bounded execution

Each worker gets a declared memory ceiling. The build worker is bounded at 6 GB. Other workers stay responsive. The breach is logged and surfaced on the dashboard.

A fleet without resource boundaries cannot distinguish a well-behaved worker from a runaway one until the machine is already under pressure. Declarative limits make the boundary explicit before the event, not visible only during it.

boundaries.toml: Declarative Resource Governance

boundaries.toml is the resource-governance config for an amux fleet. It lives in the project root alongside amux.toml and is committed to version control, making limit policies auditable and reviewable alongside the code they govern.

A minimal boundaries.toml:

# boundaries.toml — per-worker resource envelopes [defaults] memory_gb = 4 cpu_cores = 2 [workers.amux-general] memory_gb = 8 cpu_cores = 4 [workers.mixpeek-cicd] memory_gb = 6 cpu_cores = 2 [workers.mixpeek-general] memory_gb = 4 cpu_cores = 1

Workers not listed by name inherit the [defaults] values. Any worker can override any field. The harness reads this at startup and enforces the envelopes from the outside, independent of what the agent tries to do.

Enforcement is external. The agent process does not need to be aware of its limits. amux enforces the boundary from the orchestrator layer. When a worker approaches its ceiling, amux surfaces the signal on the dashboard. When it crosses the ceiling, amux pauses the worker and logs the event.

How to Set Resource Limits (Step by Step)

Step 1

Observe current usage with amux resources

Before setting limits, understand actual consumption. amux resources shows real-time CPU, memory, and disk usage across every active worker. Identify which agents run hot under normal conditions before declaring limits.

amux resources # sample output WORKER CPU MEM DISK amux-general 12% 1.4 GB 2.1 GB mixpeek-cicd 44% 3.8 GB 8.7 GB mixpeek-general 7% 0.9 GB 1.2 GB gainz 2% 0.4 GB 0.3 GB
Step 2

Create boundaries.toml with conservative defaults

Start with defaults that comfortably cover normal operation. Tight limits applied before you understand usage patterns cause unnecessary pauses. Use the amux resources baseline to set ceilings at roughly 2x the observed peak during normal work.

Step 3

Inspect and adjust with amux boundaries

amux boundaries gives an interactive view of each worker's declared limits alongside its current usage. From this view you can raise or lower individual fields without editing the file directly. Changes are written back to boundaries.toml.

amux boundaries # interactive — shows declared vs actual for each worker # press e on any row to edit its limits inline
Step 4

Commit and let the ratchet tighten over time

Commit boundaries.toml to version control. When a boundary breach happens, investigate the cause. If the work was legitimate, raise the limit. If it was a runaway task, tighten the limit and add a note. The file accumulates the fleet's resource policy history in the same way CLAUDE.md accumulates its behavioral policy history.

amux resources and amux boundaries

Two commands, two distinct jobs:

Command What it does When to use it
amux resources Real-time read: current CPU, memory, disk per worker Observing usage before setting limits; debugging a slow fleet
amux boundaries Read-write: declared limits vs actual usage; edit inline Setting or adjusting limits; reviewing limit policy across the fleet

Use amux resources to see what is happening. Use amux boundaries to set what should happen.

Limits for Isolated Workers

Isolated workers in amux run with direct owner-to-CLI transport. No board capture, no harness routing, no automated steering. The isolation is about control flow, not about resource governance.

As of October 2026, boundaries.toml limits apply to isolated workers too. The boundaries registry enforces the resource envelope from the outside regardless of the worker's isolation mode. An isolated worker that exceeds its memory ceiling is paused and logged the same way any other worker is.

This matters for long-running isolated workers: a session left overnight in isolated mode still needs a resource ceiling so it cannot exhaust the machine while the operator is away.

Resource Governance as Harness Engineering

Harness engineering applies the ratchet principle: every failure mode becomes a permanent fix in the harness. Resource limits are the ratchet applied to consumption: when a runaway agent causes a problem, the response is not just investigating and restarting. It is declaring a limit so the same class of runaway cannot happen again.

A harness without resource boundaries cannot enforce policy on consumption. It can observe a runaway agent after the fact. It cannot prevent the next one from occurring. Declarative limits close this gap.

The sequence:

  1. Agent misbehaves: memory grows unchecked, stalls the fleet
  2. You observe it with amux resources
  3. You declare a limit in boundaries.toml
  4. The harness enforces the limit going forward
  5. You commit boundaries.toml: the policy is now auditable and durable

The harness accumulates resource policy the same way it accumulates behavioral policy in CLAUDE.md. Every entry in boundaries.toml traces to a real usage event, real or anticipated.

FAQ

What are AI agent resource limits?

AI agent resource limits define the maximum CPU, memory, and disk each worker is allowed to consume. Without them, one runaway agent can starve the rest of the fleet. In amux, limits are declared in boundaries.toml and enforced by the orchestrator from the outside, independent of what the agent process does.

How do I set resource limits for Claude Code agents?

Create a boundaries.toml in your project root with per-worker or default limits. Use amux resources to baseline actual usage first, then set ceilings at roughly 2x the observed peak. Use amux boundaries to adjust limits interactively without editing the file directly.

What happens when an agent hits its resource limit in amux?

amux pauses the worker and logs the breach rather than hard-killing the process. The event surfaces on the dashboard and in the task log. The operator can raise the limit, terminate the worker, or investigate. Pausing rather than killing preserves the agent's context for inspection.

What is boundaries.toml in amux?

boundaries.toml is the declarative resource-governance file for an amux fleet. Each entry names a worker and its allowed resource envelope. A [defaults] section applies to workers not explicitly listed. The file is committed to version control alongside amux.toml, making limit policies auditable.

Do resource limits apply to isolated workers in amux?

Yes, as of October 2026. Isolated workers run with a direct transport and no harness routing, but boundaries still apply to them. The enforcement is from the orchestrator layer, which operates regardless of the worker's isolation mode.

What is the difference between amux resources and amux boundaries?

amux resources is read-only: it shows real-time consumption across all workers. amux boundaries is read-write: it shows declared limits alongside actual usage and lets you edit limits inline. Use amux resources to observe, amux boundaries to govern.
