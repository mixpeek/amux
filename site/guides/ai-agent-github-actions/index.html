Trigger AI Agents from GitHub Actions

How to fire a named Claude Code worker on any GitHub event — PR opened, test failed, issue filed.

Published August 2026

GitHub Actions can trigger a task on any repository event: a PR opened, a test suite fails, a new issue is labeled. amux adds the missing layer — a running AI coding agent that receives that task via HTTP, executes it in your codebase, and returns results you can read from your phone or CI dashboard. No IDE required. No manual intervention.

The new canonical worker-send route (POST /api/sessions/<worker-name>/send) makes a named amux agent addressable from any external system — a curl command in an Actions step, a webhook handler, a Zapier action, or a custom script. Sends to a rate-limited worker hold automatically until the limit is released, so your workflow never loses a task mid-run.

How event-driven AI agents work

The pattern has three components:

  1. amux worker. A named Claude Code (or Codex, Gemini CLI) session running on your server or local machine, registered with amux and listening for tasks.
  2. amux REST API. An HTTP endpoint that accepts a task string and routes it to the named worker. Returns immediately; the worker processes asynchronously.
  3. GitHub Actions workflow. A YAML workflow that fires on a GitHub event, builds the task payload (PR diff, issue body, test output), and calls the amux API.

The worker runs against your real codebase — not a sandbox, not a cloud VM. It can read files, write code, run tests, make commits, and push branches, with the same permissions as a developer on your team.

Step-by-step setup

Step 1: Start a named worker

# Register a named worker for code review
amux register reviewer --dir ~/Dev/myproject --yolo
amux start reviewer
# The worker name 'reviewer' is now addressable via the API

Each worker has a stable name. A fleet of specialized workers — reviewer, test-writer, docs-bot, bugfixer — can each receive tasks from different workflow events, routed by name.

Step 2: Expose amux to GitHub Actions

GitHub Actions runners need HTTP access to your amux server. Two options:

  • amux tunnel (easiest): amux tunnel start 8824 gives you a stable public HTTPS URL. Store it in a GitHub Actions secret (AMUX_URL). The tunnel stays alive as long as amux runs — no open inbound port required.
  • Cloud deployment: Deploy amux on a VPS or cloud server with a public IP. The amux server runs as a single binary; full setup takes under 10 minutes.

Step 3: Write the GitHub Actions workflow

name: AI Code Review

on:
  pull_request:
    types: [opened, synchronize]

jobs:
  ai-review:
    runs-on: ubuntu-latest
    steps:
      - name: Fetch PR diff
        id: diff
        run: |
          DIFF=$(gh pr diff ${{ github.event.pull_request.number }} --repo ${{ github.repository }})
          echo "diff=$DIFF" >> $GITHUB_OUTPUT
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

      - name: Send to AI reviewer
        run: |
          curl -s -X POST \
            -H "Content-Type: text/plain" \
            -d "Review this PR diff and comment on: correctness, edge cases, and test coverage. PR #${{ github.event.pull_request.number }}: ${{ steps.diff.outputs.diff }}" \
            ${{ secrets.AMUX_URL }}/api/sessions/reviewer/send
        env:
          AMUX_URL: ${{ secrets.AMUX_URL }}

Step 4: Read the agent's output

      - name: Wait and fetch review output
        run: |
          sleep 60  # Wait for the review to complete
          OUTPUT=$(curl -s "${{ secrets.AMUX_URL }}/api/sessions/reviewer/peek?lines=100" | \
            python3 -c "import json,sys; print(json.load(sys.stdin).get('history',''))")
          echo "$OUTPUT" | tail -50  # Show last 50 lines

For longer tasks, poll the board card status rather than sleeping: the card moves to done when the worker finishes. For PR review specifically, instruct the agent to post a GitHub PR comment directly using gh pr comment — you get the result in the PR without needing to parse peek output.

Rate-limit handling

Claude Code (and other runtimes) can hit API rate limits during long batch runs. The amux worker-send endpoint now holds a message if the target worker is rate-limited, and delivers it as soon as the limit is released. This means your GitHub Actions workflow does not need retry logic — send the task once and amux handles the rest.

# This call returns immediately (202 Accepted)
# If the worker is rate-limited, the message queues automatically
curl -s -X POST \
  -H "Content-Type: text/plain" \
  -d "Fix the failing test in auth/session_test.go" \
  $AMUX_URL/api/sessions/bugfixer/send

Workflow patterns

PR review bot

Fire a reviewer agent on every new PR. The agent reads the diff, checks the codebase context, and posts a PR comment with findings. Engineering managers see the review in the PR thread alongside human reviews.

Issue-to-PR automation

When an issue is labeled good-first-issue or autofix, trigger an agent to implement the fix and open a draft PR. The agent can query the codebase, write the fix, add tests, and push a branch — all from the issue body as input.

Nightly test expansion

Schedule a workflow to run every night at 2am. The worker scans for modules with test coverage below a threshold and writes additional tests. Morning push shows the new test files in a PR for review.

Deploy-triggered documentation

On every merge to main, trigger a docs worker with the list of changed source files. The worker updates the corresponding documentation files and opens a docs PR. Documentation stays in sync with code without manual effort.

Security considerations

  • Store the AMUX_URL as a secret. The amux tunnel URL is an unguessable token-derived URL, not publicly advertised — but treat it like an API key. Use GitHub Actions secrets, not hardcoded values.
  • Scope the worker's permissions. The Claude Code session runs with the same filesystem and Git permissions as the user who started it. On a shared server, register each worker under a user with appropriate scope.
  • Validate the event payload. If your workflow includes PR diff content in the task body, sanitize or escape it before inclusion to prevent prompt injection.
  • Rate your triggers. A workflow that fires on every commit push can quickly consume many agent turns. Use paths or branch filters to scope when the workflow runs.

Monitoring agent activity

Every worker-send call creates a board card in amux that tracks the task status — queued, running, done. From the amux dashboard or iOS app, you can see which GitHub events are actively being processed, peek into any worker's live output, and steer a running worker with a follow-up message.

# See all running AI agent tasks from the CLI
curl -s $AMUX_URL/api/board | python3 -c "
import json,sys
[print(i['status'], i['title'][:60]) for i in json.load(sys.stdin) if i['status'] != 'done']
"

FAQ

Can I run Claude Code from GitHub Actions?

Not directly — Claude Code requires a terminal session on a machine with the right API keys and codebase access. But you can trigger a Claude Code agent via the amux REST API from any Actions step. The agent runs on your server; the workflow just sends the task and optionally polls for the result.

What GitHub events can trigger an AI coding agent?

Any event supported by GitHub Actions: pull_request (opened, synchronize, labeled), issues (opened, labeled), push, schedule, workflow_dispatch, and more. The most common triggers are PR open (for review) and issue labeling (for implementation).

How do I send the PR diff to an AI agent?

Use gh pr diff in an Actions step to capture the diff, then include it in the body of your curl POST to the amux worker-send endpoint. Keep diffs under ~50k tokens to avoid context limits; for large PRs, send the changed file list and let the agent read individual files from disk.

Can I send tasks to a specific AI agent by name?

Yes. The canonical endpoint is POST /api/sessions/<worker-name>/send. A specialized fleet — reviewer, test-writer, docs-bot — receives different task types from different workflow triggers, each routed by name. The send holds automatically if a worker is rate-limited.

Does the AI agent run inside the GitHub Actions runner?

No — the agent runs on your server where amux is installed. The Actions runner just sends an HTTP request to the amux API. This means the agent has no runner timeout constraints, can run for hours, and has full access to your local codebase and toolchain.

What if the amux worker is offline when the workflow fires?

The send endpoint returns a 503 if the worker session does not exist. Start critical workers with amux start --persistent (or via launchd/systemd) so they restart on reboot. For event-triggered dispatch, check the response status in your Actions step and retry or alert on failure.
