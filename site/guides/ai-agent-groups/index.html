AI Agent Groups
Organize Your Fleet into Namespaced Sub-Teams (2026)

What is a group in amux?

Groups are one of the eight core primitives in amux: board, workers, schedulers, filesystem, groups, memories, environment, and messages. Every other primitive is scoped by the group boundary — memory lookups, environment variable inheritance, board views, and gate checks all respect the group namespace.

Concretely, a group is a string label you assign to a worker at registration. Workers with the same label form a group. Workers without a label are private to their own session.

  • Shared memory scope — all workers in a group read from and write to the same memory store. An agent's findings are immediately available to its group peers without manual copy-paste.
  • Shared environment — group-level environment variables are injected into every worker in the group. Set a GITHUB_TOKEN or a staging API key once; every group member receives it.
  • Isolated board view — the board filters to cards owned by the group. Workers do not see or accidentally claim tasks from other groups.
  • Coordination gates — group-level gates (reviewer assignments, done-vs-verified checks) apply across all workers in the group, preventing premature task closure without a peer review.

Groups at a glance

Before August 2026, comparing two groups required selecting each one in turn and holding the previous group's state in your head. The pill bar in the dashboard told you groups existed but not which was busy, which was idle, or which had a full task queue.

The groups panel, shipped in August 2026, resolves this. It renders one collapsed row per group, showing:

  • Member names — the actual worker names (not just a count), so you immediately know who is in each team
  • Activity split — active / idle / waiting counts, color-coded: active agents are working, idle agents are waiting for a prompt, waiting agents are paused on a human-in-the-loop gate
  • Board depth — doing and todo task counts for the group's board, so you can see which team has the heaviest task backlog
  • Schedule count — number of scheduled jobs registered to the group, so you know which teams have recurring automation running

Clicking a group row navigates into that group's scoped view: the board, sessions, memories, and environment all filter to that namespace automatically.

What groups enable

Specialized functional teams

Assign workers by function — backend, frontend, ops, gtm — and each team works independently on its own board queue. The groups panel lets you monitor all teams simultaneously from one screen (or from your phone). When the backend board empties and frontend still has 12 tasks queued, you know where to send reinforcements.

Customer and project isolation

Each client or project gets its own group. Their board cards, memories, and environment variables are completely isolated. An agent working on client-acme cannot see or claim tasks from client-beta. This is the same isolation pattern used by agencies managing multiple parallel client projects with amux — see amux for agencies.

Development vs. production environments

Separate a staging group from a production group. Each group inherits different environment variables (different API keys, different database URLs). Workers never accidentally read staging credentials when running production tasks.

Group-level gate enforcement

Board gates (the "done vs. verified" distinction, reviewer assignment requirements) apply at the group level. A task cannot be marked verified unless another worker in the same group has reviewed it. This gives you a lightweight peer-review workflow without any additional tooling.

How to set up groups

  1. Register workers with a group name. 
    amux register backend-1 --dir ~/Dev/myproject --group backend
amux register backend-2 --dir ~/Dev/myproject --group backend
amux register frontend-1 --dir ~/Dev/myproject --group frontend
    Workers with the same --group value are automatically placed in the same namespace. No separate group-creation step is required — the group is created on first registration.
  2. Set group-level environment variables. 
    # Via the dashboard: Settings → Groups → backend → Environment
# Or via the API:
curl -sk -X POST https://localhost:8824/api/env/apply \
  -H 'Content-Type: application/json' \
  -d '{"group":"backend","vars":{"STAGING_API_KEY":"..."}}'
    All workers in backend will receive STAGING_API_KEY on their next turn.
  3. Open the Groups panel. In the amux dashboard, click the Groups pill in the top nav or the Groups tab in the sidebar. Each group appears as a collapsed row with member names, activity split, board counts, and schedule counts.
  4. Navigate into a group. Click any group row to scope the dashboard to that group. The board, sessions panel, memories, and environment tabs all filter to the group namespace automatically. Click the group pill again or use the breadcrumb to return to the all-groups view.
  5. Monitor overnight from your phone. The groups panel is fully responsive. From the amux iOS app or mobile PWA, you can see every team's activity split and board depth at a glance. When a group shows zero active and zero todo, its team has finished its queue — you can send it new tasks directly from your phone.

Board visibilityAll cards from all workers visible to everyoneEach group sees only its own cards
Memory scopeAll workers share one memory storeEach group has its own memory namespace
Environment variablesOne global env; all workers inherit itPer-group env; workers inherit their group's vars
Task claimingAny worker can claim any task (may cause collisions)Workers claim tasks only within their group's board
Comparison viewMust switch between sessions manuallyGroups panel shows all teams simultaneously
Gate enforcementGlobal gates apply to all tasks equallyGroup-level gates (reviewer, done-vs-verified)
IsolationNone — one agent's writes affect allComplete namespace isolation between groups

Frequently asked questions

What is an amux group?

A group in amux is a named namespace that organizes workers (AI coding agent sessions) into a sub-team. Workers in the same group share memory context, environment variables, and an isolated board view. Groups are one of the eight core primitives in amux: board, workers, schedulers, filesystem, groups, memories, environment, and messages.

Do agents in a group share context?

Yes. Agents in the same group share memory scope and environment variables, so they can reference each other's outputs without manual coordination. Each agent still runs in its own isolated tmux session with its own codebase access — groups share the coordination layer, not the execution environment. A backend agent writing a memory entry like "auth service uses JWT with 15-min expiry" makes that fact immediately queryable by every other backend agent.

How many groups can I have in amux?

There is no limit on the number of groups. Each group is a lightweight namespace — no extra processes, no extra memory beyond the metadata. A typical setup has 3-8 groups representing functional areas: backend, frontend, ops, gtm, customers, and so on. Very large fleets (50+ agents) sometimes use a two-level structure: a top-level group per project and worker-level specializations within each group.

Can an agent be in multiple groups?

No. Each worker belongs to exactly one group (or to no group, in which case it is visible only to its own session). This keeps the scoping model simple and prevents board pollution across namespaces. If a task needs coordination between two groups, the standard pattern is to post the cross-group message to the board as an unowned card that either group can claim, or to use the amux send command to relay a message directly to a specific session.

How does the groups at-a-glance view work?

The Groups panel shows one collapsed row per group. Each row displays the group's member names (not just a count — names are what let you recognize who is in each team), active/idle/waiting activity split, board doing/todo task counts, and scheduled job counts. Clicking a row navigates into that group's scoped view. Previously you had to select each group in turn to compare activity — the at-a-glance panel lets you see the full fleet's team structure simultaneously, including from the mobile PWA.
