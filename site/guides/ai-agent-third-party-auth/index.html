How to Authorize AI Agents for Third-Party Services

The OAuth broker in amux's Connectors tab lets you authorize once and share that grant with every agent in your fleet. No per-session credential setup, no credentials in prompts. Updated August 2026.

amux is open source — self-host your agent fleet with built-in OAuth management, kanban, and mobile oversight. View amux on GitHub ★

The short answer: AI agents running in headless terminal sessions can't complete browser-based OAuth flows themselves. amux solves this with a central OAuth broker in the Connectors tab — you authorize a service once from your browser, and every agent in your fleet receives the grant automatically as environment variables at startup.

The problem: headless agents can't do OAuth

Most modern APIs use OAuth 2.0 for authorization — Google Drive, Gmail, Slack, GitHub, and dozens of others. The standard OAuth flow requires a browser: the user visits an authorization URL, signs in, approves permissions, and the service redirects back with an authorization code.

AI coding agents running in terminal sessions can't do this. A Claude Code session in tmux has no browser, no way to open an authorization URL, and no way to receive the redirect. The workarounds are all bad:

  • Paste the OAuth token into a prompt: Tokens appear in the agent's conversation history, which gets logged. Rotate the token and you have to update every active session manually.
  • Set tokens as environment variables before launching the session: Works for one session. Running 20 parallel agents means 20 separate env setups. Tokens expire and the agents silently fail.
  • Give agents service account keys: Service accounts work for some services but not consumer APIs. They also require per-developer key distribution and rotation.

The amux OAuth broker handles this at the platform level: authorize once, the broker holds the tokens, every agent gets them automatically.

How the amux OAuth broker works

The broker is a component of the amux server. When you connect a service in the Connectors tab:

  1. Authorization URL: amux generates an authorization URL for the service using your configured OAuth client credentials (or amux's default client for supported services).
  2. Browser flow (once): You visit the URL, approve permissions in the service's standard consent screen. This is the only browser interaction required — ever, until the grant is revoked.
  3. Token storage: The service redirects back to amux with an authorization code. The server exchanges it for access + refresh tokens and stores them locally in the amux SQLite database.
  4. Agent injection: When any agent session launches, amux injects the access token as a named environment variable (e.g., GOOGLE_ACCESS_TOKEN). The token is refreshed automatically before expiry.
  5. Health monitoring: A background canary probe periodically validates each token. Status is visible in the Connectors tab (ok / api_error / unreachable / not_granted) and reported on the board if anything breaks.

Step-by-step: connect a service

Google (Gmail, Drive, Calendar)

  1. Open the amux dashboard and click the Connectors tab (or press C).
  2. Find Google in the provider list and click Connect.
  3. A browser tab opens to Google's authorization screen. Sign in with the Google account your agents should use.
  4. Approve the requested permissions. amux requests only the scopes it uses: Gmail read/send, Drive read/write, Calendar read/write. You can narrow these in your OAuth client configuration.
  5. The browser closes and the Connectors tab shows a green ok status for Google.
  6. Every agent launched from now on receives GOOGLE_ACCESS_TOKEN as an environment variable, valid for 1 hour and refreshed automatically.

Custom OAuth service

For services not in the default registry, use the Custom provider type:

  1. In the Connectors tab, click Add Custom.
  2. Enter the service name, authorization URL, token URL, and the scopes your agents need.
  3. Paste your OAuth client ID and secret (these stay on your server — amux never transmits them).
  4. Click Connect to run the browser authorization flow.
  5. Set the environment variable name agents should use (e.g., MYSERVICE_TOKEN).

Simple API keys (non-OAuth)

For services that use API keys rather than OAuth, the Connectors tab also supports paste-once key storage with the same scoping and health-check system. See the AI Agent Connectors guide for the full key management flow.

Credential scoping

Not every agent should access every credential. The Connectors tab lets you scope each grant:

Scope Who receives the credential When to use
Global Every agent session in this amux instance Shared read-only services (public APIs, analytics)
Group Agents in a named group Team-specific or project-specific integrations
Worker One specific named agent session High-privilege credentials, billing-sensitive keys, production write access

A Google account with write access to production Drive should be scoped to worker (a specific agent assigned to a specific task), not global. A read-only analytics API key can safely be global.

What agents see

Inside a Claude Code or Codex session, credentials from the Connectors tab appear as regular environment variables:

echo $GOOGLE_ACCESS_TOKEN      # valid access token, auto-refreshed
echo $GOOGLE_REFRESH_TOKEN     # held by the broker; injected for services that need it
echo $MYSERVICE_API_KEY        # API key credentials appear the same way

Agents read them the same way any application reads credentials from env vars. No special SDK, no amux-specific library, no broker API to call. The agent's code doesn't know the tokens come from an OAuth broker.

In CLAUDE.md, you can reference the env var name so the model knows it's available:

## Available integrations
- Google Drive: use the GOOGLE_ACCESS_TOKEN env var (already set — do not ask the user for it)
- Custom API: MYSERVICE_API_KEY is available for requests to api.myservice.com

Token refresh and expiry

OAuth access tokens typically expire after 1 hour. amux handles this transparently:

  • The broker refreshes tokens proactively, before they expire, using the stored refresh token.
  • Running sessions receive a fresh token at their next launch — long-running sessions (overnight runs) get updated tokens injected via the steering queue when a refresh occurs mid-session.
  • If a refresh fails (revoked grant, expired refresh token), the Connectors tab updates to not_granted and the broker creates an autofix card on the board. The card owner gets a notification.

Security considerations

The OAuth broker is designed for teams running amux on their own infrastructure, not as a multi-tenant service. Key points:

  • Tokens stay on your server: Access and refresh tokens live in the local SQLite database. They are not transmitted to Mixpeek servers or any third party.
  • The amux database is not encrypted at rest: Anyone with read access to the server's filesystem can read the SQLite file, including stored tokens. Restrict filesystem access to the amux server process and its operators.
  • Use worker scope for production write access: Do not grant a globally-scoped token with production write permissions. An agent working on a test task should not be able to delete production Drive files.
  • Revocation is one click: In the Connectors tab, click Disconnect to revoke the stored grant and remove it from all future agent launches. You can also revoke at the service directly (in Google Account permissions, etc.) — amux's canary will detect it and update the status within one probe cycle.

FAQ

How do I authorize an AI agent to access a third-party service?

Open the amux Connectors tab, select the service, click Connect, and complete the standard browser OAuth flow once. The amux broker holds the resulting tokens and distributes them to every agent in your fleet as environment variables at launch. No per-session setup is needed after the initial authorization.

What is an OAuth broker for AI agents?

An OAuth broker holds OAuth tokens centrally on behalf of a fleet of headless agents that can't run browser-based authorization flows. The broker completes the auth flow once (via a human in a browser), stores the tokens, and distributes short-lived access tokens to agents at session launch. amux's OAuth broker is part of the server process — there's no separate service to run.

Can I scope an OAuth grant to specific agents only?

Yes — global, group, or worker scope. Global means every agent gets it. Group limits to a named group of sessions. Worker restricts to one specific named session. Use worker scope for high-privilege credentials like accounts with production write access.

What happens when the OAuth token expires or is revoked?

amux's health canary detects expired or revoked tokens within one probe cycle. The Connectors tab updates to not_granted, an autofix card appears on the board, and the card owner receives an in-app notification. Re-authorizing from the Connectors tab restores the grant for all agents.

Does amux support services that use API keys instead of OAuth?

Yes — the Connectors tab handles both. For API key-based services, paste the key once and amux injects it as an environment variable for every agent in scope. The same health-check and scoping system applies. See the AI Agent Connectors guide for full details.
