AI Agent Standing Approvals

The single biggest reason overnight AI coding runs stall: agents pause and wait for a permission response that never comes. Standing approvals solve this — you define which action categories are pre-approved, set caps, and agents handle them without waking you up. Updated September 2026.

The Overnight Hang Problem

You queue 15 tasks, start your agent fleet at midnight, and go to sleep. At 2am, agent 3 hits an action it wants approval for — calling an external API, running a long-lived test suite, writing to a config file. It surfaces the request to you and waits. You are asleep. The agent sits idle for 6 hours. By morning, 14 tasks are untouched because agent 3 was the bottleneck for four downstream tasks.

This is the most common failure mode in overnight AI coding. It is not a model quality problem — the agent correctly identified it needed authorization. It is an authorization design problem: the only channel was synchronous, human-in-the-loop approval.

Standing approvals make certain authorization decisions asynchronous. You decide in advance which categories of action are acceptable, under what conditions, and with what limits. The agent calls the approval channel, amux checks the rules, and either answers automatically or surfaces the request to you if no rule covers it.

What Are Standing Approvals?

A standing approval is a rule you define once in the amux dashboard. It says: "For this category of action, if the agent's request matches these conditions, respond with this answer."

Each rule has:

  • Title — a human-readable name, e.g. "Run tests and linters"
  • Allowed — a plain-language sentence describing what is allowed, shown to you and logged on each use
  • Category — one of six categories (see below)
  • Limits — free-text constraints shown verbatim to the agent when the rule fires
  • Caps — structured enforcement: max uses per day, maximum dollar amount per request
  • Scope — global, a specific group, or a specific worker
  • Expiry — optional date after which the rule stops firing

Every time the rule fires, amux logs it: which agent asked, what they asked for, whether the cap was still available. You get a usage feed, not blind automation.

Approval Categories

amux organizes requests into six categories, matched against the agent's escalation text:

Category Covers Risk level Typical use
access File, network, or service access Low Reading config files, running tests, using linters
credential Using stored API keys or secrets Medium Read-only calls to Stripe, Slack, internal APIs
budget Spending, paid API calls Medium Sending emails, calling paid inference APIs, purchasing
decision Judgment calls on approach or scope Medium Choosing an implementation approach, refactoring scope
prod_data Reading or writing production data High Read-only prod DB queries for diagnostic purposes
customer_outbound Emails, messages, external notifications High Automated status emails to a known-safe list

Low-risk categories (access, credential for read-only) are safe to pre-approve broadly. High-risk categories (prod_data, customer_outbound) should use narrow scope, strict require_terms, and low max_per_day caps.

How to Configure Standing Approvals

In the amux dashboard, go to Settings › Approvals. Click Add approval.

  1. Title: Name the rule clearly — "Run test suite (max 10/day)" is better than "Tests".
  2. Allowed: Write a plain sentence that describes what you are permitting. This text is shown in the usage feed on every invocation: "Agent may run the full test suite and all configured linters."
  3. Category: Choose the category from the six options. This is how amux routes incoming requests to the right rules — choose the category that best matches what you are authorizing.
  4. Limits: Add human-readable constraints to show the agent alongside the approval. Example: "Read-only. Do not modify any database records." These are informational — they are logged, not enforced programmatically.
  5. Caps: Set max_per_day to limit fires in a rolling 24h window. Set max_amount_usd if the rule covers spending — the rule will not fire if the agent's ask names a dollar figure above the cap.
  6. Scope: Choose global, group, or worker (see Scope section below).
  7. Click Save. The rule is active immediately for all running sessions in its scope.

Scope: Global, Group, Worker

Scope controls which agents can invoke a standing approval:

  • global — all workers in your fleet. Use for low-risk rules you are comfortable applying everywhere (running linters, reading config files, creating git branches).
  • group:<name> — only workers in the named group. Use when one team of agents has permissions that others should not. Example: the devops group can trigger CI; other groups cannot.
  • worker:<name> — one named session. Use for the most sensitive rules, where you want exactly one agent to have the permission and no others.

Scoping to worker is also useful when you are testing a new rule — apply it to one agent overnight, review the usage log in the morning, then expand scope if the behavior looks correct.

Limits and Caps

Two structured cap fields protect against a rule firing more than intended:

  • max_per_day — the rule fires at most N times in any rolling 24-hour window. When the cap is reached, the next matching request surfaces to you as normal. This prevents an agent that gets into a loop from invoking the same rule 200 times in one run.
  • max_amount_usd — for budget-category rules, the rule will not fire if the agent's request names a dollar amount above this cap. The amount is parsed from the escalation text. Use this for rules that authorize spending: "send up to $5/month in transactional email" becomes a concrete enforcement boundary rather than just a note in the limits field.

The require_terms field is a precondition: a comma-separated list of words or phrases, at least one of which must appear in the agent's request text before the rule fires. If you set require_terms = "test suite,linter,pytest", the rule will only fire for requests that mention one of those terms. Requests that technically fall in the same category but do not match will surface for your review.

Monitoring the Approval Feed

Every invocation of a standing approval is logged in the usage feed, accessible at Settings › Approvals › Usage. Each entry shows:

  • The timestamp and which session asked
  • The full text of the agent's request
  • Which rule fired (or "cap reached" if the rule was exhausted)
  • Whether the rule actually answered the request or the cap prevented it

After an overnight run, review the usage feed before the morning review of agent output. If a rule fired 40 times in one session, that agent was looping on something — investigate the session output to understand why. If a rule never fired, either the agents did not encounter that category, or the require_terms filter was too narrow.

The usage feed is also the right place to catch a rule that is scoped too broadly. If you see unexpected sessions invoking a rule you intended for a specific worker, narrow the scope.

Standing Approvals vs. --yolo

Claude Code's --dangerously-skip-permissions flag (often called --yolo mode) grants unlimited permission to all actions with no tracking and no caps. Standing approvals are the bounded alternative:

Standing approvals --yolo / --dangerously-skip-permissions
Scope Defined categories only Everything
Uncovered requests Surface to you Auto-approved
Caps Per-day limits, dollar caps None
Audit trail Full usage feed None
Scope control Global, group, or per-worker Per-session flag
External escalations Covered by amux alert rules Not routed through amux

Use --yolo for short, well-understood, low-stakes sessions in an isolated environment where you have reviewed the code and trust the task scope. Use standing approvals for long overnight runs, mixed-trust fleets, or any run where you want accountability and a cap on runaway behavior.

Recipes for Common Use Cases

Recipe 1: Safe overnight feature development

Three rules cover most feature-development overnight runs without exposing sensitive surfaces:

# Rule 1: Tests and linters
Title:    Run tests and linters
Category: access
Allowed:  Agent may run the test suite and all configured linters.
max_per_day: 20
Scope:    global

# Rule 2: Create branches and commits
Title:    Git operations (branch, commit, push to feature branch)
Category: access
Allowed:  Agent may create branches, commit, and push to non-main branches.
Limits:   Do not push to main. Do not force-push.
max_per_day: 30
Scope:    global

# Rule 3: Read internal config
Title:    Read configuration files
Category: access
Allowed:  Agent may read .env.example, config/, and docs/.
Limits:   Read-only. Do not write to these paths.
max_per_day: 50
Scope:    global

Recipe 2: Outbound email (marketing agent)

A dedicated session that sends transactional emails from a CRM-triggered queue:

Title:    Send transactional email (from queue)
Category: customer_outbound
Allowed:  Agent may send transactional emails to addresses in the active queue.
Limits:   Plain-text or HTML. No attachments over 5MB. One email per record.
require_terms: transactional,queue,crm
max_per_day: 200
max_amount_usd: 5.00
Scope:    worker:email-sender

Recipe 3: Read-only production data access (diagnostics agent)

Title:    Read production DB (diagnostics, read-only)
Category: prod_data
Allowed:  Agent may run SELECT queries on the production database for diagnostic purposes.
Limits:   SELECT only. No INSERT, UPDATE, DELETE, or DDL. Queries must be under 10s.
require_terms: SELECT,diagnostic,read-only
max_per_day: 10
Scope:    worker:prod-diagnostics

Frequently Asked Questions

What are AI agent standing approvals?

Standing approvals are pre-defined permission rules you set once in the amux dashboard. When an AI coding agent hits a request that matches a rule, amux answers it automatically. Requests that do not match any rule still surface to you. This lets overnight and unattended runs proceed without hanging on every permission prompt, while preserving your control over the requests that genuinely need a judgment call.

How do standing approvals differ from --yolo mode?

The --dangerously-skip-permissions flag grants unlimited permission to all actions with no tracking and no caps. Standing approvals are categorical and bounded: you specify exactly which categories are pre-approved, set per-day limits, dollar caps, and scope them to specific workers. Requests outside your defined rules still surface to you rather than being auto-approved.

What categories of actions can I pre-approve?

Six categories: access (file, network, service), credential (API keys, secrets), budget (spending, paid APIs), decision (approach, scope), prod_data (production data), and customer_outbound (emails, messages). Each is treated separately — you can pre-approve access globally without touching customer_outbound.

Can I limit how often a standing approval fires?

Yes. Set max_per_day on any rule. Once the cap is spent in a rolling 24-hour window, the rule stops firing and subsequent matching requests surface to you. For budget rules, set max_amount_usd to add a dollar-amount guard on top of the per-day cap.

Do standing approvals work with Codex and Gemini CLI?

Yes. Standing approvals work with any agent that routes escalations through amux's alert or needsyou channels: Claude Code, OpenAI Codex CLI, Antigravity CLI (formerly Gemini CLI), and any custom agent that calls the amux alert API.

Can I scope a standing approval to one agent?

Yes. Set scope to worker:<session-name> to limit the rule to a single named session. This is the right approach for the most sensitive rules, where you want exactly one agent to have a permission and no others.
