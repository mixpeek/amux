AI Agent Memory Management: How Agents Remember Things Between Sessions

AI models have no built-in persistent memory — each session starts fresh. What looks like memory is always files: the agent reads context at startup, appends discoveries mid-session, and leaves structured notes for its next session to find. This guide covers every memory layer available to coding agents in 2026, from basic CLAUDE.md to amux's 4-type shared memory system. Published August 2026.

The short answer: AI agents "remember" by reading and writing files. The primary surfaces are CLAUDE.md (project context loaded at every session start), memory files (typed notes about users, decisions, and references), and skill files (reusable how-tos the agent loads on demand). With amux, a team of parallel agents shares a memory scope — a discovery by one agent is available to every peer without manual handoff.

How Agent Memory Actually Works

There is no magic here. A language model processes a context window — a block of tokens it can see right now — and generates output. When the session ends, the context is gone. Next session: fresh context, no memory of what happened before.

What we call "agent memory" is the system of files the agent reads at session start and writes during the session:

  • Read at startup: CLAUDE.md files (project context), memory index files (what has been remembered), skill files (how to do recurring tasks)
  • Read on demand: Individual memory files (retrieved by the agent when relevant), code files, documentation
  • Written mid-session: New memory files, updated CLAUDE.md, skill files, task notes
  • Implicit memory: The codebase itself — a function written yesterday is visible today without any memory system; git history is a complete log of what happened

The practical implication: everything an agent needs to remember must exist as a readable artifact. If it only happened in a conversation, it is gone when the session ends.

CLAUDE.md — The Foundation Layer

CLAUDE.md is the most important memory surface for Claude Code agents. It is a Markdown file placed in a directory root — Claude Code reads it automatically at every session start, before any user message. It is the agent's briefing document: what project is this, what are the rules, what does the agent need to know right now.

What belongs in CLAUDE.md
  • Project overview: one paragraph — what this repo does, who uses it, main tech stack
  • Standing rules: don't mock the database, never git add -A, commit after every task
  • Non-obvious conventions: why a specific pattern is used, workarounds for known bugs
  • Deploy process: how to build, test, deploy — especially non-standard steps
  • Known gotchas: things that trip up new sessions ("the port is 8824, not 8822")
  • Links to deeper resources: pointers to longer docs the agent can read on demand

CLAUDE.md files nest. A monorepo can have a root CLAUDE.md for global rules plus per-package CLAUDE.md files that add context for that subtree. Claude Code loads every CLAUDE.md from the root to the current working directory — closer ones take precedence.

PUT IN CLAUDE.md

  • Coding conventions the agent must always follow
  • Non-obvious architecture decisions
  • Deploy steps and environment setup
  • Known bugs and their workarounds
  • Permission rules (what to ask before doing)

KEEP OUT OF CLAUDE.md

  • API keys and credentials (use amux Connectors tab)
  • Current sprint tasks or in-flight work
  • Step-by-step how-tos for common ops (use skills files)
  • Every past decision (use git history)
  • Anything that changes more than weekly

The 4 Memory Types

amux's memory system extends CLAUDE.md with typed files for agent-learned knowledge. Each file lives in ~/.claude/projects/<project>/memory/ and has YAML frontmatter declaring its name, description, and type. A MEMORY.md index lists all files — the agent loads the index each session and reads individual files when relevant.

user User memories

Who the user is, their role, expertise level, preferences, and how they like to collaborate. Lets the agent tailor explanations and avoid repeating background context every session.

Example: "User is a senior Go engineer new to the React frontend — frame frontend explanations in terms of backend analogues."

feedback Feedback memories

Corrections and confirmations: what to avoid, what approach worked. The agent writes these when the user corrects its behavior or validates an unusual choice. Prevents the same mistakes from happening twice.

Example: "Don't mock the database in tests — the team was burned when mocked tests passed but a prod migration failed."

project Project memories

Ongoing work, goals, decisions, blockers, and the reasoning behind them. Short shelf-life — always convert relative dates to absolute dates so the memory stays interpretable after time passes.

Example: "Merge freeze begins 2026-09-01 for mobile release cut. Flag any non-critical PR work after that date."

reference Reference memories

Pointers to external systems: which Linear project tracks bugs, which Slack channel holds customer feedback, which Grafana dashboard is the oncall view. Points the agent at live data without encoding the data itself.

Example: "Pipeline bugs are tracked in Linear project INGEST. Grafana oncall dashboard: grafana.internal/d/api-latency."

Memory files use frontmatter so the agent can assess relevance from the MEMORY.md index without reading every file:

---
name: feedback-no-database-mocks
description: Integration tests must use real DB — mock/prod divergence burned the team in Q3
metadata:
  type: feedback
---

Do not mock the database in tests.

**Why:** Mock tests passed on a migration that broke prod in Q3 2025.
**How to apply:** Always use the integration test suite against a real database, never a mock.

Setting Up Agent Memory (5 Steps)

  1. Start with CLAUDE.md. Create CLAUDE.md at your repo root. Include the project overview, standing rules, deploy process, and any non-obvious conventions. Keep it under 300 lines — everything beyond that should be in skills or memory files.
  2. Set up the memory directory. Create ~/.claude/projects/<project>/memory/ and add a minimal MEMORY.md index. amux auto-discovers this directory if you use it as your Claude Code client. Raw Claude Code users can reference it via a pointer in CLAUDE.md: "Project memory lives in ~/.claude/projects/this-repo/memory/ — read MEMORY.md for an index of what's been remembered."
  3. Instruct your agent to write memory files. Add to CLAUDE.md: "When you learn something worth preserving across sessions (a user preference, a project decision, a useful reference), write it as a typed memory file in ~/.claude/projects/this-repo/memory/ and update MEMORY.md." Without explicit instruction, agents won't write memory files unprompted.
  4. Set up group memory for parallel agents. If you run multiple agents with amux, assign them to the same group. amux injects group-scoped memory alongside session-scoped memory — a finding from one agent is available to every peer in the next session without any coordination step.
  5. Verify memory is being written. Run git log ~/.claude/projects/this-repo/memory/ to confirm files are being created. Ask a fresh session to recall something you told a previous session — if it can't, the memory wasn't written or the MEMORY.md index wasn't updated.

Shared Memory Across an Agent Team

Running a single agent is straightforward. Running 10–50 parallel agents — each working on different tasks — creates a coordination problem: what one agent discovers, another needs. Without shared memory, agents repeat each other's research, make contradictory decisions, and lack the project context their peers have already built up.

amux solves this at the group level. Agents assigned to the same group share:

  • Group memory files: Written by any agent, readable by all — a feedback memory written by agent A is available to agent B on its next session start
  • Board state: The shared kanban board shows every agent's current and completed work — atomic claiming prevents two agents from picking up the same task
  • Environment scope: API credentials set at the group scope (via Connectors tab) are injected into every agent's environment — no per-agent credential setup
  • Steering messages: A user or another agent can send a message to a specific agent or broadcast to a group — delivered at the agent's next turn boundary without interrupting mid-task
Example: overnight research team

10 agents run overnight, each investigating a different API integration. Agent 3 discovers that API X requires a specific auth header that isn't in the docs. It writes a project memory file: "API X requires X-Custom-Auth header — not documented, found in their GitHub issues." All 9 other agents read this on their next session and stop wasting time debugging the same undocumented behavior.

Without shared memory: each agent discovers the same issue independently, spends 20-30 minutes debugging, writes the same workaround 10 times. With shared memory: one discovery propagates to all peers within one session boundary.

Frequently Asked Questions

How do AI agents remember things between sessions?

AI models have no built-in persistent memory — each session starts fresh. Practical memory is implemented through files the agent reads at session start: CLAUDE.md (project conventions and standing rules), memory files (discovered facts about the user, project, or codebase), and external tools like databases or knowledge bases. When an agent "remembers" something, it has either written it to a file that future sessions read, or it was encoded in the model's training data.

What is CLAUDE.md and why does it matter?

CLAUDE.md is a Markdown file that Claude Code reads automatically at the start of every session. It gives the agent project context, coding conventions, standing rules, and any knowledge it needs before seeing user input. It functions as long-term project memory: tech stack, deploy process, code style, known bugs, and architecture decisions. Multiple CLAUDE.md files in nested directories let you scope memory to specific parts of a monorepo — closer ones take precedence.

What are the 4 types of amux memory?

User (who the user is, preferences, expertise level), Feedback (corrections and confirmed approaches — prevents repeating mistakes), Project (ongoing work, decisions, and their reasoning), and Reference (pointers to external systems: Linear project, Slack channel, Grafana dashboard). Each is a separate file with frontmatter so the agent can assess relevance from the index without loading everything.

How does shared memory work with parallel agents?

In amux, agents in the same group share a memory scope. A memory file written by one agent is readable by every peer in the group on their next session start. This eliminates manual handoff: if agent A discovers a non-obvious constraint, it writes a memory file, and agent B picks it up without any coordination. Especially valuable for overnight tasks where different agents work on related parts of the codebase.

What should NOT go in CLAUDE.md?

CLAUDE.md is loaded into every session context — keep it under ~300 lines. Avoid: credentials (use amux Connectors tab instead — injected as env vars, never in files), frequently-changing state (current sprint, who's on call), step-by-step how-tos (use skills files), and every past decision (git history covers that). CLAUDE.md is the briefing document, not the project log.

Can an AI agent update its own memory?

Yes. Claude Code can write files, including memory files. In amux's system, agents are explicitly instructed to write memory files when they learn something worth preserving. The agent writes the file, updates the MEMORY.md index, and the information is available to every future session. This is distinct from the model's weights (which never change) — the "memory" is just structured files that the agent reads at startup.
