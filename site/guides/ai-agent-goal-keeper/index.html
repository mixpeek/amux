AI Agent Goal Keeper

Set a goal for your Claude Code session, choose a check interval, and amux steers the agent back on track whenever it drifts — automatically, without waking you up.

Published October 2026

An AI coding agent that starts on the right task can still end up somewhere else by hour three. It finds a bug adjacent to the one it was fixing and pursues it. It adds abstractions that were not requested. It declares done before finishing edge cases. On overnight runs, no one is watching — and by the time you check in the morning, the agent may have produced something useful but not what you asked for.

The amux goal keeper solves this by inserting a goal check at regular intervals. You write a goal string that describes the specific outcome you expect, set how often to check (every N turns), and amux asks the agent whether the current work still aligns. When it does not, amux sends a re-focus prompt and logs the drift. The agent continues; the check fires again at the next interval.

Why agents drift

There are four common patterns:

Drift pattern What happens How goal keeper helps
Scope creep Agent encounters a related issue and fixes it unprompted, spending time outside the task boundary Re-focus prompt names the original goal and asks the agent to defer the unrelated issue
Rabbit hole Agent descends into debugging a subtask without making progress on the parent task Check-in forces a progress report; if it shows no progress toward the goal, amux escalates
Premature done Agent marks work done before the acceptance criterion is met Goal string includes the criterion; agent must confirm it is satisfied to pass the check
Context loss Context compaction removes the original task framing; agent restarts in a vague direction Goal string is re-injected at every check, not just at the start

Setting up the goal keeper

Three things to configure: the goal string, the check interval, and whether to continue automatically when the goal is met.

Writing a good goal string

The goal string has two parts: what to produce, and how to verify it. Both must be specific.

Good goal string: Migrate all raw SQL queries in server/db/ to use the ORM's query builder. The test suite must pass. No changes outside server/db/ except imports.

Weak goal string: Improve the database layer.

The weak version cannot produce a useful self-assessment. The agent has no basis for "am I done?" A good goal string lets the agent answer yes or no unambiguously.

Setting the check interval

The interval is measured in completed turns — one agent response counts as one turn. Guidance by task type:

Task type Recommended interval Reason
Mechanical refactor (rename, format, migrate) Every 20 turns Low drift risk; frequent checks add interruptions without value
Feature implementation Every 10 turns (default) Balanced; catches scope creep before too much time is lost
Complex debugging or architecture Every 5 turns Higher drift risk; tighter checks keep the agent from going deep on a wrong path
Research or exploration Disable goal keeper Exploration benefits from following tangents; goal keeper would fight the task

Using the CLI

Set a goal from inside a session with the /goal slash command:

/goal Migrate all SQL queries in server/db/ to use parameterized statements. Tests must pass. No changes outside server/db/.

Or set the goal at startup via the environment:

AMUX_GOAL="Migrate SQL queries in server/db/ to parameterized statements. Tests must pass." amux start myproject

To disable goal keeper continuation for a worker without removing the goal, set AMUX_GOAL_CONTINUE=0.

What a goal check looks like

At the check interval, amux sends a structured prompt to the agent. The agent responds with a brief self-assessment. amux reads the response and decides whether to send a re-focus prompt.

Example check prompt (sent by amux):

Goal check — turn 10/10.

Your goal: Migrate all SQL queries in server/db/ to use parameterized statements. Tests must pass. No changes outside server/db/.

Current status: are you still working toward this goal? Report in one sentence. If you have drifted, say so explicitly.

If the agent's response signals drift or uncertainty, amux follows up:

Re-focus: return to the original goal before continuing. Defer or note unrelated issues rather than acting on them. Resume: migrate all SQL queries in server/db/ to parameterized statements.

The goal check and any re-focus prompt are logged in the session peek view. You can read the full history when the run completes.

Goal keeper vs pinned notes vs standing approvals

Mechanism What it does Best for
Goal keeper Actively checks alignment with a specific goal at intervals; re-prompts on drift Long task runs with a clear deliverable and acceptance criterion
Pinned notes Passively injects standing text at every context reload Persistent constraints and conventions that always apply (do not commit to main, use TypeScript)
Standing approvals Pre-approves categories of actions so the agent does not pause to ask Predictable routine decisions the agent should handle without human input

These three work well together. A practical combination for an overnight run: pinned notes for style and commit conventions, standing approvals for package installs and minor file deletes, and the goal keeper for the task's specific deliverable.

Combining goal keeper with workspace isolation

Set AMUX_WORKSPACE_ISOLATION=1 alongside a goal to give the agent both a clean working context and a steering signal:

AMUX_WORKSPACE_ISOLATION=1 \
AMUX_GOAL="Add rate-limiting middleware to all /api/v2/ routes. Unit tests must cover the middleware. No changes outside server/middleware/ and server/routes/v2/." \
amux start myproject

Workspace isolation prevents shared-checkout conflicts with other agents. The goal keeper prevents the agent from drifting into unrelated parts of the codebase inside its own isolated worktree.

Frequently asked questions

What is the amux goal keeper?

The goal keeper is an amux feature that periodically asks your AI agent whether it is still working toward the goal you set. You write a goal string, choose a check interval in turns, and amux inserts a progress check at that cadence. When the agent's response shows drift, amux sends a re-focus prompt and logs the event.

Why do AI agents drift off task?

Scope creep, rabbit holes, premature done declarations, and context loss after compaction. Any of these can cause an agent that started correctly to produce something off-target by the time you check in. The goal keeper catches each class of drift actively rather than waiting for you to notice the output.

What is a good goal string to write?

Name the deliverable, the scope, and the acceptance criterion. "Migrate all Postgres queries in server/db/ to parameterized statements; tests must pass" is good. "Improve the database layer" is not. The agent needs a verifiable test to answer "am I done?" — vague strings produce vague self-assessments.

How is the goal keeper different from pinned notes?

Pinned notes inject static text passively at every context reload. The goal keeper actively asks the agent to confirm alignment and sends a re-focus prompt when it does not. Use pinned notes for standing constraints. Use the goal keeper for the specific outcome of the current task.

Can I set a goal from the command line?

Yes. Use the Claude Code /goal command inside the session, or set the AMUX_GOAL environment variable for the worker. The CLI approach is useful for scripted deployments where you queue a task programmatically.

Does the goal keeper interrupt the agent mid-thought?

No. amux waits for a turn boundary before inserting the check. The agent finishes its current response first; the goal check arrives as the next input after the configured number of completed turns.

What happens when the goal keeper detects drift?

amux sends a structured re-focus prompt that includes the original goal, a summary of the detected drift, and an instruction to return to goal before continuing. Subsequent checks continue on the same cadence. The full drift history is readable in the session peek view.

Can I pause or disable the goal keeper mid-run?

Yes. Toggle it off from the session card in the dashboard, or set AMUX_GOAL_CONTINUE=0. The ongoing turn completes; no further checks are sent. You can re-enable with the same or a revised goal.

Does the goal keeper work with Codex CLI and Gemini CLI?

Yes. Goal keeper inserts checks at the harness level using amux's session messaging. Any session amux manages accepts goal checks — Claude Code, Codex CLI, Gemini CLI, or a custom agent.

How do I use the goal keeper with workspace isolation?

Set both flags. AMUX_WORKSPACE_ISOLATION=1 gives the agent its own git worktree; the goal string keeps it working within the right scope inside that worktree. They address different failure modes and combine without conflict.
