Why AI Agents Fail (and Why It's Not the Model)

When an AI coding agent produces wrong output, crashes overnight, or silently stops making progress, the instinct is to blame the model — write a better prompt, switch to a smarter model, add more instructions. This is almost always the wrong diagnosis.

AI coding agent failures trace to context surface failures, not model limitations:

  • The agent used the wrong API because the right API was not in its context (CLAUDE.md or skill gap)
  • The agent violated a constraint that was soft (CLAUDE.md) instead of hard (hook)
  • The agent's context filled with grep noise and it lost track of its original instructions (subagent opportunity)
  • The agent repeated a mistake because the correction was never saved to memory
  • The agent built the wrong thing because the spec was ambiguous

The same failure mode persists across model upgrades because the model was never the problem. Fix the context surface and any model — current or future — produces the right output.

First Triage: Read the Status Badge

Before opening logs, read the session status badge in the amux dashboard. Each status points to a different root cause:

The Activity Log: Full Request/Response Payloads

The Activity log is the single most powerful debugging tool for AI coding agents. It records every tool call an agent made — with the exact request payload (what the agent asked for) and response payload (what it received). This makes debugging concrete: instead of guessing which tool output polluted the context, you read the exact bytes.

Accessing the Activity log

Dashboard: Sessions tab → click session name → Activity tab. Each entry shows the tool name, timestamp, and collapsed request/response. Click any entry to expand the full payload.

API:

# List recent activity for a session
curl -sk "$AMUX_URL/api/sessions/my-agent/activity?limit=100"

# Filter to a specific tool type
curl -sk "$AMUX_URL/api/sessions/my-agent/activity?tool=Bash&limit=50"

Searching for the failure point

Use the Activity log search box to find the exact turn where things went wrong:

  • Wrong output: search for the wrong value — find the tool response that introduced it
  • Wrong file read: search for the file path to find when and why the agent read it
  • Failed command: search for the command exit code or error string
  • Context bloat: look for tool responses that returned more than 1KB — these are subagent candidates

Reading tool payloads

# Example Activity log entry (API response)
{
  "id": "act_001",
  "tool": "Bash",
  "timestamp": "2026-08-04T07:32:15Z",
  "request": {
    "command": "grep -r 'authenticate' ./src/"
  },
  "response": {
    "stdout": "src/auth/middleware.js:14:  authenticate(req)...\n...45 more lines...",
    "exit_code": 0,
    "tokens": 1847
  }
}

In this example, a grep returned 45 lines when the agent only needed the function signature. That 1,847 tokens of noise pushed later instructions out of the attention window — a textbook case for a subagent. The Activity log surfaces this cost; without it, you are guessing.

Stalled Sessions: Detection and Recovery

A stalled agent is one that has stopped producing output during an active task. This is different from an idle agent that finished its task and is waiting for new instructions. The stalled badge (⚠) appears in the dashboard when amux detects an agent has been silent for longer than expected during active work.

Common stall causes and fixes

Stall cause How to detect Recovery Prevention
Resume dialog Peek shows "Would you like to resume?" Send "1" from the dashboard or your phone Start Claude Code with --continue, or clear .claude/ history before the run
Tool approval block Peek shows "(y/n)" or permission prompt Send "yes" or enable YOLO mode for the project Register with --yolo for trusted repos
Thinking block corruption Activity log last entry shows malformed JSON Restart the session from the dashboard Keep context lean to reduce corruption probability
Context window full Cost tab shows 180K+ tokens; Peek shows compaction notice Claude Code compacts its own context; or send /compact Lower the compaction threshold in amux so compaction happens earlier
Blocked on a dependency Activity log shows agent asking about a missing resource Unblock via board (close the blocking card) or steer the agent Use explicit depends_on on board cards before starting

What amux recovers from, and what it flags

amux handles a few failure modes on its own and makes the rest visible so you can act:

  1. Usage limits: delivery is held and the agent resumes at the provider's reset time
  2. Context: Claude Code compacts its own context; amux lets you set the compaction threshold
  3. Stalled work: board work that stops moving and stuck orchestrators are flagged, and an owner alert fires

amux does not answer prompts such as the resume dialog, and restarting a crashed agent process is not built into the server. On macOS, the optional scripts/tmux-watchdog.sh (not installed by default) restarts crashed Claude Code workers.

# Recovery settings in ~/.amux/server.env
AMUX_RATE_LIMIT_ACTION=wait   # hold delivery at a usage limit, resume at reset (or: off)
AMUX_AUTO_RESUME=1            # resume at the provider reset after a usage limit (default on)
AMUX_GOAL_STALL_H=2           # flag board work that has not moved in 2 hours

See the Recovery configuration guide for the full setup.

Diagnosing Context Surface Failures

The most important mental shift in debugging AI agents: the fix is almost never "write a better prompt." It is almost always "put the right information on the right context surface."

Symptom Root cause Fix Surface
Agent uses wrong build command Missing from project rules Add to CLAUDE.md CLAUDE.md
Agent ignores style rule late in session CLAUDE.md pushed out by context growth Trim CLAUDE.md; move rule to hook CLAUDE.md / Hook
Agent pushes to main despite instruction Soft rule (70% compliance) violated the 30% Move to PreToolUse hook (100% enforcement) Hook
Agent doesn't know how to deploy Deploy docs not available in context Create a deploy skill Skill
Context fills during codebase exploration Wide tool calls return too much data Create an explorer subagent; return summary only Subagent
Agent repeats corrected mistake next session Correction not persisted across sessions Save feedback to agent memory or notes Memory
Agent builds wrong feature despite clear prompt Ambiguous requirements Write a spec with acceptance criteria Spec

The debugging loop

  1. Read the Activity log for the turn where the output diverged from expectation
  2. Identify which context surface was missing, wrong, or soft when it needed to be hard
  3. Fix the surface (CLAUDE.md, hook, skill, subagent, memory, or spec)
  4. Re-run the same task with a fresh agent to confirm the fix
  5. If it recurs, add a watch card to catch it next time

Watch Cards: Continuous Monitoring

Debugging after the fact is expensive. Watch cards let you define monitoring conditions that fire in real time — before a failure escalates into a crashed overnight run or a half-finished pull request.

A watch card is a board item of type watch with a trigger condition. amux monitors the condition on a schedule and fires a steering message to the relevant session when the trigger is met.

# Create a watch card via API
curl -sk -X POST -H 'Content-Type: application/json' \
  -H "X-Amux-Session: $AMUX_SESSION" \
  -d '{
    "title": "Watch: payments-agent context > 80%",
    "type": "watch",
    "session": "payments-agent",
    "trigger": "context_percent > 80",
    "action": "steer: context is filling — consider compacting or starting a fresh session"
  }' \
  $AMUX_URL/api/board

# View armed watches (currently monitoring)
curl -sk "$AMUX_URL/api/board?is=armed" | python3 -c \
  "import json,sys; [print(i['title'], i.get('status')) for i in json.load(sys.stdin)]"

Common watch patterns

  • Context size threshold: alert when any session exceeds 80% of its context window
  • Stall duration: alert when a session has been idle for 10+ minutes during an active task
  • Error pattern: watch session output for a specific error string and steer when found
  • Board state: watch for a card stuck in "doing" for more than N hours without a status update

Armed watches are visible in the dashboard under the Board tab with is:armed filter. Stale watches (armed but not triggered recently) show the STALE badge so you can review whether the condition is still relevant.

Debugging Overnight Failures

Overnight runs are the highest-value and highest-risk context engineering scenario. Agents run unattended for 6–8 hours, and a single stall at hour 2 means 6 hours of wasted compute. The debugging workflow for overnight failures follows a consistent pattern:

Morning review workflow

  1. Check the Trends view (Review tab) for any sessions with zero activity in the last 8 hours
  2. Check the stalled badge count in the Fleet section — any non-zero count needs attention
  3. For each stalled session: open Activity log, look at the last 5 tool calls, identify where it stopped
  4. Check the board for tasks stuck in "doing" with a session that is now idle — the task may need to be reclaimed

What the owner digest tells you

If you configured amux's push+SMS owner digest (Settings → Notifications), you receive a morning summary of everything that needs human attention: stalled sessions, board cards waiting for input, tasks completed and ready for verification. This is the overnight debugging layer that does not require checking the dashboard manually.

# Configure the owner digest in ~/.amux/server.env
OWNER_DIGEST_SCHEDULE="daily at 8am"
OWNER_DIGEST_CHANNELS="push,sms"    # push = in-app, sms = iMessage

The digest lists only what requires YOUR action — it does not summarize activity you do not need to know about. See the overnight AI coding guide for the full morning review workflow.

FAQ

Why is my AI coding agent producing wrong output?

Wrong output almost always traces to a context surface failure. The most common causes: missing CLAUDE.md rule, soft rule that should be a hook, reference doc not available as a skill, context window filled with noise (subagent opportunity), or ambiguous task spec. Read the Activity log to see exactly what the agent saw when it went wrong, then fix the surface — not the prompt.

How do I read AI agent logs in amux?

Sessions tab → click session name → Activity tab. Every tool call is listed with its full request and response payload. Use the search box to find specific strings. The API endpoint is GET /api/sessions/{name}/activity. Payloads are stored in the SQLite-backed amux.db and survive server restarts.

What does the stalled badge mean?

The stalled badge (⚠) appears when an agent has been idle longer than expected during an active task — typically after 5+ minutes of silence. Most common causes: resume dialog, tool-approval block, thinking block corruption, or context window full. amux flags the stall and alerts you; it does not answer prompts or restart the session for you.

How do I debug an agent that crashed overnight?

Check the session's Activity log for the last tool call before the crash. Open Peek to see the terminal state. Common overnight failures: (1) context window filled and the resume dialog appeared but no one answered it, (2) thinking block corruption from a malformed tool response, (3) rate limit menu left unanswered. Start Claude Code with --continue or clear the project history to prevent (1). For (2), restart the session; restarting a crashed agent is not built into the amux server, though on macOS the optional scripts/tmux-watchdog.sh (not installed by default) restarts crashed Claude Code workers. Set AMUX_RATE_LIMIT_ACTION=wait to handle (3) without human intervention.

How do I monitor an agent to catch failures as they happen?

Use amux watch cards. Create a board item with type: watch and a trigger condition — a string to detect in output, a status to watch for, or a context size threshold. When triggered, amux fires a steering message to the relevant session. For overnight monitoring, the push+SMS owner digest summarizes everything waiting for human attention at your configured morning time.

Why does my Claude Code agent ignore CLAUDE.md instructions?

CLAUDE.md compliance is ~70%. For style preferences, that's acceptable. For safety-critical rules, 70% means a guaranteed incident eventually. Solution: move the rule to a PreToolUse hook (100% enforcement). Hooks run outside the model — the agent cannot choose to ignore them.

What is the difference between Activity log and session output (Peek)?

Peek shows the rendered terminal view — what you'd see watching the agent in real time. The Activity log shows the API-level record: every tool call, exact arguments, exact response, in order. Peek = situational awareness. Activity log = debugging when something went wrong.

How do I prevent the same mistake from recurring?

Fix the context surface: add the missing rule to CLAUDE.md; move the violated rule to a hook; write the skill for the knowledge that was missing; save the correction to agent memory. The goal is that the next agent running the same task sees the right context from the start. A watch card monitors for recurrence in case the fix was incomplete.
