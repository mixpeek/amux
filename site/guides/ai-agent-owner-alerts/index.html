AI Agent Owner Alerts: Push, Email, and iMessage

How amux owner alerts work

amux ships a built-in fire-alarm channel for agent-to-owner communication. When an agent calls amux alert "message" "reason", the server delivers the alert to every configured channel simultaneously: push notification to your phone, email to your inbox, and iMessage on Apple devices. The whole delivery takes under 5 seconds.

This is different from checking the dashboard. The dashboard shows you status when you look; owner alerts reach you when you are not looking. A sleeping developer, a developer in a meeting, a developer who forgot to check in at 2am: owner alerts handle all three cases without any polling.

The alert command takes two arguments: a human-readable message and a short reason. The server logs both, timestamps the delivery, and sends them together to all channels. From a terminal or from inside an agent's CLAUDE.md instructions:

amux alert "Blocked on auth migration -- need your call" "30+ min blocker"
amux alert "All tasks done -- queue empty, ready for more" "queue empty"
amux alert "Found unexpected changes in payments/ -- stopping" "scope violation"

Setup: server.env and push notifications

Email configuration

Add the following to ~/.amux/server.env:

AMUX_OWNER_EMAIL=you@example.com
AMUX_ALERT_EMAIL_FROM=alerts@yourdomain.com   # optional, defaults to a system sender

Restart the server to pick up the changes:

launchctl kickstart -k gui/$(id -u)/com.amux.server-rs

If you have a Gmail account connected via the amux Gmail API, alerts use that account for reliable delivery, threading, and signature. Otherwise, the server uses SMTP. Either way, one line in server.env is all that is needed.

Push notifications

Push notifications arrive on your phone even when the amux PWA is not open. To set them up:

  1. Open https://localhost:8824 (or your Tailscale address) in your phone's browser.
  2. Tap Share and choose Add to Home Screen.
  3. Open the installed app from your home screen.
  4. When the notification permission prompt appears, tap Allow.

On iOS, the permission prompt appears on first open of the installed PWA. On Android, it may appear before installation. Once enabled, push notifications fire through the service worker even when the screen is locked, delivering the same behavior as a native app.

For remote access (agent running on a cloud VM or a machine at the office), connect via Tailscale and install the PWA pointed at your Tailscale address instead of localhost.

iMessage

On Apple devices, push notifications can trigger iMessage delivery as well. When the amux PWA sends a push, iOS surfaces it as both a banner notification and, for configured accounts, an iMessage. No additional setup is required beyond the push permission above. A push that arrives while your phone is asleep will wake the display and sound, matching the urgency of a true fire alarm.

Verify setup immediately

After configuring, verify before you trust the channel with an overnight run:

amux alert "Test alert" "verifying setup"

Confirm the push notification arrives on your phone and an email lands in your inbox. If either fails, check the health invariant (next section) for a diagnosis.

Writing alert triggers in CLAUDE.md

The agent does not decide on its own when to alert you. You decide, once, in CLAUDE.md, and every agent on the fleet follows the same rules. This is deliberate: a well-calibrated alert policy means you get paged for real blockers, not for progress updates you would have seen in the morning review.

A good alert policy covers three cases:

1. Blockers that stall progress

# In CLAUDE.md
If you hit a problem you cannot resolve after 3 attempts, and the task cannot
proceed without a decision only the owner can make, run:
  amux alert "Blocked on [description] -- need your call" "30+ min blocker"
Then commit what you have, document the blocker in a comment, and stop.

2. Scope violations

# In CLAUDE.md
If completing the task requires modifying files in src/auth/, src/payments/,
or infrastructure/, do NOT modify those files. Instead run:
  amux alert "Task needs changes in [area] -- outside scope" "scope violation"
Then commit a note explaining what you found and stop.

3. Queue empty

# In CLAUDE.md
If you finish all tasks and the board has no more work queued for you, run:
  amux alert "All tasks done -- queue empty, ready for more" "queue empty"
Then wait without doing anything else.

What NOT to alert on

Agents that alert on routine progress quickly teach their owner to ignore the channel. Routine progress belongs on the board, not in an alert:

  • Completing a task: mark the board card done, not an alert
  • Starting a new task: no notification needed
  • Failing a test and retrying: routine, not a blocker
  • Asking a clarifying question that can wait: write a TODO comment and continue

The owner-alert channel should feel like a phone call at 3am: reserved for things that actually cannot wait.

Channel comparison: push vs email vs polling

Channel Delivery Works when Setup
Push notification Under 5 seconds Phone is on and connected (even locked) Install PWA, grant permission
iMessage (iOS) Under 10 seconds iPhone connected to internet; sounds even on silent Automatic with push on iOS
Email Under 30 seconds Any email client; no app needed AMUX_OWNER_EMAIL in server.env
Dashboard polling When you check You are already looking None, always on
amux board Immediate on write Morning review; board visible in dashboard None, used by agents automatically

amux alert fires push, iMessage, and email simultaneously. You do not choose one: you get all three on a single call, with a 60-second server-side dedup to prevent spam from a misconfigured agent.

Health invariant: verify before every overnight run

The most dangerous failure mode for owner alerts is a misconfigured channel that looks correct in server.env but silently drops alerts at runtime. amux has a continuous health check that prevents this.

Check it before every overnight run:

curl -sk $(amux url)/api/health/invariants | python3 -c "
import json, sys
d = json.load(sys.stdin)
for f in d.get('failures', []):
    print('FAIL:', f)
for p in d.get('passing', []):
    if 'alert' in p:
        print('PASS:', p)
"

Look for alert.channel_can_deliver in the passing list. If it appears in failures, the response includes a detail field explaining what is wrong and how to fix it. Common failure reasons:

  • AMUX_OWNER_EMAIL not set: add it to ~/.amux/server.env and restart
  • Email auth error: reconnect your Gmail account with GET /api/gmail/auth?account=you@example.com
  • Push subscription expired: re-open the PWA and refresh the notification permission

The invariant runs every 5 minutes automatically. If it starts failing between runs, the dashboard health indicator turns red and the failing invariant appears in the invariants tab. You do not have to check manually before every run; the dashboard shows you the state on your morning review.

Overnight runs: alerts in practice

Owner alerts become most valuable in overnight agent runs. When you queue tasks before bed and start 5-20 agents, you want to sleep through routine progress and wake up only if something genuinely needs you. Here is the combined setup:

Before starting an overnight run

  1. Verify the health invariant: alert.channel_can_deliver must be passing.
  2. Send a test alert and confirm delivery on push and email.
  3. Confirm each agent's CLAUDE.md has the three alert triggers: blocker, scope violation, queue empty.

During the overnight run

Your phone receives a push notification if any agent hits a blocker or a scope issue. For a well-decomposed task queue with good CLAUDE.md guardrails, you should see zero alerts on a typical overnight run: agents complete, queue empties, and you review in the morning.

A queue-empty alert means all tasks completed before your review time. This is a good signal: you can queue more before bed, or let the agents rest until morning.

A blocker alert at 2am means something genuinely needs you. Check the alert message, peek at the agent's output with amux peek SESSION-NAME from your phone, and either reply with a direction or leave it for the morning. The agent will wait.

Morning review

If you received no alerts overnight, open the amux dashboard and triage by board status. If you received alerts, start with those sessions before the routine review. See Running AI Coding Agents Overnight for the full morning review workflow.

FAQ

What is an AI agent owner alert?

An owner alert is a push notification and email delivered to the owner of an AI agent fleet when an agent needs human attention. In amux, the agent calls amux alert from inside its task. The server delivers the alert via push notification to the owner's phone and via email simultaneously, with iMessage on Apple devices.

What notification channels does amux support for agent alerts?

amux delivers owner alerts to three channels on a single amux alert call: push notifications via the PWA installed on your phone, email via Gmail API or configured SMTP, and iMessage on Apple devices when push notifications are enabled.

How do I set up email alerts for AI coding agents?

Add AMUX_OWNER_EMAIL=you@example.com to ~/.amux/server.env and restart the server. Optionally add AMUX_ALERT_EMAIL_FROM=alerts@yourdomain.com for a custom sender. Verify with GET /api/health/invariants: alert.channel_can_deliver must be in the passing list.

What should trigger an AI agent owner alert?

Three situations reliably warrant an alert: a blocker that will stall progress for more than 30 minutes, an unexpected error in a protected area (auth, payments, migrations), and a completed queue where the agent wants new work. Routine progress belongs on the board. Write the trigger conditions in CLAUDE.md so every agent on the fleet follows the same rules.

How do I verify that agent alerts are working?

Check GET /api/health/invariants and confirm alert.channel_can_deliver is passing. Then send a test: amux alert "Test" "pre-run check". Confirm push arrives on your phone and email lands in your inbox within 30 seconds. The invariant runs continuously; if it fails later, the dashboard marks it red.

Can I use polling instead of alerts to monitor AI agents?

Polling via the amux dashboard is good for checking status when you are already looking. Owner alerts handle the case where you are not looking. The two complement each other: polling gives you the state on demand; alerts reach you when something needs you without you asking.

How do I prevent agents from sending too many alerts?

Two mechanisms prevent alert spam. First, the server applies a 60-second dedup window: a second identical alert within 60 seconds of the first is dropped silently. Second, write tight trigger conditions in CLAUDE.md so agents only alert on genuine blockers. An agent that alerts on every progress step is a sign the CLAUDE.md triggers need narrowing.

Set up owner alerts in 5 minutes

amux ships push notifications, email, and iMessage alerts out of the box. Install amux, add one line to server.env, install the PWA on your phone, and your agents can page you from anywhere.

git clone https://github.com/mixpeek/amux && cd amux && ./install.sh

# In ~/.amux/server.env:
# AMUX_OWNER_EMAIL=you@example.com

# Test the channel:
amux alert "Setup complete" "first alert"
