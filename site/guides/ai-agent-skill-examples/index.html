AI Agent Skill Examples — Writing Invocations for amux Skills

Make your skills discoverable across the whole fleet with inferred and explicit examples. Updated October 2026.

Quick answer: amux skills can include an ## Examples section with concrete invocation phrases. amux surfaces these in the / command palette and expanded skill card. If you omit the section, amux infers examples from the skill body text. Explicit examples always take precedence over inferred ones.

Why skill examples matter

A skill without examples is a tool without a label. You know /review-pr exists, but does it review the staged diff or the current branch? Does it cover security issues or just logic bugs? Without examples, every invocation requires the user to either memorize the skill body or guess.

Skill examples solve discoverability. When you type / in any steering bar, amux shows each skill with its top examples inline. You see what the skill does before you invoke it.

The October 2026 update added two surfaces:

  • / dropdown — type / anywhere in the dashboard to open the command palette. Every skill lists its examples as clickable suggestions.
  • Expanded skill card — in the Skills tab, expand any skill to see all examples with clipboard copy buttons.

Writing explicit examples

Add an ## Examples section to the skill Markdown. Each - list item is one example:

---
name: review-pr
description: Review staged changes before committing
---

## Examples
- Review my staged changes for correctness
- Check this PR branch for breaking changes
- Run a security scan on my diff
- Review the changes in auth.ts for edge cases

## Steps
1. Run `git diff --cached` to see staged changes.
2. For each changed file: identify the intent, list edge cases not covered...

amux shows the first 5 examples in the dropdown (in order). Put the most common invocations first.

Example templates by skill type

Code review skills

## Examples
- Review my staged changes for correctness
- Check this diff for security issues (SQL injection, XSS, auth bypass)
- Run a breaking-change scan on my changes
- Review <filename> for edge cases I missed
- Check test coverage for my staged changes

Git workflow skills

## Examples
- Stage and commit my changes with a conventional message
- Create a commit for the auth refactor with a body
- Commit only the <scope> changes (not the lockfile)
- Push to origin and report the pipeline URL

Documentation skills

## Examples
- Write a changelog entry for my staged changes
- Update the README with the new <feature> I just added
- Generate API docs for the endpoints in <filename>
- Write a standup summary from today's commits

Deploy and CI skills

## Examples
- Run tests, build, and push to origin
- Check if CI is green for the current branch
- Deploy to staging and confirm the health check passes
- Roll back the last deploy if tests are failing

How amux infers examples automatically

If you don't write an ## Examples section, amux infers examples from the skill body. The inference pipeline:

  1. Scans for imperative sentences — sentences starting with action verbs (Run, Check, Review, Generate, Create, Write, List, Stage, Commit) are strong candidates.
  2. Extracts code block triggers — if the body says "Run git diff --cached", amux maps this to "Review staged changes" as an example.
  3. Reads step headers — numbered step headings like "Step 3: Review for security" become "Review changes for security issues".
  4. Deduplicates and ranks — inferred examples are deduplicated, then ranked by specificity. Generic phrases ("Do the thing") are dropped; specific ones ("Review staged changes for correctness") are kept.

Inferred examples appear after explicit ones and are capped at 5 total per skill. A skill with 3 explicit examples gets at most 2 inferred ones appended.

Tip: Run the skill once after saving to see what amux inferred. In the expanded skill card, inferred examples are labeled "(inferred)" so you can tell which are yours and which amux added.

Parameterized examples

Use angle brackets for dynamic parts of an invocation:

## Examples
- Review my changes in <filename> for edge cases
- Write a changelog entry for <feature>
- Deploy <service> to staging and run smoke tests
- Summarize commits since <date>

When a user selects a parameterized example from the dropdown, amux inserts it into the steering bar with the cursor positioned at the first <placeholder>. The user types the value and hits Enter.

Keep parameterized examples to one or two placeholders. More than two makes them harder to fill in at invocation time.

Frequently Asked Questions

What is a skill example in amux?

A skill example is a concrete invocation phrase that amux surfaces in the / command palette and in the expanded skill card. When you type / in any steering bar, amux shows each skill with its examples as one-click suggestions. Examples are either written explicitly in the skill's ## Examples section or inferred automatically by amux from the skill body text.

How does amux infer examples from the skill body?

amux scans the skill Markdown for imperative sentences, numbered step headers, and code block trigger descriptions. A /commit skill that says "Run git diff to see what changed" becomes an inferred example "Stage and commit changes." Inference runs every time the skill is saved. Explicit examples in ## Examples always take precedence; inferred ones fill remaining slots up to a total of 5.

Where do skill examples appear in the dashboard?

Two places: (1) the / dropdown — type / in any worker steering bar, Chat window, or board card input; each skill lists its examples as clickable suggestions; (2) the expanded skill card in the Skills tab, with clipboard copy buttons per example. Both surfaces shipped October 2026 (b4c191b2 + 2db6fd94).

What makes a good skill example?

A complete imperative sentence (8–12 words) that describes one specific use of the skill. "Review my staged changes for correctness" is good. "Review" is too vague. "Check all the things in the staged diff carefully before committing" is too long. Include the action verb, the scope, and the outcome when possible.

How many examples should a skill have?

Three to five. Too few and the skill seems limited; too many and the dropdown is cluttered. amux shows at most 5 examples per skill in the dropdown. If your ## Examples section has more than 5, amux shows the first 5 in order — so put the most common invocations first.

Can examples include placeholders for dynamic values?

Yes. Use angle brackets: Review my changes in <filename> for edge cases. When selected from the dropdown, the example is pre-filled in the steering bar with the cursor at the first placeholder. Use one or two placeholders per example — more makes the example harder to complete at invocation time.
