AI Agent Pinned Notes

Persistent standing instructions that survive context compaction, restarts, and session switches — so your agents keep the constraints you set, however long the run.

Published October 2026

Long-running AI agent sessions have a structural problem: the instructions you give at the start of a conversation gradually disappear as the context window fills and gets compacted. An agent that started the day knowing "do not commit directly to main" or "this module is owned by another worker" may have forgotten both by hour three.

Pinned notes in amux solve this. They are text blocks you attach to sessions, groups, or the entire fleet. The harness injects them at every context reload — after compaction, after a restart, after a rate-limit pause and resume — so the agent always has them in its active window.

The context window problem

Claude Code manages its own context window automatically. When a conversation grows large, it compacts earlier messages into a summary — preserving recent tool calls and code changes, but dropping older conversational turns. Your initial briefing is usually the first thing to go.

This works fine for self-contained tasks. It breaks down for long-running agents on tasks like:

  • Multi-day refactors where the architecture decision from day one needs to stay visible.
  • Overnight fleet runs where a constraint set before sleep must still be active in the morning.
  • Shared checkout work where the agent must know which files a peer session owns and should not touch.
  • Team coding standards that apply for the entire project's lifetime, not just the first hour.

A CLAUDE.md file in the repository handles some of this — Claude Code reads it at session startup. But it is read once, at launch. After a context compaction, CLAUDE.md is no longer in the active window unless the agent explicitly rereads the file. And re-reading a file costs a tool call and tokens on every compaction cycle.

Pinned notes are injected by the harness directly, at every reload, as a first-class system message — no tool call required, and the agent cannot accidentally overwrite them.

How pinned notes work

When amux detects a context reload event — compaction, restart, or resume after a pause — it prepends the session's pinned notes to the outgoing context injection. The agent receives them as a system-level briefing before its first tool call in the new context window.

Notes are stored in amux's SQLite database, encrypted at rest along with the rest of the agent data. They survive server restarts and do not require the session to be running to edit them.

Scoping: session, group, or global

ScopeReachesBest for
SessionOne specific workerTask-specific constraints, per-agent context, "this worker owns module X"
GroupAll workers in a named groupFeature-team coding standards, shared project context, group-level constraints
GlobalEvery session on this serverCompany-wide policies, universal safety rules, repo-wide "do not touch" lists

Notes at narrower scopes take precedence over broader ones. A session-level note on the same topic as a global note both appear — the harness does not deduplicate them. Keep global notes concise (under 100 words) since their token cost is paid on every session's every reload.

How to set up pinned notes

  1. Open the note editor. In the amux dashboard, click the Notes icon on any session card. For group or global notes, go to Settings and select Pinned Notes.
  2. Write the standing instruction. Enter the context you want the agent to see at every reload. Be specific and imperative: "Do not commit to main — open a PR instead" works better than "Remember to use PRs."
  3. Set the scope. Choose session, group, or global. When in doubt, start with session scope and promote to group or global once you have confirmed the note is working as intended.
  4. Verify the agent received it. Send the agent a message: "List your current pinned notes." It will quote them back, confirming they are in the active context window.
  5. Update when the constraint changes. Editing a note takes effect at the next context reload. Removing a note stops it from appearing — no session restart needed.

What to put in a pinned note

The most valuable pinned notes share three properties: they apply throughout a long run (not just at the start), they are easily forgotten after a compaction, and they are stable enough not to change mid-task.

Good candidatesPoor candidates
Architectural constraints: "primary key is UUID, not integer"Task prompts: "implement the login feature" (belongs in the initial prompt)
Ownership rules: "module X is owned by the infra worker — ask before editing"Volatile state: "the current PR is #482" (changes too fast)
Coding standards: "always run cargo test before committing"Secrets: "OPENAI_API_KEY=sk-…" (use the vault instead)
Safety rails: "do not push to main — open a PR"Long context: a 1,000-word style guide pasted verbatim (summarize the key rules instead)
Shared checkout warnings: "peer session amux-infra is editing src/api/auth.rs"One-off reminders: "this time, skip the lint step" (belongs in the current message)

Token cost of pinned notes

A pinned note is injected at every context reload, so its token count adds to every session's turn cost after a compaction. The overhead is small in absolute terms but compounds on long runs:

Note lengthApprox. tokensDaily cost (10 compactions/day, 10 sessions)
1 sentence (50 chars)~15 tokens<$0.01
1 paragraph (200 words)~260 tokens~$0.05–$0.15
500 words~650 tokens~$0.15–$0.40
2,000 words (long style guide)~2,600 tokens~$0.60–$1.60

The amux dashboard shows each note's token length in the editor so you can see the cost before saving. As a rule of thumb: keep session-scoped notes under 300 words, group notes under 150 words, and global notes under 100 words. Bullet points and explicit imperatives compact better than prose.

Pinned notes in multi-agent fleets

When running 10–50 agents in parallel from a shared codebase, pinned notes become a coordination tool as much as a memory tool. Common fleet patterns:

  • File ownership map. A global note lists which worker session owns which module. Workers reading this at every reload know which files to touch and which to leave for the owning session.
  • PR discipline. A global note enforces that all workers open PRs rather than pushing directly to main — even when YOLO mode would otherwise allow direct pushes.
  • Group-scoped quality gates. Workers in a "backend" group carry a note requiring tests to pass before any commit. Frontend workers carry a different note about mobile breakpoints.
  • Temporary hold notices. When a part of the codebase is in flux, pin a short note to affected workers: "migrations are frozen until Monday — do not modify db/schema.sql." Remove it when the hold lifts.
