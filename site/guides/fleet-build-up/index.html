The amux Build-Up: From One Repo to a Coordinated Agent Fleet

Published July 2026. Nine sequential steps, each mapped to the component that implements it.

The most common question after seeing a fleet run is not "how do I start a session." It is the meta-level: where do the instructions live that apply to every session? How does a task actually move from todo to done? Where do I define what good looks like, so I don't have to repeat it to each agent I spin up?

The answer has a shape, and the shape is a build-up. Each step below adds one layer, names the amux component that implements it, and explains why the layer automatically applies to every session you create afterward. Do them in order. You can stop at any step and have a working setup; each later step is what you reach for when the previous one starts to strain.

Step 1 — Put your instructions in the repo, not in a chat

"Where do I put the instructions at the high level that work across all the different sessions I spin up?"

CLAUDE.md hierarchy .claude/rules/

In files, versioned in git. Agent CLIs read an instruction hierarchy natively, before your first prompt:

~/.claude/CLAUDE.md      # you-level: applies in every project ("never force-push", "email = the email API")
your-repo/CLAUDE.md      # project-level: build commands, conventions, what done means here
your-repo/.claude/rules/ # scoped rules: one file per concern (css.md, deploy.md, testing.md)

This is deliberately not an amux control panel. Instructions live where your code lives, so they are reviewed in PRs, versioned, and identical for humans and agents. amux's job is to launch every agent inside the right working directory so this hierarchy loads.

Why it scales: a session created three weeks from now, on your phone, for a task you have not imagined yet, reads the same files. You never re-brief.

Step 2 — Hire your first session

"How do I make sure every session knows which model to use?"

Sessions session defaults

A session is one agent CLI (Claude Code, Codex, Gemini) in its own terminal, pointed at a working directory, with a model and flags recorded at creation. Create it from the dashboard or CLI; amux remembers your defaults, so model policy is a decision you make once and override per hire when a task needs a bigger or cheaper brain.

Why it scales: the session record is the employment contract: directory, model, flags, creator. Every later feature (board attribution, messaging, cost) keys off it.

Step 3 — File work on the board, not in the prompt

"How do you go from todo to in-progress to done?"

Board amux board CLI REST API

The board is the shared ledger: cards move backlog → todo → doing → review → done → verified. Both sides write to it. You add and drag cards in the dashboard; agents claim, advance, and close their own cards through the API as they work. Prompts you send a session are auto-captured as cards, so the ledger stays complete even when you forget to file.

The rule that makes it work: one card is one unit of work, something that can be honestly done or not done. Agents read the whole board before starting anything, which is how duplicated and conflicting work gets caught before it happens.

Why it scales: the board is the answer to "what is everyone doing" without reading any logs. A reviewer can reconstruct the fleet's day from cards alone.

Step 4 — Define what good looks like, as gates

"How do I define what good looks like for the agent? Where do I do that?"

Card types Status gates done ≠ verified

Two places, by lifetime. Durable standards ("tests pass before any merge") go in the instruction files from Step 1. Per-task acceptance lives on the card: its type (code, research, ops, doc...) derives a gate checklist, and the server rejects a status change until the agent explicitly acknowledges each gate. A code card cannot reach done without "implemented and merged" plus "tests pass".

The last column is the sharpest tool: done means implemented, verified means proven in production with evidence recorded on the card. Agents cannot blur the two, because the gate rejects the transition without the receipts.

Why it scales: quality stops being a per-prompt plea. It is enforced at the ledger, identically for every session, every model, every task type.

Step 5 — Let sessions talk, with provenance

"I want the agents to interact with each other."

amux send Peek Steering queue

Three primitives cover coordination:

  • amux send delivers a message from one session to another, stamped server-side with the true sender. No agent can impersonate another, and every handoff is auditable.
  • Peek lets a session read another session's terminal history: check real state instead of asking and waiting.
  • Steering queues a message to land only when the target finishes its current task: a note on the desk, not an interruption.
Why it scales: agents negotiate handoffs themselves ("I'm pushing, hold your deploy") and the origin stamps mean a message trail you can trust after the fact.

Step 6 — Wire structure: dependencies and reviewers

depends_on reviewer edges

Cards can reference each other. A card with depends_on set is blocked while its dependencies are open, and the autonomy loop skips it rather than starting doomed work. A card with a reviewer cannot pass from review to done unless the acknowledging session is that reviewer, which makes cross-agent verification structural instead of voluntary.

Why it scales: the graph replaces prose like "blocked on X" that only humans could read. Orchestration logic runs on edges, not vibes.

Step 7 — Turn on autonomy, bounded by everything above

Auto-pickup Advance nudges WIP-1

This is the payoff step, and it only works because Steps 1 through 6 exist. An idle session automatically picks up the next unblocked todo card on its lane, works it through the gates, and closes it. Sessions holding a stalled card get nudged to advance it, park it with an honest blocker, or split it. One card in doing per session keeps "what is being worked on" true.

Autonomy is bounded by the same rules as manual work: gates still reject dishonest transitions, dependency edges still block, and guards refuse cards that name irreversible operations without a human.

Why it scales: you stop dispatching. You file work; the fleet drains the queue; the ledger shows what happened, with evidence.

Step 8 — Recurring duties

Scheduler

Anything you would put on a human's recurring calendar becomes a schedule: a prompt fired at a session on a cadence ("every weekday at 8am: triage the inbox and email me a digest", "every 15m: check CI health"). Runs are recorded with their source, so a scheduled fire and a manual run are distinguishable later.

Why it scales: standing duties stop depending on you remembering to ask.

Step 9 — Watch it run

Dashboard filters Cost Alerts

Observability closes the loop. Board filters answer fleet questions directly: is:working, is:gated (sessions blocked on rate or credit limits), is:rotting (in-flight cards going stale). The Cost tab prices every turn by task, session, model, and day. Alerts escalate the rare thing that genuinely needs you now, with provenance and dedupe.

Why it scales: the meta-level you manage is the ledger and its filters, not terminals. Ten sessions read like a team standup, not ten screens.

The build-up in one paragraph

Instructions live in versioned files every agent reads (1). Sessions are hires with a recorded model and directory (2). Work lives on a shared, gated board that agents move honestly (3, 4). Sessions coordinate through stamped messages, peeks, and steering (5), structured by dependency and reviewer edges (6). Autonomy drains the queue inside those rails (7), schedules cover the recurring (8), and the dashboard is where you manage the meta-level (9).

FAQ

Where do I put instructions so every future session inherits them?

In the CLAUDE.md hierarchy in your repo and home directory (Step 1). amux launches each session in the right working directory; the agent CLI loads the files natively. Nothing to configure per session.

Is there an amux control panel for instructions?

Deliberately minimal. Durable rules belong in git-versioned files, and amux Memory adds per-project facts injected into every session in that project. The control panel manages sessions, the board, schedules, and observability, not your standards.

How does a task move from todo to done?

An agent claims the card (or auto-picks it up when idle), moves it to doing, works, and advances it through review to done by acknowledging the type-derived gates. verified is reserved for work proven in production with evidence on the card.

Can agents close their own work dishonestly?

The gates reject transitions whose acknowledgements are missing, forced bypasses are logged, and a reviewer edge requires a different session to sign off. The design goal is that the truthful path is always the easiest one.

Do I need all nine steps?

No. Steps 1 to 3 are a complete working setup. Add gates when quality needs teeth, messaging when you run more than two sessions, edges and autonomy when dispatching becomes your bottleneck.
