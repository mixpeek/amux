AI Agent Connectors — Give Your Fleet Secure Access to External APIs

Paste API credentials once, scope them to the right agents, and let the fleet pick them up automatically. Updated August 2026.

amux is the open-source control plane for running AI agent teams — MIT licensed, self-hosted. View amux on GitHub ★

The amux Connectors tab lets you configure API credentials for external services — Google, Granola, or any custom API — and make them available to your agent fleet as environment variables. Set the scope once (global, group, or per-worker), click Test to verify the connection, and every agent in that scope picks up the credential automatically at launch. Credentials stay out of CLAUDE.md files and git history.

The problem: credentials scattered across agent prompts and shell profiles

When you run more than a few AI agents, credential management becomes a recurring friction point. The common approaches each have a cost:

  • Hardcoding in CLAUDE.md — works until you push that file to a public repo, or until the key rotates and you have to find every CLAUDE.md that references it.
  • Shell environment variables — works on the machine where you set them. Fails when you start an agent via a launchd job, a remote session, or a cloud container where your shell profile is not loaded.
  • Passing keys in prompts — extremely fragile, leaks credentials into conversation history, and requires re-entering on every new session.
  • Per-agent .env files — better, but scattered. Rotating a key means finding and updating every .env file for every agent that uses it.

The Connectors tab solves all of these: one place to paste, one place to rotate, and automatic distribution to the right agents at the right scope.

Three approaches: scattered credentials vs. Connectors tab

Approach Problem When it survives
Key in CLAUDE.md Leaks if the file enters git history. Must update N files when a key rotates. One-agent, throw-away projects with no git push.
Shell env var (~/.zshrc) Not inherited by launchd agents, remote sessions, or container-started agents. Interactive terminal sessions only, single machine.
Per-agent .env file N files to update on key rotation. Scope decisions implicit and undocumented. Small fleets where files are centrally managed.
amux Connectors tab One paste. Explicit scope. Test button verifies before relying on it. Rotations update one record. Any fleet size. Works for launchd, remote, and container-launched sessions.

How to configure a connector — step by step

  1. Open the Connectors tab In the amux dashboard, click the Connectors tab or press C. The panel shows all configured providers, their scope, and their current status (connected / error / untested).
  2. Choose a provider Select from the provider registry. Named providers (Google, Granola) know their credential shape — OAuth client file path for Google, API key for Granola. For anything else, use Custom and name the environment variable yourself.
  3. Paste your credential Enter the key or token value in the secure field. For Google, provide the path to your existing gmail-oauth-client.json — amux reuses the OAuth client you already have, so no new secret needs to be copied.
  4. Set the scope Choose global (every session), group (a named group of sessions), or worker (one specific session). Start global for shared read-only tools. Narrow scope for credentials with billing exposure or write access.
  5. Test the connection Click Test. amux pings the provider to verify the credential is accepted. A green indicator confirms the integration is live. A red indicator tells you the credential is wrong before you lose a session to a runtime error.
  6. Launch an agent — credential arrives automatically Start a session. Agents in scope receive the credential as an environment variable. In Claude Code, access it via process.env.YOUR_KEY_NAME or $YOUR_KEY_NAME in shell commands — no additional setup in CLAUDE.md required.

Credential scope: which agents see which credentials

The scope model is the key design decision. Choose it based on the sensitivity and blast radius of the credential:

Scope Who gets the credential Best for
global Every agent session in this amux instance Read-only analytics APIs, shared logging services, tools every agent uses regardless of project
group All sessions in a named group (e.g., "backend", "gtm") Project-specific APIs, credentials for a single client, team-bounded integrations
worker One specific named session High-privilege write keys, billing-sensitive credentials, production system access for a designated agent only

If the same key name is configured at multiple scopes, the most specific scope wins: worker overrides group, group overrides global. This lets you set a global read-only Stripe key and give one billing-agent a write-capable key without touching any other session.

Built-in providers

Google

Gmail, Drive, Calendar

Reuses your existing gmail-oauth-client.json — no new secret needs to be copied. Agents get the OAuth client path as an env var and can call the Gmail, Drive, and Calendar APIs using the existing token flow. See the automation guide for usage patterns.

Granola

Meeting notes API

Granola exposes a key-only API. Paste the key; amux injects it as GRANOLA_API_KEY. Agents can pull meeting notes, transcripts, and action items without any additional authentication logic.

Custom

Any API key or bearer token

Define the environment variable name yourself. Paste the value. Agents receive it exactly as named. Use this for Stripe, Twilio, PostHog, Slack, Linear, or any other service your agents need to reach. No provider definition required.

Common patterns: how teams use Connectors

Pattern 1 — Shared read-only observability (global scope)

Set a PostHog or Sentry API key at global scope. Every agent in your fleet can pull error rates, query event data, or check dashboards without anyone adding a key to their CLAUDE.md. Rotate the key once when it expires; all agents pick up the new value on next launch.

Pattern 2 — Project-specific integrations (group scope)

You have a "backend" group of agents and a "gtm" group. The backend agents need a Stripe key to generate test invoices. The GTM agents need a HubSpot key to log lead activity. Set each at group scope; neither group sees the other's credentials. Add a new agent to the backend group and it immediately has the Stripe key — no individual configuration.

Pattern 3 — High-privilege production access (worker scope)

Your fleet runs dozens of agents, but only one — a designated deploy agent — should have production database credentials. Set those at worker scope for that session name. Every other agent in the fleet, even global-scope readers, gets nothing. The credential doesn't appear anywhere else.

Pattern 4 — Credential rotation without session disruption

When a key rotates (scheduled, after a leak, or at provider request), go to the Connectors tab, update the value, click Test, and confirm it's accepted. The next session launch for every agent in scope picks up the new key. No CLAUDE.md edits, no shell profile changes, no restarting running sessions except those that need the new key immediately.

Frequently asked questions

How do I connect an AI agent to an external API?

In amux, open the Connectors tab, choose the provider (Google, Granola, or Custom), paste your API key or token, set the scope (global, group, or per-worker), and click Test. The credential becomes available to agents in scope as an environment variable on their next launch — no additional configuration in CLAUDE.md.

What is the difference between global, group, and worker scope?

Global makes the credential available to every agent in the fleet — suitable for shared, read-only tools. Group scope limits the credential to agents in a named group — useful for project-specific or team-specific integrations. Worker scope restricts access to one named session — appropriate for high-privilege or billing-sensitive keys. The most specific scope wins when the same key name is set at multiple levels.

Are credentials stored securely?

Credentials entered via the Connectors tab are stored in the amux database and injected as environment variables at session launch time. They are not written into CLAUDE.md, not echoed in agent transcripts, and not included in git history. The Test button lets you verify a credential is accepted before relying on it in a run.

Do I need to restart a running session after adding a connector?

Yes — credentials are injected at launch time. A session already running doesn't pick up a new connector until it is restarted. Sessions launched after the connector is saved automatically receive it.

Can different agents use different keys for the same API?

Yes. Set two connectors for the same provider at different scopes or with different variable names. For example, a global connector can hold a read-only Stripe key (variable: STRIPE_KEY), while a worker-scoped connector on your billing agent uses the same variable name but a write-capable key — the worker-scoped version overrides the global for that session only.

What services work with the Custom connector type?

Any service that uses an API key or bearer token. Common uses include Stripe, Twilio, PostHog, Slack webhooks, Linear, GitHub tokens, OpenAI, Anthropic, and any internally hosted API. Define the variable name, paste the value, and agents receive it exactly as named.
