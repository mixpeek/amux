Running AI Agents 24/7

Continuous operation requires self-healing, not just auto-start. Updated September 2026.

An AI engineering team does not need to stop when you do. The practical ceiling on overnight runs has always been reliability: agents crash, context windows fill up, and prompts stall waiting for a human who has gone to bed. amux's self-healing watchdog addresses the three most common failure modes automatically, and the Telegram connector means your agents can reach you on your phone when something genuinely needs a decision. The result is a fleet that ships code while you sleep and hands you a morning summary over coffee.

The five failure modes of overnight AI runs

Understanding why agents stop is the first step to preventing it. Most overnight failures fall into one of five categories:

Failure mode What happens How amux handles it
Context exhaustion The agent fills its context window and halts with a capacity error Watchdog detects the threshold and triggers auto-compact. The agent resumes within seconds, losing only the most repetitive history.
Process crash An uncaught exception or OOM kill terminates the session Watchdog detects the dead process and restarts it, replaying the last message so the agent picks up where it left off.
Stalled prompt The agent asks a clarifying question and waits indefinitely Telegram relay forwards the output to your phone. You read it at breakfast and send a one-line reply that unblocks the agent.
Concurrent write conflict Two agents edit the same file and produce a merge conflict Isolate agents to separate worktrees or use the board's task claiming to ensure only one agent owns each file path at a time.
Memory pressure Too many agents exhaust RAM, triggering OOM kills that cascade amux monitors available memory and refuses to start new sessions below a configurable threshold (default 15% free).

How the self-healing watchdog works

The watchdog is a background process inside amux that polls every running session on a short interval. It tracks three signals:

  • Context fill level: when a session's context use crosses the auto-compact threshold (configurable, default 80%), the watchdog sends a compact request. The agent keeps working; users see no interruption.
  • Process liveness: if the underlying tmux pane for a session exits, the watchdog logs the event and restarts the session within a few seconds, replaying the most recent message.
  • Rate limit state: when a session hits a provider rate limit, the watchdog holds the session rather than retrying immediately, then resumes when the limit window clears.

The key property is that these three paths need no human attention. A developer can walk away from a 10-agent fleet running complex features and expect to find progress in the morning, not a set of blank terminals waiting for someone to press a key.

Stay connected with Telegram

Self-healing covers crashes and context exhaustion. The third failure mode, a stalled prompt, requires a human response. The amux Telegram connector makes that response frictionless: agents push their output to a Telegram chat, and you can reply from your phone to unblock them.

Setup takes about five minutes:

  1. Create a Telegram bot Message @BotFather on Telegram and use /newbot. Copy the token it gives you.
  2. Add the token to server.env Open ~/.amux/server.env and add TELEGRAM_BOT_TOKEN=your_token_here. Restart amux (launchctl kickstart -k gui/$(id -u)/com.amux.server-rs).
  3. Link your Telegram chat Start a conversation with your new bot and send /start. amux links this chat to the server. Any agent that sends to the Telegram connector now reaches this chat.
  4. Route agents to Telegram From the dashboard or CLI, link a specific worker: amux telegram link @worker-name. That worker's output relays to Telegram automatically. Use @lane mentions in Telegram to route your replies to the right agent.

With this in place, a stalled agent at 2am sends you a Telegram message. You see it at 7am, type a reply from your phone, and the agent has been unblocked for five hours by the time you open your laptop.

Monitor from your phone

amux ships with two mobile interfaces. The installable PWA works on any phone browser: navigate to your amux server's URL, add it to your home screen, and you have a full dashboard including live session status, board state, and the last terminal output of every agent.

The native iOS app adds push notifications, a richer board interface, and faster load times. Both interfaces let you send messages to any running agent. Checking in on a 20-agent overnight run takes about 30 seconds: glance at the board, look at any session showing an unusual status, send a message if anything needs direction.

Setting up overnight runs

A reliable overnight setup follows this pattern:

  1. Load the board before you leave. Add every task as a board card with enough detail for an agent to start without asking a clarifying question. Include acceptance criteria, relevant file paths, and any external resources the agent will need.
  2. Set continuation contracts. For each card, record a continuation: the current state, which files are in play, and what the next step should be if the agent has to pick up after a crash. This lets a fresh session resume without starting over.
  3. Isolate agents by file ownership. Use the board's blocked-on relationships to serialize work on shared files. Agents that own non-overlapping parts of the codebase can run fully in parallel.
  4. Scope task size to 2-3 hours. Tasks that run longer than one context window risk fragmented output. Scope tasks to fit comfortably within a single session's effective context, and let the board chain them with dependencies.
  5. Enable Telegram relay. Link at least your most active overnight workers to Telegram so stalled prompts reach you as messages rather than silent waits.

The morning routine

Open the board on your phone before you open your laptop. Done cards show what shipped. Doing cards show what is still running. Any card stuck in doing for more than a few hours has a note from the agent explaining why it stopped.

Check Telegram: any message from overnight tells you what the agents asked for and what you replied. Look at the git log for the last 8 hours to see what actually landed. Move done cards to verified after you confirm the output is correct.

A well-configured fleet of 10-20 agents running a full night can produce 30-60 commits of real code. The morning review takes 15-20 minutes and focuses on quality, not on restarting crashed processes.

Frequently asked questions

How do I keep AI coding agents running overnight without crashing?

Use a self-healing orchestrator like amux. The watchdog automatically compacts context when it nears the limit, restarts crashed sessions, and replays the last message. The three most common failure modes require no manual intervention. For stalled prompts, enable the Telegram connector so agents can reach you on your phone.

What causes AI coding agents to stop working overnight?

Context exhaustion, process crashes, and stalled prompts account for the vast majority of overnight failures. Memory pressure and concurrent write conflicts are less common but more damaging when they occur. See the failure mode table above for how amux handles each one.

How many agents can I run in parallel overnight?

The limit is memory. Each session uses roughly 200-400 MB of RAM. A 16 GB machine handles 20-30 agents comfortably. amux monitors available memory and stops starting new sessions below the threshold you set, so a large fleet does not OOM-kill itself.

Can I get Telegram notifications from my AI agents?

Yes. The amux Telegram connector relays agent terminal output to any Telegram chat you configure. You can reply from your phone and the reply routes back to the correct agent. See the Telegram notifications guide for setup steps.

Do I need to be on my computer to monitor overnight runs?

No. The amux mobile PWA and iOS app both show live fleet status. Telegram adds a second channel: agents push updates, you reply if needed. Most overnight runs need no interaction at all; Telegram is there for the cases where a decision is genuinely needed.

What should I put on the board before running agents overnight?

Every task that needs to be done, with enough context for an agent to start without a clarifying question. Include acceptance criteria, relevant file paths, and any external dependencies. Set blocked-on relationships between tasks that share files. Add a continuation contract to each card so a crashed agent's replacement can resume without starting over.
