Browser Profiles for AI Agents — Persistent Authentication at Scale

Save browser sessions once. Run dozens of authenticated AI automation tasks without re-logging in. Updated October 2026.

amux browser profiles let you save named Chrome browser sessions — with their full cookie and authentication state — so AI agents can run authenticated web tasks without ever logging in again. Create a profile once (interactively, with real MFA), and every subsequent agent run starts already inside your account. Multiple agents can use different profiles in parallel: one pulling Stripe data, another reviewing GitHub PRs, a third checking a client portal — all authenticated, all running simultaneously, all monitored from your phone.

Why Browser Authentication Is the Hardest Part of AI Automation

Browser automation has been technically possible for years. The reason most AI agent automation workflows fail in practice is not the agent logic — it is authentication.

Every enterprise SaaS tool, financial dashboard, and client portal sits behind a login wall. Re-implementing that login on every run means:

  • MFA blockers: TOTP, push notifications, and hardware keys cannot be scripted. Every automated login triggers them.
  • CAPTCHA interruptions: Sites detect programmatic logins and serve CAPTCHAs. The agent stalls, waits, or fails.
  • Session timeouts: Scripted logins using stored passwords break when sites enforce 2FA on new sessions, change their login flow, or add bot detection.
  • Credential sprawl: Storing plaintext passwords in environment variables or scripts is a security anti-pattern that grows more fragile with each rotation.

The right solution is to log in once as a human — with all the friction of MFA and CAPTCHA — and hand the resulting authenticated session state to the AI agent. That is exactly what amux browser profiles do.

How amux Browser Profiles Work

amux connects to Chrome via the Chrome DevTools Protocol (CDP). Browser profiles are named Chrome sessions stored in ~/.amux/playwright-auth/profiles/. Each profile maintains its own isolated cookie jar, localStorage, and session state.

Step 1 — Create a named profile in the Browser tab

Open the amux dashboard at https://localhost:8824. Go to the Browser tab and click New Profile. Give it a descriptive name that reflects the account or service:

stripe          # Stripe financial dashboard
github-work     # GitHub work organization
client-acme     # Acme Corp client portal
jira-internal   # Internal Jira instance

amux creates an isolated Chrome session config for this profile in ~/.amux/playwright-auth/profiles/<name>/.

Step 2 — Log in once and save the session

Launch a browser session under the new profile from the Browser tab. A Chrome window opens in the profile's isolated state (no existing cookies, completely fresh). Navigate to your target site and complete the full login flow — username, password, MFA code, push notification, hardware key, whatever the site requires. This is a real human login, so there are no bot-detection or CAPTCHA issues.

Once you are inside the account, close the session from the amux Browser tab. amux persists the full authenticated state to disk. The next session launched under this profile skips the login entirely.

Step 3 — Launch AI automation tasks using the saved profile

When writing a browser automation prompt or scheduling a browser task, specify the profile by name. The AI agent's Chrome session starts with the saved cookies loaded — it opens to the authenticated state, not the login page. Tasks that previously required scripted credential handling now just work:

# Example: pull last 7 days of Stripe payouts
Profile: stripe
Task: Go to dashboard.stripe.com/payouts, filter to the last 7 days,
      read the total payout amount, and post it to the amux board.

No credential configuration. No MFA workarounds. The agent operates inside the account exactly as a logged-in human would.

Step 4 — Monitor multiple authenticated sessions from one dashboard

Run a fleet of agents concurrently, each using a different profile. The amux dashboard (and iOS app) shows all active browser sessions live. From your phone you can watch one agent pulling financial data, another reviewing PRs, and a third checking client deliverables — all authenticated, all in parallel.

Real Use Cases

Financial reporting automation

A solo founder creates a stripe profile and logs in to the Stripe dashboard once. Each morning, amux schedules an agent to open Stripe, navigate to payouts, read yesterday's total, and post it as a board item. No API key required, no Stripe SDK integration, no dashboard re-login. The same pattern works for QuickBooks, Brex, Mercury, or any financial tool the founder uses.

Agency client management

A development agency manages 8 clients, each with their own portal. Rather than maintaining a password vault and re-logging in for each client check, the agency creates one profile per client portal. An amux scheduler checks each portal daily for new deliverable feedback, new support tickets, or project status changes — and posts summaries to the board. The account executive monitors all 8 from the iOS app on their phone.

Internal tool automation

An engineering team uses Jira, GitHub, and an internal analytics dashboard — all behind SSO. A github-work profile handles PR triage (drafting review comments, labeling issues). A jira-internal profile handles ticket status syncing. These run as background agents while the team ships code, surfacing updates to the shared board without any manual context switching.

Multi-tenant SaaS testing

A SaaS product team creates profiles for different test accounts (tier-free, tier-pro, tier-enterprise). Browser automation tests run against each tier in parallel — testing feature gating, quota enforcement, and UI differences across tiers simultaneously, with each session already authenticated to the correct account.

What changed in October 2026

  • One profile per identity. A profile now stands for who you are signed in as (your work account, a client account, a test user), with a named list of sites, so it is obvious which one a worker should use.
  • The harness picks the profile. amux browser for <url> recommends the profile for that site within the worker's allowed scope and shows the cookie evidence behind the choice. Starting a browser with no profile uses your default identity.
  • Logins stay fresh on their own. A sync job copies cookies for the sites you listed from your own Chrome into the matching profile every 6 hours. Sites you did not list never reach an agent profile, and signing out in Chrome removes the login from the profile on the next pass.
  • Rotating-token logins are left alone. Apps that keep a rotating refresh token in localStorage (Supabase, Auth0 SPA, MSAL, Okta) sign out both copies when the token is shared. amux now skips those entries and tells you to sign in once inside the amux profile instead, which gives it its own session.
  • Worker tabs open in a background window. When a worker drives your real Chrome, its tab opens in a new window behind your work, not in the window you are using.

Security: What Is Stored and Where

amux is a local-first tool. All browser profile data is stored on your own machine:

  • Location: ~/.amux/playwright-auth/profiles/<profile-name>/
  • Content: Chrome user data directory — cookies, localStorage, IndexedDB, session state. No passwords stored in plaintext; only the post-authentication session tokens.
  • Network exposure: The amux dashboard runs at https://localhost:8824. It is not exposed to the internet unless you explicitly use amux tunnel. Profile data never leaves your machine.
  • Access control: Standard OS file permissions on ~/.amux/. The same protection as your browser's existing profile directory.

If a session token expires, the agent will hit the login page and stop — it will not attempt to re-authenticate or access credentials. You re-run the interactive login to refresh the profile.

Getting Started

  1. Install amux: curl -fsSL https://amux.io/install.sh | bash
  2. Open https://localhost:8824 → Browser tab → New Profile
  3. Name the profile, launch a session, log in to your target site, stop the session
  4. Schedule a browser task using the saved profile

Chrome (or Chromium) must be installed on the machine running amux. No additional configuration is required.

Frequently Asked Questions

What is a browser profile in amux?

A browser profile in amux is a named, saved Chrome browser session that persists cookies, localStorage, and authentication state across runs. You create a profile (e.g. "stripe"), log in to the target site once, and every AI agent task launched with that profile starts already authenticated — no re-login needed.

How do AI agents use saved browser sessions?

When you create a browser automation task in amux, you select a profile from the profile picker. amux launches Chrome via CDP (Chrome DevTools Protocol) with the saved profile's credentials loaded. The agent sees the site as already logged in and can proceed directly to the task — pulling reports, filling forms, reading dashboards — without triggering login flows.

Is it safe to store browser credentials in amux?

amux is a local-first tool. Browser profiles are stored in ~/.amux/playwright-auth/profiles/ on your own machine. The dashboard runs at https://localhost:8824 — it is never exposed to the internet unless you explicitly use the tunnel feature. Your credentials never leave your machine, and no amux server ever sees them.

Can multiple AI agents use different browser profiles at the same time?

Yes. Each agent runs in its own isolated Chrome session tied to a specific profile. You can run a "stripe" agent pulling financial data simultaneously with a "github-work" agent reviewing PRs and a "client-acme" agent checking a client portal — all in parallel, all authenticated independently.

What browsers does amux support for browser profiles?

amux uses Chrome (or Chromium) via the Chrome DevTools Protocol (CDP). Chrome must be installed on the machine running amux. The profiles store Chrome-native session data (cookies, localStorage). Firefox and Safari are not supported for profile-based automation.

How is this different from Playwright test fixtures?

Playwright test fixtures create fresh browser state on each run — authentication typically requires a setup step that logs in programmatically using stored credentials. amux browser profiles are persistent human-created sessions: you log in interactively once (including MFA flows that are impossible to script), and the saved state is reused indefinitely. There is no credential management code to write and maintain.
