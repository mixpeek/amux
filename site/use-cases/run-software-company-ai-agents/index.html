Run a Software Company with AI Agents

Engineering, QA, devops, and product documentation running in parallel — coordinated by one person from a phone. amux is the open-source control plane for AI agent teams: kanban, self-healing, CRM, and email built in. Published September 2026.

Quick answer: Register one amux session per department (engineering, qa, devops, product). Load a sprint's worth of tasks onto the shared kanban board. Enable auto-drain so sessions self-assign tasks when their queue empties. The self-healing watchdog handles crashes, context overflow, and idle hangs automatically. You review PRs and steer agents from your phone. One person. Company-scale output.

The AI Staffing Model

In a traditional software company, each department runs independently and hands off work via tickets, PRs, and Slack. With amux, each department is a named session. Every session shares one kanban board, one message thread, and one dashboard. Handoffs are board card transitions — attributable, visible, and zero-latency.

You are not limited to five departments. A monorepo with distinct sub-products might have separate engineering sessions per service. An early-stage startup might collapse QA and devops into one session. amux has no session limit — your API token budget is the practical ceiling.

Engineering: Feature Development

The engineering session handles the core coding loop: read a card from the board, implement the feature, open a PR, move the card to done. With YOLO mode (default for new sessions), it never blocks on a tool-approval prompt.

# Register an engineering session for your project
$ amux register engineering --dir ~/Dev/myproject --yolo

# Add a feature task to the board
$ amux board add "Add JWT refresh token rotation" --group engineering

# Enable auto-drain — the session claims the next task when idle
$ amux board drain on engineering

# Start the session — it reads the board and begins immediately
$ amux start engineering

Parallel development works by running multiple engineering sessions against different feature branches. See the parallel feature development guide for how to prevent merge conflicts across concurrent sessions.

QA: Testing and Bug Triage

A dedicated QA session receives handoff cards from engineering, writes integration tests, reproduces reported bugs, and files new board cards for anything it finds. It can also audit PRs on GitHub directly and post review comments.

# Register a QA session
$ amux register qa --dir ~/Dev/myproject --yolo

# Engineering session marks its work done and creates a QA card
$ amux board add "Test JWT refresh token rotation — PR #142" --group qa

# QA session picks it up, runs the test suite, posts findings on the board

For test generation at scale, see the automated code review use case and the bug triage and fixing guide.

Devops: CI/CD and Infrastructure

The devops session handles everything below the application layer: Dockerfile maintenance, CI workflow updates, dependency version bumps, secrets rotation reminders, and monitoring config. These are high-context, low-judgment tasks that run cheaply on smaller models.

# Register a devops session
$ amux register devops --dir ~/Dev/myproject --yolo

# Typical devops board card
$ amux board add "Bump all pip deps to latest, fix any breaking changes, update Dockerfile" --group devops

# Another: weekly security scan
$ amux board add "Run npm audit and pip-audit, file cards for any HIGH or CRITICAL findings" --group devops

The CI/CD pipeline creation use case and dependency updates guide cover common devops agent patterns.

Product: Specs and Documentation

The product session generates user-facing documentation, changelog entries, feature specs, and README updates. It reads the board for completed engineering work and writes the corresponding docs automatically — no separate documentation sprint needed.

# Typical product board card (created when engineering marks something done)
$ amux board add "Write changelog entry and user docs for JWT refresh token rotation" --group product

# Or schedule it to run every Friday at 5pm
$ curl $AMUX_URL/api/schedules -X POST \
  -d '{"title":"Weekly docs update","session":"product","command":"Read all board cards marked done this week. Write changelog entries for user-facing changes. Update README where affected. Commit to docs/ branch.","schedule_expr":"weekly on Friday at 5pm"}'

Cross-Department Handoffs via the Board

The shared kanban board is the coordination layer. When engineering finishes a task, it creates a QA card. When QA passes, it creates a product card for docs. Every card carries an author, a timestamp, and a description — the full audit trail lives on the board without any separate project management tool.

Handoff flow for a single feature

1. Product session creates card: "Add JWT refresh token rotation" — group: engineering
2. Engineering session auto-claims it (auto-drain), implements, opens PR, marks done
3. Engineering creates card: "Test JWT refresh token rotation — PR #142" — group: qa
4. QA session claims it, runs tests, comments on PR, marks done
5. QA creates card: "Write changelog + docs for JWT refresh rotation" — group: product
6. Product session generates docs, commits to docs/ branch, marks done
7. You review and merge three PRs from your phone

All of steps 1–6 happen without human input. The entire handoff chain is auditable on the board. You see the story of the feature — from card to shipped — in one view.

Auto-Drain: Self-Managing Task Queue

Shipped September 2026 (AMUX-4055). With auto-drain enabled, a session automatically claims the next open card from the board when its current task finishes — no human needed to restart it. Load a full sprint in the evening, enable drain on every session, and let the fleet work through the backlog overnight.

# Enable auto-drain for all departments
$ amux board drain on engineering
$ amux board drain on qa
$ amux board drain on devops
$ amux board drain on product

# Sessions only claim cards tagged for their group
# engineering claims --group engineering cards; qa claims --group qa cards

Each session logs why it declined a card (wrong group, no tasks available, drain disabled), so you can audit the queue in the morning and see exactly where things stalled. The agentic engineering guide covers auto-drain and sprint planning in detail.

A Full Sprint in 24 Hours

Here is what a 24-hour sprint looks like when every department is running in parallel:

24-Hour AI Company Sprint

Evening (30 min) — You load 15 cards onto the board: 8 engineering, 3 QA, 2 devops, 2 product. Enable auto-drain. Start all sessions. Check from your phone that all 5 sessions are active.
Overnight — Engineering completes 5 features and opens 5 PRs. QA tests 4 of them. Devops bumps 12 dependencies and updates the Dockerfile. Product writes changelog entries for everything completed.
Morning (20 min) — You open the iOS app. Board shows 11 cards done, 4 still in progress. Review 5 PRs — merge 4, leave 1 with a comment. Send one message to engineering redirecting a session that went off-track.
Afternoon — Remaining sessions finish. QA finds 2 bugs and files cards. Engineering picks them up via auto-drain. Product publishes updated docs to the docs branch.
End of day (15 min) — All 15 original cards done. 2 bonus bug-fix cards also done. You merge the docs PR. Sprint complete.

Total human time: about 65 minutes across the whole day. The rest is the fleet.

FAQ

Q Can one person actually run a software company with AI agents?
For a focused product with clear scope — yes. One person with amux can coordinate 10–50 parallel AI sessions across engineering, QA, devops, and product. The bottleneck shifts from execution to your judgment: architecture decisions, reviewing PRs, and steering agents that go off-track. Most solo founders using amux report spending 1–2 hours per day on coordination and the rest on strategic work.
Q How do I prevent agents from breaking each other's work?
Use feature branches: each engineering session works on its own branch and opens a PR. The shared kanban board enforces that two sessions never claim the same card (compare-and-swap). For files that multiple sessions might touch (like a shared config), use the board's task tagging to route those cards to a single session. See the parallel feature development guide for branch strategy patterns.
Q What types of tasks are NOT suitable for AI agents?
Tasks requiring novel system design (architecture from scratch), nuanced customer negotiations, decisions that depend on market intuition, and anything where a wrong answer has high blast radius (database migrations on production, billing system changes). Use agents for well-specified execution tasks. Use yourself for judgment calls that compound.
Q How much does it cost to run an AI software company with amux?
amux itself is free and open source. The cost is AI API usage. For a typical 5-session fleet running 8 hours per day: $20–80/day depending on model mix. Claude Code on Claude 3.5 Sonnet runs roughly $10–30/day per active session. Gemini CLI and Codex can reduce costs for batch tasks. Most teams set a daily API budget alert in their model provider's billing dashboard.
Q How do I get started running a software company with AI agents?
Install amux: brew install mixpeek/amux/amux (macOS) or git clone https://github.com/mixpeek/amux && cd amux && ./install.sh (all platforms). Open the dashboard at https://localhost:8824. Register your first two sessions (engineering + qa). Add 5 tasks to the board. Enable auto-drain. Start both sessions. The getting started guide takes under 5 minutes.
