amux vs AutoGen (Microsoft)

AutoGen programs multi-agent reasoning pipelines. amux operates AI coding agent teams. Different layers of the stack — often used together. Updated September 2026.

The short answer: AutoGen (59,000+ GitHub stars, Microsoft Research) is a Python framework for building multi-agent conversation systems — you write code to define how agents reason together. amux is an open-source runtime for operating AI coding agent teams (Claude Code, Codex, Gemini CLI) with usage-limit and reboot recovery, a web dashboard, a shared kanban board, and mobile monitoring. They solve different problems at different levels of the stack.

The Core Distinction

AutoGen and amux operate at different layers of the AI agent stack:

  • AutoGen — the intelligence layer. You program how agents reason, what tools they call, and how they converse. A GroupChat with an AssistantAgent and a UserProxyAgent is an AutoGen concern.
  • amux — the operations layer. You run and monitor the agent sessions doing the actual work. A fleet of Claude Code tmux sessions with usage-limit resume and mobile monitoring is an amux concern.

The clearest analogy: AutoGen is to agent logic what Kubernetes is to application logic — it defines the orchestration pattern. amux is to coding agent sessions what a container runtime is to containers — it keeps them visible and manageable.

AutoGen in Depth

AutoGen is a research-originated framework from Microsoft that has grown into one of the most widely used multi-agent frameworks in the AI ecosystem. Its 59,000+ GitHub stars reflect both the quality of its abstractions and the breadth of use cases it enables — from automated research pipelines to complex group chat orchestrations.

Core Components

  • ConversableAgent — the base class. Every AutoGen agent can send messages, receive messages, execute code, and call tools. You extend this to create specialized agents.
  • AssistantAgent — an LLM-backed agent that responds to messages and can write and suggest code. Configured with a model (GPT-4o, Claude, Gemini) and a system prompt.
  • UserProxyAgent — acts as a human proxy. Can execute code locally (in a Docker sandbox or on the host), and can either auto-reply or pause for a real human to respond.
  • GroupChat — orchestrates multiple agents into a conversation with configurable speaker selection (round-robin, auto, custom). The GroupChatManager handles turn-taking.
  • AutoGen Studio — a visual, no-code interface for building and testing AutoGen workflows. Ships separately; built on React + FastAPI.

AutoGen 0.2 vs 0.4

AutoGen has two active major versions with different architectures:

  • AutoGen 0.2 (pyautogen) — the widely adopted classic API. ConversableAgent + GroupChat pattern. Simpler to get started, extensive examples and community. Most existing AutoGen tutorials use this version.
  • AutoGen 0.4 (autogen-agentchat) — a rewrite with an event-driven, actor-model architecture. Supports distributed agent teams, typed message protocols, and cancellation. Not backward compatible with 0.2. More suitable for production-scale systems.

The two versions coexist: install pyautogen for 0.2, autogen-agentchat for 0.4. Community consensus in mid-2026 is that 0.2 is more practical for most use cases; 0.4 is for teams building distributed production systems.

amux in Depth

amux is an open-source control plane for running an AI engineering team from a single dashboard. It manages the operational reality of running Claude Code, OpenAI Codex CLI, or Gemini CLI sessions at scale: usage-limit resume, reboot recovery, cost tracking, work coordination, and mobile monitoring.

Key operational capabilities that AutoGen doesn't provide:

  • Recovery — when a provider usage limit hits, amux holds delivery and resumes at the reset time. The amux server restarts through launchd or systemd, and on macOS every worker comes back in its own conversation after a reboot. Stall detection flags stuck work and sends owner alerts.
  • Context compaction — Claude Code compacts its own context as it fills, and amux lets you set the compaction threshold per session.
  • Atomic task claiming — the kanban board uses SQLite compare-and-swap so multiple agents can pull from the same task queue without duplicate work. Essential for fleet-scale automation.
  • Multi-runtime — Claude Code (primary), OpenAI Codex CLI, and Gemini CLI. If one provider's rate limits are saturating, distribute across runtimes.
  • Mobile dashboard — a PWA and native iOS app with real-time SSE updates. Monitor and steer your fleet from your phone. Sessions restore their state after iOS evicts the backgrounded app.

Why Not Both? (Composition Patterns)

AutoGen and amux are complementary, not competitive. The most powerful patterns use AutoGen for the reasoning layer and amux for the execution layer.

Pattern 1: AutoGen supervisor → amux REST API → Claude Code sessions

An AutoGen AssistantAgent receives a high-level task ("refactor all authentication endpoints to use the new middleware"). It decomposes the work into subtasks and POSTs them to the amux board via POST /api/board. A second AutoGen agent monitors the board via GET /api/board and reports completion. Claude Code sessions running inside amux pick up tasks via the kanban system and execute them.

# AutoGen agent posting a subtask to amux
import requests
requests.post("https://localhost:8824/api/board", json={
    "title": "Refactor auth middleware in /api/users.py",
    "session": "claude-code-worker-1",
    "status": "todo"
}, verify=False)

# AutoGen agent reading session output (peeking)
output = requests.get(
    "https://localhost:8824/api/sessions/claude-code-worker-1/peek",
    params={"lines": 50}, verify=False
).json()["output"]

Pattern 2: amux as AutoGen's code-execution backend

Use amux's REST API as a custom code-execution tool in an AutoGen agent. Instead of AutoGen running code in a local subprocess or Docker container, it sends code to a persistent Claude Code session in amux. This gives you the same coding-specialized model behavior with amux's session persistence and usage-limit resume on top.

# AutoGen tool definition: "run this in a coding agent session"
def run_in_coding_agent(task: str, session_name: str = "code-worker") -> str:
    """Send a task to an amux-managed Claude Code session."""
    r = requests.post(f"https://localhost:8824/api/sessions/{session_name}/send",
        json={"text": task}, verify=False)
    return r.json().get("status", "sent")

Pattern 3: Parallel AutoGen + amux monitoring

Run AutoGen workflows in their own amux sessions. A data-analysis AutoGen workflow runs as a session named autogen-research; a coding AutoGen workflow runs as autogen-code. amux's dashboard shows both alongside your Claude Code sessions, and stall detection and usage-limit handling apply to them the same way.

FAQ

Is AutoGen better than amux for coding tasks?

They're not directly comparable for coding tasks — they solve different parts of the problem. AutoGen provides the reasoning patterns (how agents collaborate, how they decide what to do next). amux provides the execution infrastructure (keeping the coding sessions running through usage limits, flagging stalls, showing you what's happening). For coding specifically, most teams find that running Claude Code inside amux is more practical than using AutoGen's UserProxyAgent code execution — Claude Code is a coding-specialist model with CLAUDE.md context and yolo mode, which AutoGen doesn't replicate.

Does AutoGen have recovery for long-running sessions?

Not built-in. AutoGen conversation objects live in Python memory — if the process dies, the conversation is lost. You have to implement your own persistence and recovery logic using AutoGen's checkpointing APIs or external state stores. amux keeps tmux-backed sessions going through usage limits (delivery resumes at the provider's reset) and, on macOS, brings every worker back in its own conversation after a reboot. Restarting a crashed agent process is not built into the amux server today; an optional macOS script (scripts/tmux-watchdog.sh, not installed by default) restarts crashed Claude Code workers. Stall detection and alerts tell you when a session stops.

Can I use AutoGen 0.2 and AutoGen 0.4 at the same time?

Not in the same Python environment — they have conflicting package names (pyautogen vs autogen-agentchat). Use separate virtual environments if you need both. In mid-2026, most production teams stay on 0.2 unless they specifically need the distributed actor model features in 0.4. AutoGen 0.4 is a complete architecture rewrite, not an incremental update.

How does amux compare to AutoGen Studio?

AutoGen Studio is a visual builder for creating and testing AutoGen workflows — it's a no-code editor on top of the AutoGen framework. amux is an operational dashboard for running any tmux-backed coding agent session (Claude Code, Codex, Gemini CLI). They're almost completely different tools: AutoGen Studio helps you design agent logic; amux helps you run agents at scale with monitoring, stall alerts and usage-limit resume. You can use both — design your AutoGen workflow in Studio, then run it as a managed session inside amux.

What does amux add that Claude Code Agent Teams doesn't?

Claude Code's built-in Agent Teams (claude --agent-teams) spawns parallel Claude Code sub-agents using git worktrees for a single high-level task. When the task is done, the sub-agents exit. amux is persistent infrastructure: sessions survive across tasks, the kanban board persists state, stall detection runs continuously, and you can monitor and steer everything from a mobile app. Agent Teams is a one-shot fan-out; amux is an always-on fleet. Both are useful — Agent Teams for a single complex task, amux for ongoing parallel development across many tasks and sessions.

Summary

AutoGen builds the brain; amux runs the hands. AutoGen is the right tool when you need to program sophisticated agent reasoning — group chats, tool-calling pipelines, conversation patterns. amux is the right tool when you need to operate AI coding agent sessions at scale: usage-limit resume, mobile monitoring, task coordination, and cost tracking.

The best AI engineering teams use both: AutoGen to orchestrate complex workflows, amux to run and monitor the coding sessions executing those workflows. They complement each other naturally because they operate at different layers of the same stack.
