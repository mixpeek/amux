amux vs DIY tmux Scripts

You can manage Claude Code in tmux manually. Here's what happens when you try to scale it.

Last updated: September 29, 2026

Quick answer: DIY tmux scripts work fine for 1-2 interactive Claude Code sessions. When you want to run 5-10 agents unattended overnight and check in from your phone, you spend more time maintaining the scripts than shipping features. amux is what you'd build after six months of maintenance if you kept going — minus the six months.

The typical DIY path

It starts simply. Three tmux commands:

# Start a session
tmux new-session -d -s agent1 "claude"

# Send a task
tmux send-keys -t agent1 "implement the user auth flow" Enter

# Read the output
tmux capture-pane -t agent1 -p

This works. For one session. Then you add a second, and write a loop. Then you want to see what both are doing at once, so you write a status checker. Then one crashes at 2am and you write a restart watcher. Then two agents race on the same task and corrupt a file, so you write a task-claiming mechanism. Then context overflows silently and neither agent is doing anything, so you add ANSI parsing. Then you can't check in from your phone without SSH.

Six months later you have a bash script that is 800 lines and still breaks in new ways. That is amux, but untested and maintained by you alone.

The self-healing problem in detail

The hardest part of DIY tmux is self-healing. Claude Code sessions fail in at least four distinct ways, each with different detection and recovery logic:

Context overflow. Claude Code hits its context window and exits to a shell prompt. Your session is now running a shell, not Claude. Detection requires recognizing the shell prompt pattern in tmux output. Recovery requires restarting Claude and either summarizing the prior context or replaying the task from scratch. Getting this right — without false-firing on legitimate shell commands in the task — takes several iterations.

Usage limit hit. Claude Code displays a "Usage limits reached" screen and waits. The session is alive but doing nothing. Detection requires parsing this specific screen. Recovery requires waiting for the reset window and then pressing Enter or sending a prompt.

Stuck prompt. An agent is waiting for confirmation on a file deletion, database migration, or other action that requires approval. The output looks similar to normal idle — both are paused. Distinguishing "waiting for approval" from "thinking" requires understanding Claude Code's terminal output structure.

Process crash. Claude exits with a non-zero status. The tmux pane shows a shell prompt or an error. Recovery requires restarting and, ideally, replaying the last message so the agent knows what it was doing.

amux handles all four. DIY scripts typically handle crash restart — the obvious one — and leave the rest as manual interventions.

The race condition problem

If you have 5 agents all reading from a shared task list and claiming work, you need atomic claiming. Two agents reading the same "todo" item and both starting it will corrupt the same file or submit conflicting commits.

amux uses SQLite with compare-and-swap semantics: an agent can only claim a task if it is still in todo state at the moment of the claim. The claim is atomic; two agents racing on the same task result in exactly one claim and one polite rejection. The other agent moves to the next item.

Implementing this with bash and file locks is possible but subtle: you need exclusive locks, timeout handling, and a recovery path when a lock holder crashes. Most DIY implementations skip the subtlety and get occasional duplicate work or corrupted files.

What happens at 5+ agents

A common pattern: you build a 2-agent setup with bash scripts, it works, you add more agents. By 5 agents the scripts are doing things like:

for i in 1 2 3 4 5; do
  status=$(tmux capture-pane -t agent$i -p | tail -5)
  # is it working? is it stuck? is it done?
  # each agent needs different handling...
done

The output parsing grows to handle every variation in Claude Code's terminal output. The restart logic grows to handle each failure mode. The task-claiming logic grows to handle races. Eventually you have something that mostly works but occasionally does something strange at 3am and you don't know why.

amux is the tested, maintained version of this. The same Rust binary used by everyone running amux handles the edge cases that emerge at scale — and the fixes go into every user's installation on the next brew upgrade.

September 2026: what's new in amux

Recent amux releases added capabilities that are essentially impossible to replicate in DIY scripts:

  • Approval memory. When you approve an action in the needs-input panel, amux saves it as a standing rule. The next agent requesting the same action type proceeds without pausing. One approval prevents 50 future interruptions. A DIY script would need a persistent approval store, a matching algorithm, and scope management across sessions.
  • Vault checkout. amux order --url runs a full headless checkout flow — navigate, fill, confirm, return receipt. Useful for procurement and subscription management. Implementing this in bash requires a headless browser library, session management, and receipt parsing.
  • Needs-input owner gating. Destructive actions stay with the owner; downstream agents cannot override them. Implementing this kind of role-based action routing in tmux scripts requires significant custom architecture.
  • CUA computer-use sandboxes. amux runs a CUA desktop sandbox for native apps, OS dialogs, and bot-blocked flows. There is no equivalent DIY path for this.

When DIY tmux is still the right answer

  • 1-2 sessions, interactive. If you're running a single Claude Code session and watching it work, a few tmux commands are all you need. amux adds overhead you won't use.
  • You want full control over every detail. Custom scripts give you full flexibility. amux is opinionated about how sessions are managed. If your workflow is unusual enough that amux's model doesn't fit, building custom tooling may be the right call.
  • Minimizing dependencies. amux requires tmux and a Rust binary. If your environment is locked down and you can't install new software, bash scripts that only call tmux directly have lower requirements.

Migration path

amux is not a replacement for your tmux sessions — it manages them. Your existing tmux workflow stays; amux adds the fleet coordination layer on top. You don't migrate your sessions; you register your project and amux wraps it:

curl -fsSL https://amux.io/install.sh | bash

# Register your project (wraps existing sessions or creates new ones)
amux register myproject --dir ~/Dev/myproject --yolo

# Start the session
amux start myproject

# Open the dashboard
amux serve  # → https://localhost:8824
