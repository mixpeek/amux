amux vs LangGraph

LangGraph builds the decision graph. amux runs the coding-agent fleet. Updated July 2026.

Quick answer: LangGraph (~38k ★, MIT) is a Python/TypeScript framework for building stateful multi-agent workflows in code — nodes are functions, edges are transitions, state is checkpointed. amux (310 ★, MIT+CC) is an open-source control plane that runs Claude Code, Codex, and Gemini CLI sessions from a web dashboard, with built-in self-healing, kanban coordination, and mobile management via iOS app. LangGraph defines how agents decide; amux manages the sessions that execute. Most teams that need both eventually combine them.

What each tool actually is

LangGraph is a graph-based framework for building stateful, multi-actor LLM applications. You write Python (or TypeScript) code: nodes are functions that call LLMs or take actions, edges define how state flows between them, and checkpointers persist state across steps. It sits at the same layer as your application code — it is your agent logic.

amux is a fleet operator for coding agents. Install it, register sessions (Claude Code, Codex, Gemini CLI), and amux handles the rest: launching tmux sessions, watching for crashes and context exhaustion, replaying on recovery, syncing state to a shared kanban board, and streaming output to your web dashboard or phone. You don't write code to manage the fleet — you monitor and steer it from a UI.

The framing that helps most: LangGraph is where you build the brain; amux is where you run the hands. LangGraph defines decisions; amux manages the sessions executing them.

When to choose amux

  • You want to run 10-50 Claude Code, Codex, or Gemini CLI sessions in parallel — without writing Python orchestration code
  • You need unattended overnight operation with automatic crash recovery and context compaction handling
  • You want a web dashboard and iOS app to monitor your fleet from anywhere
  • Your agents are general-purpose coding sessions pulling tasks from a shared kanban board
  • You want built-in CRM, email, browser automation, and scheduler as part of the same system
  • You want to self-host on your own machine with zero cloud dependencies (single Rust binary)

When to choose LangGraph

  • You're building a custom agent application that needs fine-grained programmatic control — specific nodes, conditional edges, complex branching
  • You need graph-level state checkpointing and deterministic replay for your agent workflow
  • Your agents call LLM APIs directly (not Claude Code CLI) and you're integrating them into a larger application
  • You need human-in-the-loop at the graph level — interrupting mid-graph and resuming based on user input
  • You're building a ReAct agent, supervisor hierarchy, or parallel subgraph workflow that requires framework-level control
  • Your team is comfortable writing Python/TypeScript and wants code-first agent orchestration

Why not both?

amux and LangGraph solve different problems and compose naturally. Here are three patterns for using them together:

Pattern 1: LangGraph supervisor → amux coding fleet

A LangGraph supervisor graph handles the decision logic: which tasks to create, in what order, whether a result needs revision. When it decides a coding task should run, it posts to amux's REST API to spawn or steer a Claude Code session.

# LangGraph node that delegates to amux
import requests, os

def coding_node(state):
    amux_url = os.getenv("AMUX_URL", "https://localhost:8824")
    task = state["current_task"]
    # issue task to amux session
    requests.post(
        f"{amux_url}/api/sessions/{state['agent_name']}/send",
        json={"text": task["prompt"]},
        verify=False
    )
    # poll for completion
    while True:
        peek = requests.get(
            f"{amux_url}/api/sessions/{state['agent_name']}/peek",
            verify=False
        ).json()
        if "TASK COMPLETE" in peek.get("output", ""):
            return {**state, "result": peek["output"]}

Pattern 2: amux board as LangGraph shared memory

Multiple LangGraph agent instances running in parallel all read from and write to the amux kanban board via REST API. Each agent claims tasks atomically (POST /api/board/TASK-ID/claim), preventing duplicated work without needing a shared LangGraph state. amux's SQLite compare-and-swap is the synchronization primitive.

Pattern 3: LangGraph decision agent + amux coding sessions side-by-side

One Claude Code session in amux is dedicated to running a lightweight LangGraph supervisor — it receives the backlog, decomposes it into tasks, and posts them to the amux board. Other sessions pull tasks from the board and execute them with full Claude Code tooling (files, git, shell, browser). LangGraph provides the decomposition intelligence; amux provides the execution infrastructure and monitoring.

FAQ

What is LangGraph and how does it work?

LangGraph is an open-source Python/TypeScript library (~38k ★, MIT) from the LangChain team for building stateful, multi-actor LLM applications as graphs. You define a StateGraph where nodes are functions (typically LLM calls or tool invocations) and edges are conditional transitions between them. State is carried through the graph and can be checkpointed to databases like SQLite, PostgreSQL, or Redis. LangGraph is used to build ReAct agents, supervisor agent hierarchies, and human-in-the-loop workflows.

Does amux replace LangGraph?

No — they operate at different layers. amux is an operations platform for running Claude Code / Codex / Gemini CLI sessions with a dashboard and self-healing. LangGraph is a framework for building custom agent decision logic in code. You'd reach for amux when you want to run many coding agent sessions from a UI without writing orchestration code. You'd reach for LangGraph when you're building a custom agent application that needs fine-grained programmatic control over how agents make decisions. They're often used together.

Can LangGraph run Claude Code CLI sessions?

Not directly — LangGraph calls LLM APIs (via ChatAnthropic, ChatOpenAI, etc.) rather than managing terminal sessions running the Claude Code CLI. If you want to run actual claude CLI processes in tmux with self-healing, board coordination, and a monitoring dashboard, that's amux's job. However, you can build a LangGraph node that calls amux's REST API to spawn or interact with Claude Code sessions.

Is amux self-hosted? What about LangGraph Platform?

amux is fully self-hosted by default — single Rust binary on your own machine, zero cloud dependency (MIT + Commons Clause). amux Cloud (from $39/month) runs the same amux for you on a dedicated always-on server at yourname.amux.io. Self-hosting stays free with every feature. LangGraph itself (the library) is open source and self-hostable. LangGraph Platform is Anthropic's managed hosted deployment service for LangGraph applications — a separate paid product for teams who don't want to operate their own infrastructure.

How does amux coordinate agents without LangGraph?

amux uses a SQLite-backed kanban board with atomic compare-and-swap claiming (POST /api/board/TASK-ID/claim — 200 if won, 409 if already claimed). Any session — Claude Code, Codex, or Gemini CLI — can claim a task and the SQLite CAS prevents duplicated work without coordination code. Sessions also communicate via the Messages API (amux send SESSION "message") and can read each other's output with GET /api/sessions/NAME/peek. It's a minimal coordination layer that doesn't require writing Python orchestration code.
