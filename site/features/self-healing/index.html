Recovery: what amux does when agents stop

amux keeps agents going through usage limits and restarts: delivery is held and resumes at the provider's reset, and on macOS every worker comes back in its own conversation after a reboot.

// quick answer

Does amux restart Claude Code agents automatically? Not when an agent process crashes. Restarting a crashed agent process is not built into the amux server today. On macOS, an optional script, scripts/tmux-watchdog.sh, restarts crashed Claude Code workers; it runs as a separate launchd job that the installer does not set up. Nothing does this on Linux or for other providers. amux does resume agents after usage limits, restarts its own server through launchd or systemd, brings every worker back after a macOS reboot, and alerts you when board work or a goal stalls.

The ways an unattended agent stops

Most people running several Claude Code agents overnight hit the same handful of stops. Here is what amux does about each one today, and where it leaves the job to you.

1. Usage limits (most common)

A provider's usage or rate limit stops every agent on that account. Without help, each one sits until somebody types "continue" after the reset.

What amux does: it holds message delivery to the limited agent and resumes it at the provider's reset time. This works on every platform and is on by default.

# ~/.amux/server.env, or the worker's Scope tab for AMUX_AUTO_RESUME
AMUX_AUTO_RESUME=1          # default on; 0 turns automatic resume off
AMUX_RATE_LIMIT_ACTION=wait # default; "off" leaves Claude Code's usage-limit menu for you

2. Restarts and reboots

The amux server can die, and the machine can reboot under a fleet of running agents.

What amux does: the installer runs the server as an OS service (launchd on macOS, a systemd user service on Linux), which restarts the server process if it exits. On macOS the installer also adds a login job, com.amux.fleet-start, that brings every non-archived worker back after a reboot, each resumed in its own conversation. It runs at login, so after an unattended reboot the workers start once someone logs in (or with automatic login turned on).

3. Context filling up

A long session fills its context window.

What happens: Claude Code compacts its own context and continues. amux lets you set the threshold it compacts at; the value lives in Claude Code's autoCompactWindow setting, and amux records the window each launch resolved and warns when it shrinks between launches.

4. Tool-approval prompts

Unless permissions are skipped, Claude Code pauses at tool calls and waits for someone to approve them.

What amux does (YOLO mode): the --yolo flag is an alias for Claude Code's --dangerously-skip-permissions, so the prompt never appears. Register overnight workers with it.

amux register myproject --dir ~/Dev/myproject --yolo

5. Stalls

Sometimes work just stops moving: a board card sits in progress, an orchestrator gets stuck, or a goal's progress count stops changing.

What amux does: stall detection surfaces stalled board work and stuck orchestrators, and owner alerts fire. For a worker with a goal checker, the owner gets one push and one email when progress has not moved for AMUX_GOAL_STALL_H hours (default 6, 0 turns it off).

Crashed agent processes

Restarting a crashed agent process is not built into the amux server today. On macOS, an optional script, scripts/tmux-watchdog.sh, restarts crashed Claude Code workers; it runs as a separate launchd job that the installer does not set up. Nothing does this on Linux or for other providers. The script skips archived, paused and isolated workers, and holds a worker for a human after three restarts in 30 minutes rather than restarting it forever. Setup is in the recovery configuration guide.

Configuration reference

Frequently asked questions

Does amux automatically restart Claude Code when it crashes?

No. Restarting a crashed agent process is not built into the amux server today. On macOS, an optional script, scripts/tmux-watchdog.sh, restarts crashed Claude Code workers; it runs as a separate launchd job that the installer does not set up. Nothing does this on Linux or for other providers. What amux does do is keep the rest of the fleet going: it resumes agents after usage limits, the OS service restarts the amux server, on macOS every worker comes back after a reboot, and stall detection alerts you when work stops moving.

What is YOLO mode?

YOLO mode is the --yolo flag, an alias for Claude Code's --dangerously-skip-permissions. Claude Code then skips its tool-approval prompts, so an unattended worker never waits on one. Set it per worker with amux register myproject --dir ~/Dev/myproject --yolo, or turn on "YOLO by default for new workers" in the dashboard's Settings, Workers tab.

How do I set the compaction threshold?

Claude Code compacts its own context, and amux lets you set the threshold it compacts at. The value lives in Claude Code's settings (autoCompactWindow, globally or per model), and amux records the window each launch actually resolved and warns when a launch resolves a smaller one than the launch before.

Can amux run agents unattended overnight?

Yes, within these limits. Usage limits hold delivery and resume at the provider's reset, the amux server is restarted by launchd or systemd if it dies, and on macOS a login job brings every non-archived worker back after a reboot. Stall alerts tell you when board work or a goal stops moving. An agent whose process crashes stays down unless you run the optional macOS script.

What happens when a provider usage limit hits?

amux holds message delivery to that agent and resumes it at the provider's reset time, on every platform. Automatic resume is on by default (AMUX_AUTO_RESUME). On Claude Code's usage-limit menu amux picks the wait option; set AMUX_RATE_LIMIT_ACTION=off to leave that menu for you.
