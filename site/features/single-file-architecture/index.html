Rust Workspace Architecture
How amux is Built (2026)

amux is a 4-crate Cargo workspace that compiles to a single binary. No Docker, no config files required. Commit a change — a background build watcher compiles it and the running server self-adopts within seconds.

Last updated: August 12, 2026

Quick answer: amux is a 4-crate Cargo workspace — amux-server (axum HTTP + REST + SSE), amux-dashboard (real static files: app.js, app.css, index.html, sw.js), amux-core (shared types), and amux-cli (Rust CLI). The workspace builds to one binary. A background launchd agent watches for new commits, rebuilds in ~60s, and the running server exits cleanly so launchd relaunches it with the new binary. SQLite is the only database. The only system dependency is tmux.

What lives in the workspace

  • crates/amux-server — axum HTTP server: REST API (~60 endpoints in src/api/, one module per family), SSE event streaming backbone, SQLite layer (src/db/), append-only SQL migrations (migrations/), orchestration jobs (src/runtime_jobs/)
  • crates/amux-dashboard — the web SPA as real static files: static/app.js, static/app.css, static/index.html, static/sw.js. No inline HTML. No build step for the dashboard itself. The server binary serves them directly.
  • crates/amux-core — shared types and interfaces used by both the server and the CLI
  • crates/amux-cli — the amux-rs Rust CLI (board, send, alert, and other subcommands)
  • amux (bash) — the legacy bash CLI the fleet still runs; an HTTP client of the server, not part of the Rust build

Why a compiled Rust workspace?

  • No dependency hell — ./install.sh builds the binary and registers the launchd agents. Nothing to pip install, npm install, or docker pull.
  • Single compiled binary — copy it to a new machine; it runs immediately alongside tmux. No package manager, no virtualenv, no node_modules.
  • Auditable in an afternoon — four crates with clear boundaries: server, dashboard, types, CLI. Every endpoint is in src/api/. Every SQL migration is in migrations/. No hidden framework magic.
  • Commit-to-ship — the auto-builder watches for new commits, not file saves. This prevents half-written edits from triggering a rebuild mid-change.
  • Zero runtime surprises — Rust’s type system catches shape errors at compile time. SQLite is the only database. There is no ORM, no cache layer, no message broker.

How the auto-build cycle works

A launchd agent runs scripts/rust-auto-build.sh every 60 seconds. The script checks whether the last commit touching crates/ or Cargo.* has moved since the previous build. If so, it runs cargo build --release (with CARGO_TARGET_DIR=~/.amux/rust-build-target — shared across sessions, so each parallel build hits a warm cache), installs the binary to ~/.local/bin/amux-server-rs, and the running server detects the new binary on its next health-check cycle, exits cleanly, and launchd restarts it with the updated code.

Because the target directory is shared, two concurrent sessions doing incremental rebuilds of the same commit finish in roughly the time of one — the second builder waits for the lock and then finds the work already done.

Contributing

The pattern for a new REST endpoint: add a handler module in crates/amux-server/src/api/ and register it in the router in crates/amux-server/src/lib.rs. Run the syntax gate after any edit:

cargo check --workspace

For dashboard changes (crates/amux-dashboard/static/app.js), bump APP_VER in app.js and CACHE in sw.js together, or browsers holding the cached script never receive the fix. Verify the JS parses:

node --check crates/amux-dashboard/static/app.js

Commit — the auto-builder ships it within about 60 seconds. Before pushing, run:

cargo clippy --workspace --all-targets -- -D warnings
cargo test -p amux-server

Frequently asked questions

How is amux's server built?

amux is a 4-crate Cargo workspace: amux-server (axum HTTP server + REST API + SSE backbone), amux-dashboard (real static files: app.js, app.css, index.html, sw.js), amux-core (shared types), and amux-cli (the Rust CLI). The whole workspace compiles to a single binary with no runtime dependencies beyond tmux.

Does amux require Docker?

No. amux compiles to a single Rust binary and requires only tmux at runtime. Install with ./install.sh — it builds the binary and registers the launchd agents. No Docker daemon, no container registry, no image builds.

How does amux auto-deploy updates?

A background launchd agent (scripts/rust-auto-build.sh) runs every 60 seconds. When the last commit touching crates/ or Cargo.* changes, it rebuilds the binary and installs it. The running server detects the new binary, exits cleanly, and launchd restarts it with the updated code. Commit a change — it is live within about 60 seconds.

How do I contribute to amux?

Clone the workspace, run cargo check --workspace after edits, and commit. The auto-builder picks up the commit and ships the new binary within about 60 seconds. For a new REST endpoint, add a handler module in crates/amux-server/src/api/ and register it in the router.

Is the amux dashboard a separate web app?

No. The dashboard is real static files (app.js, app.css, index.html, sw.js) in crates/amux-dashboard/static/, served directly by the amux-server binary. There is no separate build step, no webpack, no npm install. Edit the static files, bump the cache version, and commit — the auto-builder ships it.

Run your AI engineering team from one dashboard

amux is an open-source control plane for AI coding agents — resumes after usage limits and reboots, phone-first, MIT + Commons Clause, single compiled binary.

git clone https://github.com/mixpeek/amux && cd amux && ./install.sh
amux register myproject --dir ~/Dev/myproject --yolo
amux start myproject
# → https://localhost:8824
