AI Agent Fleet

A collection of AI coding or automation agents running in parallel under a shared control plane — with a common task queue, inter-agent coordination, self-healing, and remote monitoring.

Published: August 27, 2026

Run an AI engineering team from one dashboard

View amux on GitHub ★
Definition: An AI agent fleet is a group of AI coding or automation agents — such as Claude Code, OpenAI Codex CLI, or Gemini CLI instances — running in parallel under a shared control plane. The fleet has a common task queue, coordination layer, monitoring dashboard, and self-healing watchdog. Running 10 Claude Code agents overnight to generate tests across a codebase, each claiming tasks from a shared kanban board, is an example of operating an AI agent fleet.

What makes a group of agents a fleet?

Launching two Claude Code windows manually is not a fleet. A fleet requires shared infrastructure that coordinates what agents do, tracks what each has completed, prevents duplicate work, keeps agents running when they crash or hit a context limit, and gives a human visibility into the whole operation from a single view — or a phone.

The term became common in 2025 as teams moved from individual AI coding assistants (one agent per developer) to engineering teams where a single person oversees dozens of AI agents working in parallel on distinct tasks. An AI agent fleet is the equivalent of a traditional software engineering team — but every team member is an AI agent, and the "manager" is one human with a dashboard and a phone.

Fleet components

A complete AI agent fleet control plane has four layers:

Layer What it does amux equivalent
Agent sessions The individual AI coding agents running tasks — Claude Code, Codex CLI, Gemini CLI, or other headless runtimes tmux sessions per agent, each running a supported runtime
Task queue / coordination A shared board where tasks are posted and agents claim work atomically — preventing two agents from taking the same job SQLite-backed kanban board with atomic compare-and-swap claiming
Self-healing watchdog A process that monitors agent health, detects context overflows and crashes, and restarts or compacts sessions automatically Built-in watchdog with auto-compact, crash restart, and stuck-prompt detection
Monitoring and oversight A dashboard that shows live output from every agent, a mobile interface for remote approval and steering, and message history for inter-agent communication Web dashboard (SSE-streamed), iOS app + PWA, Messages tab

Fleet vs single agent vs orchestrator vs task queue

Concept Definition Example Scope

Why use a fleet instead of a single agent?

A single agent is throughput-bounded by one context window. A codebase with 200 files to refactor takes one agent as long as it takes to process them serially. A fleet of 10 agents splits the work: each agent handles 20 files, and the total wall-clock time is roughly one-tenth of the single-agent time. For work that can be decomposed — writing tests, generating documentation, running security audits, updating dependencies across modules — fleet throughput compounds directly with fleet size.

Beyond throughput, a fleet adds resilience. When one agent hits its context limit or encounters an error, the self-healing watchdog handles recovery automatically. Overnight runs complete without a human sitting at the desk. The next morning you review the results, not the crash logs.

How amux manages an AI agent fleet

amux is the open-source control plane for running an AI agent fleet from a single dashboard or your phone. When you use amux, your fleet gets:

  • Parallel agent sessions — launch 1 to 50+ Claude Code, Codex, or Gemini CLI sessions headlessly in tmux, each isolated in its own project directory
  • Shared kanban board — post tasks before a run; agents claim them with atomic SQLite compare-and-swap so no two sessions take the same job
  • Self-healing watchdog — auto-compacts on context overflow, restarts on crash, replays the last message on stuck prompts; your fleet runs overnight without human intervention
  • Inter-agent messaging — sessions send and receive messages via REST API, coordinate handoffs, and delegate sub-tasks through named @worker channels
  • Session cloning — duplicate any live session to run parallel prompt experiments, compare outputs, then pick the better result and discard the other
  • Mobile oversight — the iOS app and installable PWA give you live fleet visibility, steering messages, and approval gates from anywhere
  • Business tooling — scheduler, CRM, Gmail-API email, browser automation, and notes run in the same fleet alongside coding agents

Fleet size and scaling

Most developers start with 3–5 agents and scale up as they gain confidence in the fleet's self-healing behavior. The practical ceiling on a single machine is memory: each Claude Code session uses roughly 200–400 MB, so a MacBook Pro with 32 GB of RAM can comfortably sustain 10–15 agents without swapping. A Linux server with 64 GB can run 30–50+.

API rate limits are often the binding constraint before hardware. Claude Code's rate limits vary by plan — Max plan subscribers get higher limits than Pro. See the Claude Code rate limits guide for fleet-specific tuning, and the scaling to 50+ agents guide for machine sizing recommendations.

Multi-runtime fleets

A fleet does not need to be homogeneous. amux supports mixed-runtime fleets where Claude Code, Codex CLI, and Gemini CLI agents run side-by-side in the same fleet, sharing the same kanban board and messaging layer.

Teams use multi-runtime fleets to assign specific runtimes to the tasks they handle best: Claude Code for complex reasoning and architecture tasks, Codex for high-throughput boilerplate generation, Gemini for documentation and summarization. The board distributes work across all runtimes; the dashboard shows all sessions in a single view regardless of which runtime each is running. See the multi-runtime agent setup guide.

FAQ

What is an AI agent fleet?
A group of AI coding or automation agents running in parallel under a shared control plane. The fleet shares a task queue, coordination layer, self-healing watchdog, and monitoring dashboard. A solo developer running 10 Claude Code agents overnight to generate tests across a codebase is operating an AI agent fleet.
How is a fleet different from a single agent?
A single agent processes tasks serially and requires human presence to restart on failure. A fleet processes tasks in parallel across many agents, claims work from a shared board to prevent duplication, heals automatically from crashes and context overflows, and runs unattended overnight with remote monitoring from a phone.
What does a fleet control plane do?
A fleet control plane launches, monitors, and self-heals agent sessions. It provides a shared task board, inter-agent messaging, a self-healing watchdog, and a web and mobile dashboard. amux is a fleet control plane for Claude Code, Codex CLI, and Gemini CLI fleets.
How many agents can a fleet run?
Fleet size is bounded by host memory (each agent uses 200–400 MB) and API rate limits from the model provider. A MacBook Pro with 32 GB can run 10–15 agents; a Linux server with 64 GB can run 30–50+. amux itself imposes no session count cap. See the scaling guide for sizing details.
Can a fleet run different AI runtimes together?
Yes. amux supports mixed-runtime fleets where Claude Code, Codex CLI, and Gemini CLI agents run side-by-side, sharing the same board and messaging layer. Different runtimes can be assigned to different task types based on their strengths. See the multi-runtime setup guide.
What is the difference between a fleet and an orchestrator?
An orchestrator routes tasks to agents and manages dependencies. A fleet is the full collection of agents plus the control plane — launch, monitoring, self-healing, task coordination, inter-agent messaging, and human oversight. amux is a fleet control plane that includes an orchestration layer (the board and messaging system) as one of its components.
