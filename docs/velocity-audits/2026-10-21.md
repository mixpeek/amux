## Bottlenecks, ranked by velocity lost

### 1. Red main held 14 finished fixes out of the running build for 13 hours

Evidence:

- Builder log, 08:00 today: `CI-GATE tip d01e718fe is red; activating newest
  green 1804dccac (14 newer commit(s) not yet green) verdict=ci_gate_held_back`.
- `rust` workflow on main: 1 success in the last 20 runs (1804dccac at
  22:58Z). The rest failed or were cancelled from 19:25Z yesterday onward.
- Current failure: `spa-gates` dashboard unit tests, 8 peek tests (`not ok 90`
  to `not ok 98`, "full history cannot block streaming" and others), after the
  peek commits 41a40b5c6 / 6d8fc5989 / 8209fe385. Earlier:
  `bilateral_peers_bypass_isolation_and_group_boundary`,
  `every_directly_routed_api_path_is_in_the_table`, an e2e browser WebSocket
  reset.
- Held back and therefore invisible to Ethan: 96e5b8e36 (hide the top
  magnifying glass, 20:06), faa794a1d (restore the details one), 8209fe385 and
  6d8fc5989 (MSG-92354: delivered message missing in peek, slow search),
  21ead245e (MSG-92346 markdown on phone), 9370acf06, 54f5afecc, b135ef187 and
  27374a52c (disk cleanup).
- `amux requests` shows "on main not live" for 3 amux, 3 amux-admin and
  3 desktop requests.

Cost: at least one repeated ask (MSG-92394 at 07:33 re-requests the glass
removal that landed 11.5h earlier). Every fix from yesterday evening is unseen,
so Ethan cannot verify or give feedback on any of it.

Proposals:

- **1a. Say "held back by red CI" wherever Ethan looks.** `amux requests`
  prints "on main not live" with no reason. When the builder verdict is
  `ci_gate_held_back`, each such request should say "held: main red since
  <time>, failing <job/test>", and the dashboard header should carry the same
  one-line banner. The builder already knows both facts; they stop in a log
  file nobody reads.
- **1b. A red main gets an owner within minutes.** On the first red `rust` run
  on main, send the failing test names to the session named in the breaking
  commit's `Amux-Session` trailer, and re-send while red. If main is still red
  after a fixed budget (for example 60 minutes), revert the breaking commit
  automatically. Today `amux` fixed it at 07:42 (d01e718fe), about 12 hours
  after the first red, and only after the owner had started asking again.

### 2. The same request goes to several workers, and one of them builds the wrong thing

Evidence:

- Magnifying glass: MSG-92045 to amux (09:08), MSG-92344 to amux-admin (19:57),
  MSG-92355 correction (21:17: "I was referring to the worker list page, NOT
  the worker details page, undo"), MSG-92394 to amux (07:33). Commits:
  ca7d27355 removed the wrong one, faa794a1d reverted it, 96e5b8e36 removed the
  right one.
- Disk cleanup: MSG-92205 desktop, MSG-92356 amux-admin, MSG-92390 and
  MSG-92391 desktop, MSG-92395 amux.

Cost: 4 messages, 3 commits including a revert, and roughly 22 hours open for
a one-line UI change. Two workers working the same disk feature in parallel.

Proposals:

- **2a. Cross-worker duplicate detection on owner requests.** When an owner
  message matches an open request held by another worker, link them and tell
  both workers (and Ethan, in the send receipt) who already owns it.
- **2b. UI requests close with a screenshot of the exact element.** A worker
  closing a UI request posts the before and after crop of the element the
  owner's screenshot pointed at. ca7d27355 would have shown the wrong page.

### 3. Ethan has to poll amux-helper for status

Evidence: 39 open requests at amux-helper, most of them questions: MSG-92036,
92057, 92075, 92089, 92095, 92144, 92170, 92185, 92208, 92209 ("what were the
priorities I mentioned earlier?"), 92210, 92277, 92352, 92357, 92381, 92388.

Cost: about 15 owner messages spent asking "is it done / is it moving / when".
MSG-92209 shows the owner's own priorities were not written down anywhere he
could see.

Proposals:

- **3a. Owner priorities are stored, not remembered.** When Ethan states
  priorities to a worker (MSG-92095), persist them as that worker's goal list
  and show them on the worker card.
- **3b. A live progress line per long-running goal**: last measured step,
  next step, current blocker, and an ETA the worker updates. "Is it
  continuing?" should be answered by the worker card, not a message.

### 4. Requests stay open after they are answered or fixed

Evidence: 53 open owner requests across amux, amux-admin, amux-helper and
amux-cloud. Several are answered questions or are fixed and live (the
usage-limit resume asks MSG-92149/92152/92161 at amux-admin, while the fixes
fc927a54d, e55146a75 and be509590b are live in 1804dccac).

Cost: the open list is too noisy to tell what is still owed, which feeds
bottleneck 3.

Proposal:

- **4a. Close requests from the work, not from memory.** A commit made while a
  worker's active task is a request should carry that request's id
  automatically (the Tasks history already knows the task). A question that
  got an answer should close as answered at the turn's end.

### 5. A retried send delivered the same message twice

Evidence: MSG-92390 and MSG-92391 to desktop, identical text, 2 seconds apart,
both `submit_verdict: retried`, both `delivery: direct`.

Cost: the worker processed one request twice. Small, but it will repeat on
every flaky send.

Proposal:

- **5a. Idempotency key on owner sends.** The composer attaches one key per
  draft; the server delivers a key once and returns the first receipt to the
  retry.

### 6. A signed-out client polled all night

Evidence: from 100.66.26.84, 2112 `401` on `GET /api/pinned` and 1049 on
`GET /api/needs-input`, 2026-10-20 08:30 to 2026-10-21 07:14.

Cost: unknown. If that client is Ethan's phone or iPad, its dashboard has been
silently empty or stale for a day. Needs one confirmation from Ethan about
which device it is.

Proposal:

- **6a. A 401 stops the poll loop and shows a sign-in prompt**, and the server
  logs one WARN per client per hour instead of 3000 silent errors.
