## Bottlenecks, ranked by cost

### B1. The worker list failed after a 30 s wait, 378 times in five hours (top)

From 13:00Z to 18:00Z on 2026-11-02 the server logged 378
`sessions_cache_stuck` (101, 102, 45, 0 and 139 per hour). Your own devices
(Tailscale addresses) got 32 of those 503s, each after about 30 s
(`_amux_request_log`, average 30,086 ms). Fleet list builds in that window
took 19.3 s at the median, 68 s at p90 and 234 s at most (181
`sessions_build_exceeds_ttl`).

The five stack samples the server took while the builder was stuck
(`~/.amux/logs/sessions-stall-20261102T*.txt`) show why. The build makes a
database write inline (`record_task_changes`, through `Store::write`) and
waits for the single writer thread. That thread was busy with something
slow each time:

- 15:02Z: the storage sweep (`sweep_guarded_delete`) for the whole sample.
- 17:36Z: `throughput_store::evaluate_wip` from the orchestrator tick, for
  the whole sample.
- 13:15Z and 14:50Z: usage-account readings, browser and tool-event inserts
  queued ahead.
- 14:50Z and 15:02Z also had the build in `tmux capture-pane`.

The list view refuses to serve the last snapshot once a structural change
has invalidated it, so during these stalls every client waited 30 s and got
nothing.

Cost: about 16 minutes of your own waiting (32 x 30 s), plus the "worker
updates are unavailable" state for everyone else during those hours.

## Proposals

- **19a. The worker list never waits on the database writer (B1).** The
  fleet build should queue `record_task_changes` without waiting for the
  reply, so a slow writer cannot hold the list. Also cap how long one
  writer job holds the writer (the storage sweep and `evaluate_wip` should
  work in chunks) and log a verdict naming the job when it runs over. Check:
  zero `sessions_cache_stuck` in a day that has a storage sweep.
- **19b. A spec that reddens main twice in a day says who should fix it
  (B2).** `scripts/main-ci-watch.sh` already keeps one card per red stretch.
  It should also name the failing spec, the author of the spec's last change
  and how many of the day's red runs it caused, so a racing spec reaches its
  owner the same day. Today that took a velocity audit.
- **19c. A goal that stops before it is met tells you (B3).** When a
  worker's goal goes from active to cleared while `met` is false, tell you in
  that worker's thread: the condition, how long it ran, and what cleared it.
  You then decide whether to restart it. Today it stopped silently.

## Order of work

19a first: it cost you the most waiting, and it is amux server work in this
lane. The clipboard part of B2 is already fixed (6c1439179). 19c is small
once the clear event is found. 19b changes a fleet script and goes after.
